# Теплосеть: недостатки алгоритмов и план доработки

**Версия:** 1.0 · **Дата:** 19 сентября 2026 года  
**Назначение:** рабочий документ для разработчика по результатам текущего бенчмарка.  
**Расчётная модель:** актуальное техническое приложение из `ТЗ (1).zip`, а не прежнее приложение с реконструкцией.  
**Граница работы:** собраны результаты отчёта и предложенные в обсуждении доработки. Исходный код solver-а и его выходные GeoJSON здесь повторно не запускались и не проверялись.

> **Главное решение:** сохранить `B2-C` как контрольную реализацию; добавить возможность создавать развилки внутри новых труб; обеспечить полный пересчёт и независимую проверку; затем сравнить обычный и обученный выбор одинаковых действий. Не считать замену A* на нейросеть самостоятельным решением задачи проектирования сети.

## 1. Что команда делает в первую очередь

### Решения, которые предлагаем зафиксировать

| Приоритет | Решение | Результат работы |
|---|---|---|
| P0 | Зафиксировать код, конфигурацию и результаты `B2-C`; не заменять его незавершённой новой версией | Воспроизводимая контрольная точка и сохранённый выходной GeoJSON |
| P0 | Проверить полноту checker-а именно по новому ТЗ | Матрица правил, положительные тесты и намеренно испорченные решения |
| P1 | Добавить `JUNCTION_IN_EDGE` — присоединение к новой камере внутри выбранной трубы | B1/B2 могут рассматривать соединения, которых сейчас нет в наборе узлов |
| P1 | Логировать предложения, отказы, принятые изменения и происхождение лучшего решения | Понятно, что реально делает B3 и почему он не улучшает B2 |
| P2 | Реализовать общий граф коридоров и групповые объединения как отдельно измеряемые доработки | Геометрия и топология проверяются раздельными экспериментами |
| P2 | Доработать B3 до перестройки рёбер/поддеревьев, затем добавить адаптацию операторов | Не только перестановка порядка подключения, а изменение самой сети |
| P3 | Обучить R1/R2 на той же проверенной среде и том же пространстве действий | Можно измерить пользу обучения относительно сильного необучаемого поиска |

Это **предлагаемый порядок работ**, а не уже выполненные изменения. Подготовку обучающих сцен можно вести параллельно с P1/P2. Сравнительное обучение следует начинать после фиксации правил среды и версий генератора действий.

### Что сейчас не нужно делать

Не переписывать весь сервис только ради отказа от A*. Не объявлять RL бесполезным из-за хорошего результата B2. Не объявлять B2 оптимальным из-за совпадения с B3. Не возвращаться к старой модели реконструкции. Не считать «ноль нарушений» доказательством полноты checker-а без тестов его самого.

**Практический ориентир:** сначала расширить набор допустимых инженерных решений; потом сравнить способы выбора среди них.

## 3. Недостатки каждого алгоритма и действия разработчика

### 3.1. B0-GRID: оставить как контроль, не делать основным проектировщиком

**Что реализовано по отчёту.** Независимые подключения, прямой путь и восьмисвязный A*. Это исполняемый baseline текущего ядра. [B, «Что реализовано»]

**Главное ограничение постановки.** Каждое подключение рассматривается отдельно. Алгоритм не выбирает полноценную общую магистраль для группы потребителей. Цена одной линии не описывает эффект перераспределения расходов по всей новой сети.

**Отдельный риск геометрии.** Привязка к направлениям сетки ограничивает набор ломаных. Но без выходных GeoJSON нельзя утверждать, что именно этот запуск содержит запрещённые ступеньки: опубликован только итог checker-а.

**Что делать:**

1. Сохранить B0-GRID как контроль сложности и регрессий, а не удалять его из экспериментов.
2. Отделить интерфейс поиска отдельного пути от выбора схемы подключений.
3. Проверять и при необходимости геометрически упрощать путь до экспорта, сохраняя обязательные узлы, подход к ОКС и границы спецпроходов.
4. Повторять пространственную проверку после упрощения; нельзя сглаживать линию только в визуализации.
5. Не добавлять самовольную денежную надбавку за поворот: новое приложение её не предусматривает. [T, §2.1]

**Критерий готовности.** B0 воспроизводим; выдаваемая геометрия проверяется по актуальным правилам. Его экономический проигрыш совместным схемам не является программной ошибкой сам по себе.

### 3.2. B0-CORRIDOR: текущий lite не доказывает качество полного графа коридоров

**Что реализовано по отчёту.** Независимые подключения, прямой путь, обходы по углам препятствий и A*. Общего предрасчитанного corridor graph пока нет. [B]

**Ограничение.** Название версии не должно создавать впечатление, что уже протестирован полноценный общий граф допустимых коридоров. Перебор локальных обходов и общий граф — разные реализации.

**Что делать:**

1. Выделить `CorridorGraphBuilder`, которым пользуются все сравниваемые стратегии.
2. Включить заданные вводы ОКС, допустимые подходы к ним, камеры, кандидаты присоединения, геометрические точки обхода и разрешённые прямые переходы.
3. Разделять два графа: **кандидатный граф** возможных труб и **выбранную сеть**, за которую начисляется стоимость. Кандидаты сами по себе не являются построенными трубами.
4. Хранить длину, геометрию и пересекаемые ограничения; допустимость с учётом диаметра перепроверять после sizing. Один граф, проверенный для тонкой трубы, не гарантирует допустимость толстой.
5. Сохранять альтернативы коридоров, а не только один путь для пары точек.
6. Считать время построения графа отдельно и в общем времени решения. Не скрывать дорогую предварительную обработку.

**Критерий готовности.** Несколько стратегий работают на одной зафиксированной версии графа. Видны размеры графа, время построения, причины удаления рёбер и результат относительно исходного lite.

**Не обещаем заранее.** Полный граф не обязан победить на каждой сцене; расширение набора кандидатов может увеличить время поиска. Это проверяется экспериментом.

### 3.3. B1: добавить новые точки соединения и групповой выбор

**Что реализовано по отчёту.** Regret-2, присоединение к уже построенным узлам, полный пересчёт расходов и камер. Нет вставки в произвольную внутреннюю точку трубы и группового merge. [B]

**Главный недостаток.** Хорошая точка ответвления может лежать посередине длинного участка, а не в его существующем конце. При ограничении только готовыми узлами такой проект отсутствует среди действий.

**Второй недостаток.** Последовательное добавление по одному ОКС может не увидеть выгодное совместное решение для пары. Это риск конструктивной эвристики; отчёт не доказывает, что он реализовался на конкретной сцене.

**Что делать:**

1. Реализовать `JUNCTION_IN_EDGE` по разделу 5.
2. Добавить предложения `GROUP_CONNECT` для небольших групп, начиная с пар; перебор всех подмножеств в первый этап не включать.
3. Сравнивать предложения по полной стоимости получившейся сети, а не по длине нового отвода.
4. После каждого принятого изменения обновлять предложения, стоимость которых зависит от изменённых расходов, диаметров или вместимости камер.
5. Сохранять несколько начальных порядков как отдельный эксперимент, не подменяя этим новые геометрические действия.

**Критерий готовности.** На специально подготовленной сцене B1 создаёт камеру в ранее отсутствовавшей внутренней точке трубы; на парных сценах выбирает как совместный, так и раздельный вариант в зависимости от проверенной полной цены.

### 3.4. B2-U / B2-Q / B2-C: усилить текущую лучшую основу

**Что реализовано по отчёту.** Взвешенный медоид, три порядка формирования магистрали, выбор лучшего. Виртуальных узлов магистрали внутри рёбер нет. [B]

**Что пока неизвестно.** В отчёте не расшифрованы конкретные формулы весов и различия U/Q/C. Их нельзя придумывать по буквам. Разработчик должен указать эти формулы в конфигурации и документации.

**Ограничения:**

- Отсутствуют те же внутренние точки соединения, что нужны B1.
- Ограниченный набор центров/порядков не является перебором всех возможных схем сети.
- Совпадение итоговых чисел не показывает, одинаковы ли геометрия, распределение ОКС и места присоединения.
- Один прогон не позволяет надёжно выбрать между U/Q/C по малой разнице времени.

**Что делать:**

1. Зафиксировать неизменённый B2-C и его экспорт как контроль.
2. Подключить общий генератор junction-кандидатов; не создавать для RL более богатое пространство, чем для B2.
3. Локально сравнивать перенос камеры, новое ответвление, совместное подключение пары и переприсоединение подветви.
4. Для каждого решения сохранять структуру подключений, геометрию и историю получения, а не только score.
5. Отдельно проверить несколько вариантов магистрали. Варьирование числа/расположения центров — последующий эксперимент, а не уже подтверждённая доработка.

**Критерий готовности.** Версия `B2-C+J` может проверить новые конструктивные варианты и сохраняет старый допустимый результат как резервный. Отсутствие выигрыша на одной сцене честно отражается в таблице.

`B2-C+J` здесь — **предлагаемое имя эксперимента**, а не существующая в отчёте версия.

### 3.5. B3: превратить архив и перестановки в измеряемую перестройку сети

**Что реализовано по отчёту.** Общий архив B0/B1/B2, фиксированные destroy/repair-перестановки, выбор лучшего. Нет адаптивных весов операторов и удаления поддеревьев на уровне рёбер. [B]

**Почему результат нельзя переинтерпретировать.** Если в архиве уже лежит B2, возврат того же результата означает сохранение найденного решения. Это не независимое подтверждение оптимальности. По отчёту нельзя установить, сколько содержательных новых топологий было проверено.

**Что делать в два этапа:**

**Этап A — настоящие изменения топологии.** Выделять подветвь по рёбрам, временно удалять её подключение и восстанавливать через другие коридоры, junction-позиции или присоединения. Удалять также ненужные после перестройки элементы с нулевым обслуживаемым расходом. Не путать это с перестановкой списка ОКС.

**Этап B — адаптация выбора операторов.** Только после появления работающих операторов учитывать их результаты: число допустимых предложений, улучшение score, время и частоту новых лучших решений. Не закреплять вероятности вроде «merge всегда 60%» без измерений.

Обязательно сохранять:

```text
initial_solution_id
best_solution_origin
proposed_moves
unique_candidate_count
feasible_moves
rejected_by_reason
accepted_moves
improving_moves
new_best_count
best_score_over_time
```

**Критерий готовности.** Виден хотя бы один тест, где выбранные рёбра реально меняются, а не только порядок подключения. В отчёте указано, вернул B3 исходный B2 или нашёл новый проект. Выигрыш сравнивается при одинаковом бюджете поиска.

### 3.6. R1 и R2: не результаты, а ещё не реализованное обучение

**Что реализовано по отчёту.** API-контракты со статусом `NOT_TRAINED`. У R1 отсутствуют PPO-модель и training pipeline; у R2 — обученный контроллер ALNS. [B]

**Главный недостаток.** Пока нет обученного объекта, чьё качество можно измерить. Нельзя приписывать R1/R2 преимущество, проигрыш или стоимость inference.

**Что делать:** подготовить версионированную среду, генератор сцен, разделение train/validation/test, обучение, сохранение модели и отдельный путь inference. R1 и R2 сохранять как разные эксперименты: политика конкретных действий и контроллер уже работающих операторов. Подробная постановка — раздел 9.

**Критерий готовности.** Есть загружаемая модель, manifest её обучения, воспроизводимый inference и результаты на отложенных сценах. До этого обе версии остаются вне рейтинга качества.

### 3.7. X0: не выдавать перебор порядков за точный оптимум всей задачи

**Что реализовано по отчёту.** Полный перебор порядков вставки при числе ОКС не более 6. Набор рассматриваемых маршрутов конечен и ограничен текущим shortlist; полного перебора общего candidate graph нет. [B]

**Ограничение.** Все порядки одной процедуры построения — не все деревья, координаты развилок и схемы присоединения.

**Что делать:**

1. Подписывать текущий результат как «лучший среди всех перебранных порядков при данной процедуре вставки и shortlist».
2. При необходимости использовать уточняющее внутреннее имя `X0-PERM`; это предлагаемая маркировка, не переименование исходного отчёта.
3. Для крошечных сцен создать отдельный конечный набор рёбер/узлов, перебрать все допустимые выбранные подграфы и оценить их теми же актуальными правилами.
4. Называть такой результат точным **только в зафиксированном кандидатном пространстве**, если перебор закончен и назначение допустимых диаметров/других решений также исчерпывающе учтено.
5. При прерывании сохранять лучший найденный результат и статус незавершённого поиска, не «OPTIMAL».

**Критерий готовности.** Эталон сопровождается описанием пространства решений, границ перебора и фактом его завершения. Малый результат X0 из отчёта нельзя использовать как доказанный глобальный оптимум произвольной трассировки.

## 4. Правила нового ТЗ, которые нельзя потерять

Этот раздел — контроль актуальности, а не новая инженерная модель. Основной PDF и приложение расходятся; ранее выполненный разбор фиксирует ответ организаторов о применении актуального приложения. Нельзя смешивать новую структуру входа со старой реконструкцией. [U, §§1–4]

| Область | Что должно действовать | Источник |
|---|---|---|
| Цель подключения | Каждая `oks_connection_point` самостоятельна; расход берётся из её `flow_tph` | [T, §1] |
| Полигоны | ОКС — `restriction_type = oks`; связь с точкой определяется пространственно, отдельного `oks_id` нет | [T, §1.2] |
| Свой ОКС | Разрешён один финальный прямой подход от ближайшей к точке границы; исключение из собственного отступа не отменяет другие препятствия | [T, §2.2] |
| Топология | Единственный путь от подключаемой точки до соответствующего присоединения, без замкнутых маршрутов | [T, §2.1] |
| Разветвление | Только в камере; максимум четыре примыкания; проходящая старая линия занимает два | [T, §2.1] |
| Диаметры | Минимальные допустимые по расходу и длине, без искусственного сброса длины, без уменьшения к присоединению | [T, §2.3] |
| Длины | Проверяются по каждому непрерывному пути; параллельные ветви не суммируются; техническое разбиение не сбрасывает отсчёт | [T, §2.3] |
| Присоединение | Использовать подходящую существующую камеру не далее 10 м, если вместимость позволяет; иначе новая камера на старой трубе | [T, §2.4] |
| Старая сеть | Реконструкция и расчёт резерва не входят в обязательную модель | [T, §2.4] |
| Новая камера | Цена по максимальному ДУ всех примыкающих участков; присоединение к старой трубе уже включено | [T, §3.2] |
| Существующая камера | Каждый заканчивающийся в ней новый линейный участок — отдельная врезка за 5 млн ₽ | [T, §3.2] |
| Геометрия | Повороты до 90°; нет необоснованных мелких изломов и пересечений новых труб вне общего узла | [T, §2.1] |
| Спецпроход | Прямой участок, выделенные границы, все геометрические требования; при перекрытии применяется максимум Kспец | [T, §4] |
| Отказ | Нельзя намеренно не подключать доступную точку ради уменьшения score | [T, §2.5] |
| Экспорт | Четыре типа: `heat_network`, `heat_chamber`, `technical_node`, `variant_summary` | [T, §7] |

### Актуальная формула стоимости

```text
pipe_cost = сумма стоимости новых heat_network
chamber_cost = сумма стоимости новых heat_chamber
tie_in_cost = 5_000_000 * число новых участков в существующих камерах

construction_cost = pipe_cost + chamber_cost + tie_in_cost
calculated_cost = construction_cost + unconnected_penalty
L = сумма длин новых участков
S = 0.7 * (calculated_cost / 25_000_000) + 0.3 * (L / 100)
```

Разбивки стоимости не складываются повторно с `construction_cost`. Реконструкция не входит ни в C, ни в L. [T, §§3.2, 6]

**Пример правила, не результат бенчмарка:** новая ветвь ДУ100 присоединяется через новую камеру на старой трубе ДУ500. Камера стоит 5 млн ₽; отдельные 5 млн за врезку не добавляются. Для камеры нельзя взять цену 3 млн только по ДУ новой ветви. [T, §3.2]

Для базового 2D-режима `depth_start` и `depth_end` равны null, Kгл = 1. Глубина — отдельный необязательный режим; результаты режимов не смешиваются в одном ранжировании. [T, §5]

## 5. Главная доработка: развилка внутри трубы

### 5.1. Что нужно уметь построить

Была новая труба между U и V. Рядом есть ОКС B. В числе кандидатных решений должна появиться новая точка X:

```text
U ─────────── X ─────────── V
              │
              │
           ввод ОКС B
```

X — не обязан быть уже существующим узлом графа. После выбора X становится камерой-развилкой. Просто совпадение линий на картинке не создаёт соединения.

Это доработка B1/B2, непосредственно отвечающая на ограничение, указанное в отчёте. [B] Далее описано **наше предложение реализации**.

### 5.2. Генератор кандидатов X

Для каждого рассматриваемого участка новой сети:

1. Работать с реальной полилинией в EPSG:32637, а не с прямой между её крайними точками.
2. Добавить ортогональные проекции доступной точки подхода ОКС на сегменты этой полилинии.
3. Добавить несколько соседних позиций вдоль трубы и подходящие геометрические позиции из других допустимых коридоров.
4. Включить существующие концы как альтернативы: иногда новая камера не нужна.
5. Удалить геометрические дубли с документированным численным допуском.
6. Для каждой позиции попытаться построить законный отвод; близость по прямой сама по себе недостаточна.

Шаг дополнительных проб и предел числа кандидатов — настройки эксперимента, **не требования ТЗ и не гарантия полноты**. Записывать их в manifest. Нельзя обещать, что конечный shortlist содержит лучшую непрерывную координату.

Для первой версии можно консервативно не предлагать камеры внутри спецпроходов и собственного финального подхода ОКС. Это **ограничение нашей реализации**, а не выдуманный общий норматив; оно фиксируется в конфигурации и в перечне непроверенных возможностей.

### 5.3. Изменение должно быть транзакцией

Полное предложение — не только «поставить X», а комплект:

```text
что переносим или подключаем
какой участок разрезаем
координата X
маршрут нового отвода
какие старые элементы заменяются
какое присоединение к старой сети сохраняется
```

Все изменения делаются в отдельном кандидате. При неудаче исходный проект остаётся неизменным.

Если ОКС B уже подключён, сначала в копии проекта удаляется его прежний уникальный отвод; общие питающие участки других ОКС не удаляются. Это переподключение, а не второе питание того же потребителя.

### 5.4. Порядок расчёта одного кандидата

```text
Создать копию текущей сети
        ↓
Выполнить объявленное отключение переносимой ветви
        ↓
Разделить U—V в X с точной геометрией обеих частей
        ↓
Создать или корректно переиспользовать камеру X
        ↓
Добавить отвод и необходимые технические границы
        ↓
Проверить топологию и законное присоединение
        ↓
Пересчитать расходы по всей затронутой новой сети
        ↓
Назначить диаметры с учётом длины и направления
        ↓
Повторно проверить габариты, повороты и пересечения
        ↓
Рассчитать камеры, врезки и полную стоимость
        ↓
Сравнить с текущим проектом
```

**Важная тонкость:** после добавления потребителя вырасти может не только диаметр отвода, но и диаметры общих участков. Более широкий габарит способен сделать ранее допустимый коридор непригодным. Нужен повторный геометрический контроль, а при перепрокладке — новый расчёт длины и диаметра.

Если предусмотрен цикл `диаметр → геометрия → диаметр`, он должен иметь ограничение числа попыток и обнаружение повторяющихся состояний. Исчерпание попыток означает отказ конкретного кандидата, а не доказанную невозможность подключения ОКС вообще.

### 5.5. Псевдокод интерфейса

Это контракт проектирования, а не готовый Java-код:

```text
tryJunctionMove(current, move, context):
    candidate = copy(current)

    applyDeclaredDetachments(candidate, move)
    x = splitActualPolyline(candidate, move.edge, move.position)
    ensureBranchChamber(candidate, x)
    attachRoute(candidate, move.consumerOrSubtree, x, move.route)
    pruneUnusedElements(candidate)

    if not topologyValid(candidate):
        return Rejected("TOPOLOGY", affectedIds)

    result = engineeringEvaluator.recalculate(candidate, context)
    if not result.valid:
        return Rejected(result.reason, result.affectedIds)

    return EvaluatedCandidate(
        network = candidate,
        score = result.score,
        deltaScore = result.score - current.score,
        changes = structuralDiff(current, candidate)
    )
```

Старый расход, диаметр и цена разрезанного ребра не копируются как окончательные ответы в обе части: их нужно пересчитать. Суммарный расход пары «подача + обратка» не удваивается.

### 5.6. Чем доказать, что доработка полезна

Подготовить небольшую сцену, где заранее перечислены допустимые альтернативы: соединение через концы U/V и соединение через X. Полным расчётом установить, какое решение лучше. Затем проверить, что версия с junction-кандидатами действительно рассматривает X и не проигрывает своему сохранённому исходному варианту.

Добавить обратную сцену: камера и увеличение общего диаметра делают X невыгодным. Проверить, что алгоритм не объединяет ветви автоматически.

## 6. Целевая архитектура и цикл поиска

### 6.1. Разделить четыре роли

| Модуль | Ответственность | Что он не должен подменять |
|---|---|---|
| `CorridorGraphBuilder` / `RoutePlanner` | Геометрические возможности и варианты маршрутов | Экономический выбор всей сети |
| `MoveGenerator` / `JunctionCandidateGenerator` | Конкретные изменения связей, камер, групп и присоединений | Решение о допустимости на основе одной картинки |
| `EngineeringEvaluator` | Точный расчёт новой сети по ТЗ | Нейросетевую оценку вместо таблиц |
| `IndependentChecker` | Проверка экспортированного результата по исходным данным | Доверие внутренним кэшам и заявленному score |

Стратегия выбора действий — заменяемая часть: жадный поиск, фиксированные перестройки, ALNS, R1 или R2. Одинаковые инженерные правила должны действовать для всех.

### 6.2. Инварианты состояния

Предлагаем хранить выбранную новую сеть как лес присоединённых деревьев: несколько отдельных групп ОКС допустимы, один общий ствол для всех не обязателен. Для первой реализации у каждого такого дерева — одно законное присоединение; это явный инвариант нашей модели, обеспечивающий однозначное направление расчёта к корню.

Объединение двух уже присоединённых деревьев должно включать выбор сохраняемого присоединения и удаление заменяемой части. Нельзя просто дорисовать перемычку и предположить, что сеть осталась корректной.

Если используется `EDGE_EXCHANGE`, он корректен как операция дерева только при точных условиях: концы нового ребра в одной компоненте дерева; удаляется другое ребро образовавшегося цикла. Даже тогда сохраняется лишь графовая структура, **не** гарантируются вместимость камер, геометрия, диаметры и правильная экономическая модель.

Точки ОКС не становятся бесплатными разветвителями или транзитными узлами. Поворот и техническое разбиение трубы не создают дополнительного сброса предельной длины.

### 6.3. Полный цикл улучшения

```text
input, rules = loadAndValidate()
candidates = buildCandidateSpace(input, rules)

baseline = runFrozenB2C(input, candidates, rules)
require independentCheck(export(baseline), input, rules).valid

current = baseline
best = baseline
archive.add(baseline, origin="B2-C")

while budgetRemaining():
    move = selector.choose(current, best, candidates, remainingBudget)
    proposal = moveGenerator.buildCompleteProposal(current, move)
    evaluated = engineeringEvaluator.tryApply(current, proposal)

    logAttempt(move, evaluated)
    if not evaluated.valid:
        continue

    if acceptanceRule(current, evaluated):
        current = evaluated.network

    if evaluated.score < best.score:
        checked = independentCheck(export(evaluated.network), input, rules)
        if checked.valid:
            best = evaluated.network
            archive.add(best, origin=move.id)
        else:
            logEvaluatorCheckerDisagreement(checked)

return checkedExport(selectDistinctVariants(archive))
```

Бюджет, выбранные seed, правила приёма ухудшений и максимальное число кандидатов задаются явно. Для первой версии достаточно жадного принятия; для исследования последовательностей с временным ухудшением нужен отдельный режим поиска. Нельзя незаметно менять эти условия между сравниваемыми методами.

При остановке возвращается лучший **проверенный полный** проект, а не промежуточный результат destroy. Если вариант baseline отсутствует или не проходит checker, фиксируется ошибка/неполный результат, а не выдумывается гарантия подключения.

## 7. Что должен доказать независимый checker

### 7.1. Граница текущих свидетельств

Отчёт сообщает ноль нарушений, но не содержит матрицы проверяемых правил, исходного кода checker-а и отчётов по всем тестовым командам. Это **не утверждение, что проверок нет**; это утверждение, что их покрытие нельзя установить по предоставленному файлу. [B, «Как воспроизвести»]

Нужна независимая проверка именно экспортированного GeoJSON: ссылка на узел, геометрическое совпадение и корректный расход должны согласовываться. Допустимо совместно использовать проверенную геометрическую библиотеку и таблицы ТЗ, но нельзя считать проверкой повторный вызов того же ошибочного расчёта из кэша solver-а.

### 7.2. Минимальный набор проверок

| ID | Сцена или намеренное изменение | Ожидаемый результат |

| C01 | Удалить или подменить обязательную ссылку конца трубы | Ошибка контракта/связей, не «подключено» |

| C03 | Перепутать ID двух вводов при сохранении линий | Несогласованность ID и координат |
| C04 | Две точки в одном `oks`-полигоне | Две самостоятельные цели и два расхода |
| C05 | Законный прямой подход внутрь собственного полигона | Принимается с предусмотренным исключением из отступа |
| C06 | Использовать свой полигон как транзитный проход либо отменить чужое препятствие | Отклонение |
| C07 | Две новые линии пересекаются без общего узла | Отклонение, не автоматическое соединение |
| C08 | Сделать разветвление в `technical_node` | Отклонение; нужен heat_chamber |

| C12 | Уменьшить ДУ ниже реально необходимого по расходу | Отклонение; перечислить зависимые ОКС |
| C13 | Неизменный расход 3 т/ч, непрерывная длина 300 м | ДУ80 при остальных допустимых условиях; ДУ50/65 не проходят длину |

| C17 | Уменьшить ДУ по направлению к присоединению | Отклонение |
| C18 | Увеличение общего ДУ нарушило отступ/габарит | Отклонение, даже если старый тонкий маршрут проходил |
| C19 | Поворот больше 90° или запрещённые необоснованные изломы | Отклонение по согласованным правилам геометрического контроля |
| C20 | Спецпроход изогнут, имеет неверный угол или неправильные границы | Отклонение соответствующего правила |

| C26 | Подменить `score`, `length` или агрегированную стоимость | Независимый пересчёт обнаруживает расхождение |
| C27 | Удалить общий питающий участок | Все зависящие ОКС теряют подключение |
| C28 | Экспорт содержит входные ссылки на ОКС/существующие камеры | Законные ссылки принимаются, не требуется копировать входные объекты |
| C29 | Две строки отчёта заявлены как разные варианты, но геометрия слегка сдвинута | Не считать автоматически содержательно разными |
| C30 | Намеренно исключить доступный ОКС ради меньшего S | Не засчитывать как успешное полное решение |

Таблица — **предлагаемое покрытие**, а не заявление о 30 уже выполненных тестах. Для сложных правил нужны несколько положительных и отрицательных фикстур. Например, не всякое уменьшение диаметра является нарушением: C12 создаётся на сцене, где меньший ДУ действительно недостаточен.

Фраза ТЗ об «необоснованных» изломах не даёт универсального численного порога. Численные допуски, диагностические критерии и спорные формы согласуются отдельно; их нельзя выдавать за дословный норматив.

### 7.3. Подключённость, допустимость и найденный оптимум — разные статусы

Предлагается выдавать три независимых результата:

```text
schema_and_engineering_valid
all_required_points_connected
optimization_reference_status
```

Неполный выход со штрафом может соответствовать предусмотренному случаю ненайденного маршрута, но не становится успешным тестом полного подключения. На сцене с известным допустимым полным решением отказ не должен обходить этот критерий.

Независимый checker не доказывает существование или отсутствие всех возможных путей в непрерывном пространстве. Поэтому дополнительно нужны журнал попыток, расширение поиска при неудаче и контрольные альтернативы. «Не найдено в текущем shortlist» не равно «технически невозможно».

### 7.4. Что реально покрывает текущая карта

По сохранённому аудиту исправленного набора: 144 объекта, 17 точек, 29 старых участков, 9 камер, 88 ограничений и 1 источник. Среди `restriction` — 85 `oks`, 2 `water`, 1 `railway`. [A]

Следовательно, одна полная сцена сама по себе не проверяет все обязательные виды специальных пересечений. Нужны дополнительные сцены с road, tram_tracks, gas_pipeline, power_cable и другими обязательными типами. Старая heat_network отдельно участвует в проверке пересечений без присоединения.

Точки 12 и 15 из аудита лежат в одном полигоне 92 и остаются отдельными потребителями. Это полезный конкретный регрессионный тест. [A]

## 8. Как сравнивать улучшения без самообмана

### 8.1. Отделить пространство решений от стратегии поиска

Предлагаемые эксперименты; новых результатов для них ещё нет:

| Эксперимент | Что меняется | Что сохраняется | Какой вопрос решаем |
|---|---|---|---|
| E0 | Ничего: зафиксированный B2-C | Весь текущий стек | Воспроизводится ли исходный результат? |
| E1 | Добавлены junction-позиции | Стратегия B2-C и расчётные правила | Полезны ли новые точки разветвления? |
| E2 | Добавлен общий corridor graph | Зафиксированная политика и согласованный набор топологических действий | Полезна ли новая геометрическая модель? |
| E3 | Добавлены групповые соединения | Граф, evaluator, бюджет | Что даёт совместный выбор для пары/группы? |
| E4 | Добавлены edge-level перестройки B3 | Тот же граф, действия и стартовый проект | Что даёт поиск с перепроектированием? |
| E5 | Выбор доступных действий обучает R1 | Тот же генератор действий, checker и бюджет | Что даёт именно обученная политика? |
| E6 | Выбор операторов обучает R2 | Одинаковые destroy/repair и стартовые проекты | Полезен ли обученный контроллер относительно необучаемого ALNS? |

Не обязателен только один последовательный запуск E0→E6. Нужны парные сравнения, где явно меняется одна группа факторов. Если одновременно поменяли граф, кандидаты и модель, вывод должен быть про пакет изменений, а не про «победу RL».

### 8.2. Время, бюджет и повторяемость

Для каждого эксперимента фиксировать вход, версию кода, правила, конфигурацию, оборудование, ограничения ресурсов и seed.

Сравнивать в двух режимах:

- одинаковый бюджет времени, включая построение кандидатов, inference и проверку;
- одинаковый бюджет полных оценок кандидатов, дополнительно публикуя фактическое время.

Эти режимы не эквивалентны: геометрический фильтр, генератор действий и модель тоже стоят времени. Не учитывать только время «главного while».

Для измерения скорости выполнить повторные запуски. Начальное практическое предложение — 10 повторов на фиксированной сцене, без утверждения, что этого достаточно для любой статистической уверенности. Для стохастических методов использовать заранее заданный одинаковый набор seed; для детерминированных отделять прогрев и колебания среды.

Публиковать медиану, диапазон/квантили, лучший и средний score, частоту полных допустимых решений и пиковую память. Время обучения приводить отдельно от inference. График `лучший S → затраченное время` полезнее одного лучшего числа после неизвестного бюджета.

### 8.3. Метрики качества

| Группа | Метрики |
|---|---|
| Корректность | Полнота целей, ошибки связей/геометрии/диаметров/сметы, расхождения checker и evaluator |
| Обслуживание | Подключённые точки и суммарный обслуживаемый расход |
| Экономика | Стоимость труб, камер, врезок; construction_cost; calculated_cost; официальный S |
| Структура | Число новых камер, врезок, присоединённых деревьев, распределение ОКС по ним |
| Геометрия | Длина, число фактических поворотов, длина спецпроходов, диагностические изломы |
| Поиск | Уникальные кандидаты, допустимые предложения, новые лучшие решения, причины отказа |
| Ресурсы | Время по стадиям, память, число полных оценок |

Снижение числа камер или поворотов не заменяет официальный S и не отменяет обязательных ограничений. Красивое решение с неправильным вводом не участвует в рейтинге допустимых полных решений.

### 8.4. Одинаковые числа не означают одинаковые проекты

Сохранять три разных признака:

1. Хеш байтов результата — для воспроизводимости файла.
2. Нормализованную структуру связей ОКС, камер и присоединений — для сравнения топологии независимо от сгенерированных ID.
3. Геометрическое сравнение с объявленным допуском — для обнаружения почти одинаковых трасс.

Упорядочивание координат, техническое разбиение и произвольные ID не должны сами по себе создавать «новый вариант». Но нормализация не должна стирать реальную разницу в положении камеры, коридоре, диаметре или границах спецпрохода.

Хеш/нормализация — инструмент диагностики, а не доказательство глобальной эквивалентности всех геометрических сетей.

### 8.5. Когда доработку принимаем

Обязательный входной барьер — корректность. Затем смотрим, даёт ли доработка лучшее качество или тот же результат за меньший бюджет на наборе сцен, а не только на одной карте.

Разработчик до эксперимента объявляет критерий принятия: например, отсутствие регрессии полноты/корректности и улучшение медианного S на отложенном наборе при равном времени. Конкретный целевой процент улучшения нужно согласовать, а не придумывать после получения красивого результата.

Если улучшения нет, сохраняем результат эксперимента и не меняем контрольную версию. Если расширение пространства помогает обычному поиску так же, как RL, это полезный инженерный результат, но не доказательство пользы обучения.

## 9. Обучение с подкреплением: R1 и R2

Раздел описывает **предложение следующего этапа**. В отчёте обе версии имеют статус `NOT_TRAINED`. Сам факт наличия таблицы затрат не доказывает, что RL лучше обычного поиска. [B]

### 9.1. Что поручить агенту

Нейросеть не предсказывает табличную цену и не решает, можно ли игнорировать правило. Она выбирает инженерное действие или оператор, а среда точно строит и проверяет результат.

| Версия | Предлагаемая роль | С чем сравнивать |
|---|---|---|
| R1 | PPO-политика выбирает конкретное допустимое изменение: ОКС/подветвь, целевое ребро/камеру, junction-позицию и вариант коридора | Необучаемый поиск на тех же конкретных действиях |
| R2 | Контроллер выбирает destroy/repair-оператор и, при предусмотренном контракте, размер перепроектируемой части | Фиксированный и адаптивный необучаемые контроллеры над теми же операторами |

Конкретная детализация действий R1 — проектное предложение; исходный отчёт сообщает отсутствие PPO-модели, но не описывает реализованную архитектуру этой модели.

Начальная стратегия обучения: улучшать уже полный допустимый проект B1/B2. Это снижает риск смешать «не умеем построить сеть» и «не умеем выбирать улучшения». Конструктивное обучение с пустой сети можно исследовать отдельно; оно не является условием первого честного сравнения.

### 9.2. Что включить в состояние

```text
Все точки подключения и их расходы
Текущая выбранная новая сеть и её присоединения
Текущие диаметры, камеры, вместимость, длины и стоимость
Кандидатные коридоры и возможные изменения
Геометрические ограничения и допустимые подходы к ОКС
Лучшее найденное полное решение и его S
Оставшийся бюджет эпизода
```

Из старой модели не переносить несуществующие обязательные данные о резерве и реконструкции. Старый diameter остаётся там, где нужен для габаритов и стоимости новой камеры на старой трубе. [T, §§2.4, 3.1–3.2]

### 9.3. Границы действия и допустимость

Первое обучаемое действие должно завершаться полноценным предложением сети, а не оставлять бесплатную неподключённую ветвь. Сложный destroy/repair считается одной внешней транзакцией для сравнения полных проектов.

Явно невозможные действия исключаются маской: например, несуществующий узел или заранее известное превышение числа примыканий. Полный evaluator всё равно нужен: после изменения расхода могли вырасти диаметры и нарушиться геометрия.

Недопустимый кандидат не попадает в архив допустимых решений. Его расчёт тратит бюджет и регистрируется. Нельзя позволять агенту получать выгоду от ошибок экспорта, пропущенного ОКС или маленького штрафа за нарушенную вместимость.

### 9.4. Награда должна соответствовать тому, что возвращает сервер

Ранее обсуждалась награда `S(current_before) − S(current_after)`. Она согласована с минимизацией **конечного текущего** проекта при суммировании без дисконтирования.

Но если сервер возвращает **лучший проект из архива**, предлагается явно использовать соответствующую цель:

```text
N_t = текущий полный допустимый проект
B_t = лучший полный проверенный проект, найденный к шагу t
r_t = S(B_t) - S(B_(t+1))
```

Для конечного эпизода без дисконтирования:

```text
сумма r_t = S(B_0) - S(B_T)
```

Это алгебраическое соответствие цели: максимальная накопленная награда означает наибольшее улучшение возвращаемого лучшего проекта. Никаких дополнительных «бонусов за камеру» или «бонусов за merge» не требуется.

Текущее состояние может временно ухудшаться, пока лучший архив сохраняется. Это даёт возможность исследовать последовательность перестроек, а не принуждает к одному жадному шагу. Нужна информация о текущем проекте, лучшем результате и бюджете; один scalar score не описывает состояние.

Если команда выберет возврат последнего проекта, другую скидку будущих наград или штраф за время, цель изменится. Это отдельный эксперимент, который надо описать. Нельзя незаметно менять reward между версиями и сравнивать их как один метод.

**По новому ТЗ:** экономический отказ от доступного ОКС не является разрешённым итоговым действием. Временное отсоединение внутри транзакции допустимо как механизм перестройки, но не как способ сдать дешёвое неполное решение. [T, §2.5]

### 9.5. На чём обучать

Предлагается генератор задач, а не запоминание одной карты:

| Семейство | Что варьируем | Какую развилку решений проверяем |
|---|---|---|
| Малые проверяемые сцены | 2–6 ОКС, конечные варианты коридоров и камер | Совместное и отдельное подключение; возможность сопоставления с малым перебором |
| Внутренние junction-позиции | Положение ОКС относительно середины/концов магистрали | Создать камеру внутри трубы или идти к существующему узлу |
| Пороговые расходы | Расходы рядом с границами допустимых ДУ | Экономию общей трубы против её увеличения |
| Ограниченная вместимость | Камеры с разным числом старых примыканий | Выбор законного места присоединения |
| Разные препятствия | ОКС, вода, railway, дороги, кабели и другие обязательные типы | Обход против специального пересечения |
| Групповые перестройки | Кластеры и разнесённые группы потребителей | Общий ствол против нескольких деревьев |

Тарифы и обязательные правила в основном обучающем эксперименте фиксируются по актуальному приложению. Варьируются сцены, геометрия и расходы. Увеличение масштаба задач — отдельная проверка, а не обещание переносимости.

Для каждого учебного примера нужна проверка входа. Для сцен, где ожидается полное подключение, полезно хранить хотя бы один заведомо допустимый проект, подтверждённый checker-ом. Проект, построенный эвристикой, не называется оптимальной разметкой без доказательства.

### 9.6. Разделение данных

Разделять train/validation/test по исходным сценам/картам. ОКС одной сцены не раскладываются между выборками как независимые задачи. Все модификации одной исходной карты сохраняют общий `base_scene_id`; это помогает обнаружить утечки.

Текущая карта уже использовалась для анализа и выбора доработок. Её честный статус — **регрессионная/разработческая сцена**, а не нетронутый финальный тест. Для итогового заявления о переносе нужны новые отложенные сцены.

Число сцен и эпизодов обучения выбирается по кривым качества и ресурсам. В исходном отчёте этих данных нет; фиксированное обещание «столько-то эпизодов достаточно» здесь не даётся.

### 9.7. Что считается готовым обученным методом

Нужны модель и manifest с версиями правил, генератора данных, генератора действий, split, seed и конфигурации обучения. Inference должен воспроизводимо загружать модель в целевом окружении сервиса; выбранный путь исполнения необходимо отдельно проверить на совместимость со стеком проекта.

Рейтинг R1/R2 допустим только после независимой проверки выходов на тех же тестах, что у B2/B3. Общий preprocessing, кэширование, бюджет поиска и доступные действия должны быть сопоставимы. Стоимость обучения и ресурсы inference показываются отдельно.

**Зависимости:** DEV-01–03 нужны до доверия новым результатам. DEV-04 открывает главный отсутствующий класс соединений. DEV-06 можно вести параллельно, но измерять отдельно. R2 зависит от реально работающих операторов DEV-08; обучать выбор отсутствующих операторов бессмысленно.

### Конкретная первая задача разработчику

> Сохрани текущий B2-C как контроль. Реализуй `JUNCTION_IN_EDGE` для новой полилинии с полной транзакцией разрезания, установки камеры, отвода, пересчёта и отката. Добавь две малые сцены с противоположным экономическим выбором и тест роста общего ДУ. Сравни версию с исходным B2-C одним checker-ом; сохрани каждый проверенный вариант и причины отказа.

## 11. Что сохранять в результатах каждого запуска

### 11.1. Минимальный комплект артефактов

Предлагаемая структура, ещё не существующий контракт репозитория:

```text
results/<run_id>/
    manifest.json
    input.geojson
    variants.geojson
    checker_report.json
    per_oks_report.json
    cost_breakdown.json
    moves.jsonl
    metrics.json
    summary.md
```

Для большого входа допустима ссылка на неизменяемое хранилище с проверяемым хешем вместо лишней копии. Нельзя подменять исходную сцену молча исправленным файлом.

В manifest нужны версии solver/evaluator/checker, версия правил и пространственных допусков, графа и действий, hash входа, seed, параметры бюджета и оборудование. Для R1/R2 добавляется model artifact и split.

### 11.2. Машинный отчёт

Поля нового отчёта должны позволять восстановить не только «кто победил», но и почему:

```text
algorithm_id, run_id, scene_id, input_sha256
code_version, rules_version, checker_version
candidate_generator_version, candidate_config, seed
training_model_id или null
status, connected_count, total_count, served_flow_tph
pipe_cost, chamber_cost, tie_in_count, tie_in_cost
construction_cost, unconnected_penalty, calculated_cost
new_network_length, score_unrounded
wall_time_total, time_by_stage, peak_memory
proposed_moves, feasible_moves, unique_candidates
accepted_moves, improving_moves, rejection_counts
best_origin, best_iteration, best_trace
output_sha256, structure_signature
```

`score_unrounded` — число из расчёта до форматирования таблицы. Это не обещание бесконечной численной точности геометрии. Допуски сравнения суммы, длины и геометрии должны быть заданы и не маскировать реальные нарушения.

### 11.3. Команды из исходного отчёта

Следующие команды **цитируются из [B]**, а не заявляются как проверенные здесь или как вновь реализованные:

```bash
docker compose up -d --build
python scripts/run_algorithm_benchmark.py
python scripts/run_algorithm_benchmark.py \
  --input data/benchmark_fixtures/new_tz_smoke/input.geojson \

  --algorithm X0
python scripts/benchmark_smoke_tests.py
python scripts/run_numeric_benchmarks.py
python scripts/run_benchmark_suite.py
```

Автор отчёта указывает машинную сводку `results/algorithm-benchmark/summary.json` и читаемую `summary.md`. Для следующего разбора нужны сами результаты этих команд, а не только перечень способов запуска.

## 12. Открытые вопросы и запрещённые выводы

### Что уточнить у разработчика

| Вопрос | Почему без него вывод ограничен |
|---|---|
| Каковы формулы U/Q/C и как выбирается итоговый B2? | Буквы и название «взвешенный медоид» не определяют реализацию |
| Какие правила проверяет независимый checker? | Ноль ошибок не показывает непокрытые классы ошибок |
| Какие рёбра реально менял B3? | Совпадение с архивным B2 не раскрывает работу поиска |
| Совпадают ли выходные геометрии B2-U/Q/C/B3? | Округлённые показатели не определяют структуру |
| Каков raw отчёт по времени, памяти, прогреву и повторам? | Разницу долей секунды нельзя надёжно интерпретировать без разброса |
| Совпадает ли хеш входа бенчмарка с аудитом актуального датасета? | Название «обновлённый набор» не заменяет идентификатор файла |
| Где ограничиваются число коридоров и окно поиска? | Это границы пространства решений и возможные причины ненайденного пути |
| Как назначаются ДУ при взаимодействии длин, общих участков и монотонности? | Простого правила «минимальный по расходу» по новому ТЗ недостаточно |
| Как устроен путь исполнения будущей модели в целевом сервисе? | Обучение и API-контракт сами по себе не доказывают готовность inference |

### Чего не писать в следующем отчёте

| Неподтверждённая формулировка | Корректная замена |
|---|---|
| «A* не подходит для труб вообще» | Независимые маршруты не решают задачу совместной сети; геометрический поиск оценивается отдельно |
| «Corridor graph не помогает» | Текущий lite дал небольшой выигрыш S относительно B0-GRID на одной сцене |
| «B3 подтвердил оптимум B2» | B3 сохранил лучший B2-вариант и не улучшил его текущими операциями |
| «Все реализации готовы» | В отчёте перечислены ограничения lite; у R1/R2 только контракты без моделей |
| «X0 нашёл точный оптимум всей сети» | X0 исчерпал порядки вставки в заданной процедуре и shortlist |
| «RL хуже/лучше» | Обученные R1/R2 ещё не сравнивались |
| «Ноль нарушений доказывает корректность всего продукта» | Проверки текущего checker-а пройдены; их покрытие подтверждается отдельными тестами |
| «Можно оставить дорогой ОКС неподключённым и заплатить штраф» | Новое приложение запрещает намеренный экономический отказ от доступного подключения |
| «Ближайшая старая труба плоха из-за реконструкции» | Реконструкции в новой обязательной модели нет; сравниваем действующие статьи затрат |

## 13. Словарь

| Термин | Простое значение в этом проекте |
|---|---|
| Baseline | Простая или замороженная версия, с которой сравниваем изменения |
| Топология | Кто с кем соединён: ветви, камеры и присоединения |
| Геометрия | Где именно проходят выбранные линии |
| Candidate graph | Набор возможных узлов и участков, ещё не выбранных к строительству |
| Junction | Точка разветвления; после выбора в проекте — тепловая камера |
| Junction внутри ребра | Новая камера посередине ранее цельной трубы |
| Медоид | Представитель группы из рассматриваемого набора; в отчёте используется взвешенная версия, формула весов не приведена |
| Regret-2 | Подход к порядку вставки с учётом различия альтернатив; точные формулы текущего B1 нужно смотреть в реализации |
| Evaluator | Расчёт допустимости и стоимости предлагаемого проекта |
| Checker | Отдельная проверка конечного экспортированного проекта |
| Destroy / repair | Временно разобрать часть выбранной сети и собрать иначе |
| ALNS | Поиск с несколькими destroy/repair-операторами и адаптацией их выбора |
| Policy / политика | Правило или обученная модель выбора следующего действия |
| Inference | Применение уже обученной модели без обновления её весов |
| Ablation / изолированный эксперимент | Сравнение, где меняется одна часть системы |
| Мутационный тест | Проверка, обнаружит ли checker специально внесённую ошибку |
| Лучший найденный | Лучший среди действительно проверенных вариантов, без обещания глобального оптимума |

### Как читать статусы

- **По отчёту / по приложению** — содержание соответствующего источника, не новый эксперимент.
- **Наша интерпретация** — вывод из опубликованных данных с указанной границей.
- **Предлагается / что делать / критерий готовности** — задача разработчику или проектное решение; не факт реализации.
- **Не установлено** — информации в предоставленных материалах недостаточно.

При подготовке этого файла проверены перенос таблицы, арифметика опубликованного score и согласованность плана с разобранными правилами нового приложения.
