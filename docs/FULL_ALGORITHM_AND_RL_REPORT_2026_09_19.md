# Полный отчет по алгоритмам и R1

> Этот отчет зафиксировал промежуточный macro-R1 до реализации concrete-action R1 и R2. Актуальный полный
> отчет: `docs/RL_ALGORITHMS_IMPLEMENTATION_REPORT_2026_09_19.md`.

Дата проверки: 2026-09-19.

## 1. Короткий вывод

На основном датасете лучший проверенный результат дал `B2-C-J`:

- подключено 17 из 17 ОКС;
- длина новой сети 1504.95 м;
- стоимость 228 974 801.11 руб.;
- официальный score `S = 10.93`;
- независимый checker: `VALID`, нарушений 0;
- время полного запуска 11.190 с.

`R1` реализован и исполняется как отдельный Java-класс с обученной PPO-моделью. Он нашел тот же лучший проект
`S = 10.93`, но за 29.599 с. На этой сцене RL не улучшил качество относительно `B2-C-J` и оказался в 2.65 раза
медленнее. Поэтому рекомендуемый рабочий алгоритм сейчас — `B2-C-J`, а `R1` остается экспериментальным.

На малой сцене, где применим `X0`, лучший результат `S = 0.70` одновременно получили `B3`, `R1` и `X0`.
Это показывает, что одного победителя для любой геометрии пока нет.

## 2. Что именно реализовано в R1

Законченный исполняемый контур `R1 v1` состоит из:

- `R1Solver.java` — эпизод, состояние, маска действий, вызов policy, транзакционная оценка предложений,
  best archive, rollback при ошибке, награда и диагностика;
- `R1PilotPolicy.java` — проверка manifest/hash, загрузка весов и Java inference;
- `scripts/r1/core.py` — идентичная среда обучения, стабильные candidate snapshots и schema guards;
- `scripts/r1/ppo.py` — masked actor-critic и clipped PPO update;
- `scripts/r1/train.py` — обучение, train/validation split и сохранение модели;
- `models/r1_pilot_v1/model.json` — фактически обученный артефакт;
- `scripts/r1/check_java_parity.py` — сравнение Python и Java по state, logits, цепочке действий и hash модели.

Каталог действий `R1 v1`: `B2-U`, `B2-Q`, `B2-C`, `B2-C-J`, `B3`, `STOP`. Возвращается не последнее,
а лучшее полное предложение из архива. В финальном эпизоде выполнено 6 policy calls, проверено 5 предложений,
найдено 2 улучшения, ошибок применения 0. Цепочка:

```text
B2-C -> B3 -> B2-C-J -> B2-U -> B2-Q -> STOP
```

Hash весов:

```text
cd55b131e68ceede9cceb93235ab3b3a168313d1a0425214068f122d58d6251e
```

Python и Java дали одинаковые state, logits и цепочку действий: `MATCH`.

### Честная граница R1

`R1 v1` завершен для объявленного конечного пространства макродействий. Но это еще не расширенный `R1 v2`,
описанный в исследовательском плане. Сейчас policy выбирает готовый полный проект, а не конкретные
`CONNECT/ATTACH/MERGE/REATTACH` с ID ОКС, ребра, позиции junction и коридора в текущем графе.

Из-за этого агент в финальном прогоне оценил все пять предложений. Его результат пока эквивалентен дорогому
обученному селектору архива, а не самостоятельному локальному оптимизатору сети. Для заявления о production RL
нужны локальные graph-edit действия, общий с B3 бюджет evaluator calls, сотни независимых parent-сцен и отдельный
test split. В текущем коде эти возможности не спрятаны за ложным статусом: `R1` помечен
`IMPLEMENTED_EXPERIMENTAL`, `R2` — `NOT_TRAINED`.

## 5. Конкретные недостатки по алгоритмам

| Алгоритм | Что работает | Конкретный недостаток | Следующий необходимый этап |
|---|---|---|---|
| PORTFOLIO | Быстрый валидный default, 4 порядка | Не рассматривает junction внутри ребра; на основной сцене хуже B2-C-J на 0.34 S | Добавить B2-C-J в контролируемый portfolio или сменить default после регрессий |
| B0-GRID | Независимые grid-маршруты | На основной сцене нет выходной камеры в ветвлении у узла 106; `INVALID`; очень длинная сеть | Исправить контракт камеры/ветвления и оставить только как geometry control |
| B0-CORRIDOR | Независимые corridor-маршруты | Нет камеры у узла 106 и степень узла 5 при максимуме 4; `INVALID` | Разделять присоединения и учитывать вместимость до построения |
| B1 | Regret-2 и присоединение к созданным узлам | Вставляет только в существующие узлы, не в середину ребра; 2357.41 м | Подключить общий генератор junction и групповые перестройки |
| B2-U | Невзвешенный medoid и три порядка | На этой сцене совпал с Q/C; полноценная backbone topology не оптимизируется | Несколько стволов и реальный поиск точек общей магистрали |
| B2-Q | Medoid с весом расхода | Вес не изменил выбранную сеть; нет самостоятельного преимущества | Пороговые flow-сцены и несколько backbone-кандидатов |
| B2-C | Medoid с весом стоимости | Замороженный воспроизводимый control, но без junction | Использовать как контроль для каждого расширения |
| B2-C-J | Транзакционный split ребра, камера, пересчет flow/ДУ/стоимости | Только 5 ближайших host edges и жадная последовательность; нет переноса подветви и совместного выбора нескольких junction | Расширить group/reattach moves и сравнить при равном evaluator budget |
| B3 | 29 детерминированных destroy/repair порядков | Это reorder-lite, а не edge-level ALNS; нет удаления поддерева и адаптивных весов | Реализовать реальные destroy/repair операции, затем adaptive controller |
| R1 | Обученная PPO policy, mask, archive, rollback, Java inference | Выбирает целые solver-предложения и в финале оценивает их все; нет доказанного выигрыша RL | Локальные graph-edit actions, общий candidate generator с B3, большой train/test |
| R1-PILOT | Воспроизводимость старого API | Полный дубль `R1`, не отдельный алгоритм | После миграции клиентов удалить alias из рейтинга |
| R2 | Контракт зарегистрирован | Нет edge-level ALNS-операторов и обученной модели | Сначала закончить B3 edge-level, затем обучать controller |
| X0 | Полный перебор порядков для <= 6 ОКС | Перебирает не все геометрические сети, а только порядки текущего shortlist | Малый конечный candidate graph и доказуемый exhaustive search |

## 6. Надежность проверки

Финальный код прошел:

- Docker/Maven build;
- 13 unit-тестов R1/PPO;
- Python/Java parity: `MATCH`;
- junction regression: выгодный случай, невыгодный случай, обязательная камера, достаточный ДУ;
- frozen B2-C hash control: `PASS`;
- checker mutation smoke tests: все `PASS`;
- 64 числовые проверки по 7 шаблонам: `MATCH`;
- полный benchmark-suite: contract 1/1, decision 1/1, limits 1/1;
- независимую проверку каждого результата итогового бенча.

Checker проверяет структуру GeoJSON, связность ОКС с существующей сетью, расходы по путям, ДУ, стоимость,
повороты без hairpin/разворота на 180 градусов, запретные пересечения, специальные углы, камеры в ветвлениях,
максимальную степень камеры и итоговый summary.

Оставшаяся граница checker-а: это текущая 2D-модель ТЗ. Она не доказывает строительную реализуемость по глубине,
вертикальному профилю и данным, которых нет во входном GeoJSON.

## 7. Решение на текущем этапе

1. Для практического результата использовать `B2-C-J`: он дает лучший score при меньшем времени, чем R1.
2. `R1` сохранить как полностью воспроизводимый экспериментальный контур и контроль обучения, но не выдавать
   равенство с `B2-C-J` за пользу RL.
3. Следующая содержательная разработка — не еще одно переобучение текущей policy, а общий набор локальных
   `MERGE/REATTACH/JUNCTION` действий для B3 и R1. Только после этого сравнивать обучаемый и необучаемый выбор
   при одинаковом времени и числе полных оценок.
4. `R2` не ранжировать до появления настоящего edge-level B3 и model artifact.
