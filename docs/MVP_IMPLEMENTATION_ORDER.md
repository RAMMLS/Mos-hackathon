# MVP_IMPLEMENTATION_ORDER

**Версия 1.0 · 18 сентября 2026 года**  
**Цель:** получить `input.geojson → result.geojson`: независимые подключения, полный расчёт и один проверенный вариант. **Без LNS, ALNS и ML.** Подробные правила и псевдокод: [algorithm_design.md, версия 0.3](algorithm_design.md).

## 1. С каким набором начинаем

По результатам анализа, переданным командой **[НД]**:

| Объекты | Количество |
| --- | ---: |
| Точки подключения | 17 |
| Участки существующей сети | 29 |
| Камеры | 9 |
| Ограничения | 88 |
| Источник | 1 |
| **Всего** | **144** |

Это контрольные количества текущего набора, не константы алгоритма. Возможные 2–3 ГБ из рабочего гайда — отдельный масштаб, не установленный размер этого файла.

**Проверка перед расчётом:** сводка не выделяет `oks_future`, где приложение задаёт `flow_tph`. Проверить, откуда получается расход каждой точки и связь через `oks_id`. При иной схеме нужен явный адаптер; отсутствие расхода — ошибка входа, а не ноль. Сводка сама по себе не означает отсутствия этих данных. **[ТА, §2.2; НД]**

## 2. Решения, которые уже не выбираем заново

**Граф:** локальная регулярная восьмисвязная сетка + обязательные точки с точными координатами + проверяемые переходы через разрешённые препятствия. Поиск — **A\***. Не строим дорожный граф, visibility graph или 3D-сетку.

Стартовые настройки **[Решение]**: шаг 2 м; окно вокруг концов с запасом 100 м; при неуспехе расширять окно, локально пробовать шаг 1/0,5 м в пределах бюджета. **`k = 1` на кандидата врезки**, один порядок обработки, один выходной вариант. Параметры — не нормы ТЗ.

Потоковое чтение; для текущего набора — геометрии и пространственный индекс в памяти под лимитом. Без обязательной дисковой БД. Стек: Java 11, Spring Boot/Spring Data, Docker Compose, офлайн. **[РГ]**

## 3. Порядок реализации

### Шаг 1. Загрузка и исходные правила

Загрузить каталог диаметров/цен; проверить поля, геометрии, уникальность ID и ссылки. Сопоставить статистику с [НД], записать хэш файла. Перевести координаты из EPSG:4326 в EPSG:32637. Восстановить направление старой сети по `upstream_object_id`, проверить достижимость источника и отсутствие циклов. Создать индекс.

**Готово:** известны точка и расход каждого ОКС; ошибки входа не исправляются молча. Подробности: §4 и приложение A полной спецификации.

### Шаг 2. Кандидаты врезки

Сначала рассмотреть до 8 камер и до 12 труб в радиусе 250 м; для труб — ближайшие проекции и подходящие концы. При неуспехе расширять поиск, включая остальные камеры/трубы. **[Решение]**

При расстоянии **≤10 м** использовать существующую камеру, если после подключения к ней примыкает не более четырёх участков. Учитывать уже выбранные новые ветви; иначе проверить новую камеру на трубе. **[ТА, §8.2]**

**Готово:** список кандидатов без дублей; ближайшая врезка ещё не считается лучшей. Подробности: §5.

### Шаг 3. Маршрут A*

Добавить точные концы в сетку. Проверять целые рёбра, габарит труб и отступы от запретных полигонов. Дороги, трамвай и коммуникации пересекать отдельными проверенными переходами; выделять специнтервалы и коэффициенты. Поисковые штрафы не включать в фактическую стоимость.

**Готово:** один допустимый маршрут на рассматриваемую пару либо причина неуспеха. Неудача ограниченного поиска не доказывает невозможность подключения. Подробности: §6–7.

### Шаг 4. Полный evaluator

Посчитать расходы, диаметры, предельные длины, габариты, камеры и спецпроходы. Передать добавленный расход к источнику; реконструировать только нужные части старых труб, общие части не оплачивать дважды. Учесть реконструкцию камер, врезки и штрафы. При росте диаметра перепроверить маршрут.

```text
S = 0.7 × (C / 25_000_000) + 0.3 × (L / 100)
L = длина новой сети + длина реконструкции
```

**Готово:** контрольные примеры совпадают с независимым расчётом; недопустимые варианты отклоняются. Подробности: §9–11.

### Шаг 5. Независимые подключения

Обрабатывать ОКС по убыванию расхода, при равенстве — по ID. Начать с пустой новой сети и штрафов за всех. Для каждого маршрута пробно добавить подключение, вызвать evaluator **для всего варианта** и сравнить настоящий `S`, включая возможность оставить ОКС неподключённым.

Общая старая сеть и занятость камер пересчитываются совместно. Пересекающиеся новые линии не объединять автоматически. **[Решение]**

**Готово:** все точки учтены; соответствующие ОКС подключены либо оштрафованы с диагностикой причины. Подробности: §8.1–8.2.

### Шаг 6. Экспорт и приёмка

Вернуть один `FeatureCollection` в EPSG:4326. Создавать по необходимости `heat_network`, `tie_in`, `heat_network_reconstruction`, `heat_chamber`, `heat_chamber_reconstruction`, `technical_node`; добавить ровно один `variant_summary`. Не создавать пустую реконструкцию ради наличия типа. В 2D `depth_start/depth_end = null`. **[ТА, §10]**

**Готово:** независимая проверка ссылок, геометрии, сумм и штрафов проходит; результат запускается через Docker Compose. Подробности: §14 и приложение B.

## 4. Когда первый этап закончен

При валидном входе текущий набор проходит сквозной запуск; все 17 точек имеют учтённый исход. Сохранены результат, ошибки/причины неподключения, `C`, `L`, `S`, время и память. Повторный запуск с теми же настройками воспроизводит результат.

До сдачи проверить маленькие эталоны: прямое подключение; обход парка; спецпроход дороги; граница 10 м и заполненная камера; частичная/общая реконструкция; неподключение; ошибочный вход; согласованность экспорта. Обучение и доказанный оптимум для этого не нужны.

## 5. Что оставляем после MVP

Объединения → несколько маршрутов/порядков и дедупликация → локальные перестройки/edge exchange → LNS → ALNS/отжиг. ML, масштабирование до 3 ГБ и глубина — отдельные этапы. Не создавать зависимость первого запуска от этих модулей.
