# Проектирование теплосети: спецификация алгоритма

**Файл:** `algorithm_design.md`  
**Версия:** 0.3 · 18 сентября 2026 года  
**Назначение:** подробная спецификация baseline и последующих улучшений; развитие `heat_network_algorithm_plan.md`.  
**Статус:** проект алгоритма, а не реализованный и испытанный сервис.

> **Начинать разработку с [MVP_IMPLEMENTATION_ORDER.md](MVP_IMPLEMENTATION_ORDER.md).** Первый этап — загрузка → кандидаты врезки → A* → независимые подключения с полным evaluator → один проверенный GeoJSON. Объединения, edge exchange, LNS, ALNS и ML не входят в первый этап. Этот большой документ — справочник по модулям и дальнейшему развитию, а не список задач первого спринта.

## 0. Как читать документ и чему доверять

Используются пять пометок:

- **[ТА]** — требование из загруженного «Технического приложения.docx»; после пометки указан раздел.
- **[РГ]** — положение рабочего `heat-network-case-onboarding.md`, включая записанные уточнения встречи. Это не самостоятельный официальный норматив.
- **[НД]** — сводка текущего набора данных, переданная командой по результатам ранее выполненного анализа. Это сведения о конкретном наборе, а не ограничения для любого входного файла.
- **[Решение]** — предложенный здесь способ реализации. Его параметры можно менять после тестов, не меняя ТЗ.
- **[Уточнить]** — источник не даёт однозначного ответа. Временная интерпретация описана явно и не выдаётся за правило организаторов.

Техническое приложение задаёт расчётный контракт. Рабочий гайд добавляет сведения о стеке и встрече. При расхождении не выбираем удобную формулировку молча: регистрируем вопрос и версию принятого правила. Предыдущие сообщения про AlphaZero, Штейнера и LNS — идеи решения, а не новые требования ТЗ.

### 0.1. Текущий набор данных

**[НД]** По переданным командой результатам анализа текущий GeoJSON содержит **144 объекта**:

| Категория из сводки | Количество |
| --- | ---: |
| Точки подключения | 17 |
| Участки существующей сети | 29 |
| Существующие камеры | 9 |
| Пространственные ограничения | 88 |
| Источник | 1 |
| **Всего** | **144** |

Эти количества — контрольная сводка конкретного набора: `17 + 29 + 9 + 88 + 1 = 144`. Не зашивать их в валидацию любых будущих датасетов. При первом запуске загрузчик сохраняет собственную статистику и хэш входа, чтобы связать расчёт с конкретной версией набора.

Упомянутые в рабочем гайде **2–3 ГБ — возможный масштаб других входов**, а не установленный размер нынешнего файла из 144 объектов. Сводка не сообщает число координат, распределение диаметров и результаты измерения ресурсов. Не делать из числа объектов вывод о проверенной производительности. [РГ, §4; НД]

**Проверка источника расходов.** Сводка не выделяет отдельно `oks_future`, а техническое приложение размещает `flow_tph` в `oks_future` и связывает его с точкой через `oks_id`. Перед расчётом проверить фактическое размещение расхода и соответствие точек ОКС. Если текущий набор имеет иную схему, оформить явное правило адаптации; не придумывать недостающие значения и не заменять их нулём. Это проверка контракта, а не утверждение, что расходы в наборе отсутствуют. [ТА, §2.2; НД]

Грунты и геологические слои **не предусмотрены описанным входным контрактом**; переданная сводка состава не описывает дополнительные атрибуты. Реальный рельеф в дополнительной задаче явно не учитывается. [ТА, §2 и §6]

### 0.2. Объём первого MVP — без LNS

**[Решение]** Зафиксирован профиль `baseline`: один детерминированный порядок обработки точек, до одного найденного маршрута на кандидата врезки (`k = 1`), последовательное добавление независимых подключений и одна лучшая проверенная выходная схема. Полный инженерный расчёт обязателен уже здесь, включая реконструкцию общих старых участков и штрафы.

**Граф MVP:** локальная регулярная восьмисвязная сетка + обязательные точки с точными координатами + отдельные проверяемые переходы через разрешённые препятствия. Начальный шаг 2 м, локальное уточнение 1/0,5 м при неуспехе; подробнее §6.1. Не выбирать заново между grid, visibility graph и octree в первом спринте.

Для нынешнего набора допускается хранение геометрий и пространственного индекса в памяти в рамках заданного лимита. Потоковый загрузчик и интерфейс хранилища сохраняем; дисковую БД и обработку больших файлов не делаем предварительным условием первого baseline.

**Не входят в первый MVP:** объединение/разделение ветвей, edge exchange, несколько стартов, архив разнообразия, LNS, ALNS, имитация отжига, ML, 3D и промышленная обработка 3 ГБ. Их описание ниже — roadmap. Стек Java 11, офлайн-режим и Docker Compose из рабочего гайда сохраняются. [РГ, §2 и §4]

Сложность поиска откладываем, правила ТЗ — нет. Обучение выбора действий (§16) не требуется для запуска первого MVP и не подменяет проверки.

## 1. Решение целиком

### 1.1. Что получает и возвращает сервис

На входе один `FeatureCollection`: существующие трубы, камеры, источник, будущие и существующие ОКС, точки подключения, ограничения. На выходе один `FeatureCollection` с рассчитанными вариантами. Геометрия входа/выхода — EPSG:4326; длины и буферы считаются в EPSG:32637. [ТА, §2 и §10]

Стек Java 11, Spring Boot/Spring Data, офлайн-работа и Docker Compose зафиксированы в рабочем гайде. Конкретные версии библиотек нужно проверять на совместимость отдельной сборкой, а не брать автоматически самые новые. [РГ, §2 и §4]

### 1.2. Последовательность MVP и последующее развитие

**Первый MVP — профиль `baseline`:**

```text
Прочитать GeoJSON и проверить вход, расходы и ссылки
  → восстановить старую сеть и направление к источнику
  → создать пространственный индекс
  → в фиксированном порядке обрабатывать точки подключения
      → найти кандидаты врезки с учётом занятых портов
      → A* построить маршрут для каждого рассматриваемого кандидата
      → проверить весь пробный вариант и пересчитать реконструкцию и S
      → оставить лучшее допустимое независимое подключение либо штраф
  → полностью перепроверить итоговый baseline
  → сформировать один выходной GeoJSON
```

**После приёмки baseline, отдельными этапами:** несколько порядков старта и маршрутов → выгодные объединения → локальные изменения → LNS → ALNS/отжиг → необязательное обучение. Выдачу содержательно разных вариантов добавляем после работающего экспорта одной схемы. Дополнительный профиль глубины также не входит в первый этап.

**Главное разделение:** `RoutePlanner` отвечает «как соединить эти две точки», `InitialSolutionBuilder` собирает независимые подключения, `EngineeringEvaluator` проверяет заданный вариант и считает. `DiameterPlanner` подбирает допустимые диаметры. `NetworkOptimizer` решает «как перестроить связи и ветки», но появляется только после MVP.

### 1.3. Что оптимизируем

```text
S = 0.7 × (C / 25_000_000) + 0.3 × (L / 100)
L = длина новой сети + длина реконструируемых существующих участков
```

`C` включает новое строительство, новые камеры, врезки, реконструкцию труб и нужных существующих камер, штрафы за неподключённые ОКС. Меньше `S` — лучше. [ТА, §8–9]

**Нельзя заменить формулу на `0.7 × рубли + 0.3 × метры`.** Нормировка является частью ТЗ. Нельзя также ранжировать только по стоимости новых труб: это потеряет камеры, врезки и реконструкцию.

Недопустимый вариант не конкурирует с допустимым, даже если он очень дешёвый. Неподключённый ОКС — разрешённое состояние со штрафом; пересечение парка, перегруженная камера или недостаточный диаметр — нарушение правил. [ТА, §3, §5 и §8.3]

## 2. Термины и свойства решения

### 2.1. Словарь для разработчика

| Термин | Что означает здесь |
| --- | --- |
| Топология | Кто с кем соединён, без привязки к точной форме линии |
| Геометрия | Где физически проходит каждая линия |
| Граф | Узлы и соединяющие их рёбра |
| Узел | Врезка, камера, точка подключения или промежуточная точка |
| Ребро | Один потенциальный или выбранный путь между узлами |
| Дерево | Связная сеть без циклов |
| Лес | Несколько отдельных деревьев; они могут подключаться к разным местам старой сети |
| Кандидат | Один из вариантов, который ещё предстоит проверить |
| Baseline | Простое начальное решение для сравнения с оптимизатором |
| Эвристика | Практическое правило выбора; не доказательство оптимальности |
| LNS | Перепроектирование достаточно большого фрагмента текущего решения |
| ALNS | LNS с адаптацией частоты выбора операций |
| Seed | Начальное число генератора случайности для воспроизводимого запуска |
| Evaluator | Детерминированная проверка и оценка законченного кандидата |

### 2.2. Три разных графа — не смешивать

**[Решение]** Храним раздельно:

1. `ExistingNetwork`: существующие трубы, камеры, источник и ссылки `upstream_object_id`. Геометрию нельзя произвольно удалять или перестраивать.
2. `RoutingGraph`: служебные точки пространства и допустимые перемещения. Миллионы возможных перемещений не означают миллионы реально построенных труб.
3. `SolutionGraph`: только выбранная новая сеть, её физические узлы и привязки к существующей сети.

Расчёт расхода делается по `SolutionGraph + ExistingNetwork`, а поиск пути — по `RoutingGraph`.

### 2.3. Что должно быть истинно для завершённого варианта

**[ТА + Решение]** Проверяем:

- Каждый подключённый ОКС учитывается ровно один раз и имеет однозначный путь к источнику. Неподключённые перечислены отдельно и оштрафованы.
- Новые ветви не создают циклов. В MVP каждая новая ветвящаяся компонента имеет одну точку присоединения к существующей сети. Это выбранная модель радиального подключения, согласованная с требованием рабочего гайда об отсутствии циклов.
- Развилки находятся в камерах; у физической камеры не более четырёх примыкающих участков, включая старые. [ТА, §3]
- Одна линия представляет **пару** подающей и обратной труб: расход и длина пары не удваиваются. [ТА, §3]
- Все ограничения проверены для фактического диаметра и расчётного габарита, а не только для оси.
- Все расходы, расходы реконструкции и стоимости пересчитаны для текущей топологии, а не унаследованы от предыдущего кандидата.
- Совпадение линий на карте не означает бесплатного объединения. Объединение — отдельная операция с узлом, суммой расходов и новым расчётом.

Два независимых подключения могут прийти в одну существующую камеру. Это один физический узел, но несколько независимых врезок и соответствующих оплат. Графовую степень считаем по физическим участкам, а не по числу GeoJSON-записей. [РГ, §4; ТА, §8.2]

### 2.4. Незаконченный и законченный вариант

**[Решение]** `PartialSolution` после удаления ветвей может содержать ещё не назначенные ОКС. Его нельзя сравнивать с готовым решением по «маленькой текущей цене».

До оценки каждому ОКС назначается один из двух статусов: `CONNECTED` или `UNCONNECTED_WITH_PENALTY`. Если ОКС временно выпал после удаления общего ребра, он попадает в список восстановления, а не исчезает из расчёта.

Внутренние расчётные функции разрешено сначала объединить в один модуль evaluator; отдельный класс на каждую строку не является требованием.

### 3.2. Минимальная модель

Псевдоструктуры ниже — описание, не синтаксис готовых Java-классов. В Java 11 реализовать обычными классами.

```text
ProblemData
  featureStore, spatialIndexes
  existingNetwork
  demands: oksId → {connectionPointId, point, flow_tph}
  rules, catalog, sourceFileHash, rulesVersion

TieInCandidate
  hostType: EXISTING_CHAMBER | EXISTING_PIPE
  hostId
  pointXY
  stationFromUpstream: число для врезки внутрь трубы
  reason: nearest_chamber | projection | sampled_point | alternative

LogicalBranch
  fromPhysicalNodeId, toPhysicalNodeId
  routeGeometryXY, routeId
  assignedDemandIds
  diameterHint, assignedDiameter

Solution
  physicalNodes, logicalBranches, tieInPorts
  connectedOksIds, unconnectedOksIds
  revision, provenance

Evaluation
  status: VALID | INVALID | REQUIRES_REROUTE | SEARCH_INCOMPLETE
  violations[]
  calculatedSegments[], chambers[], tieIns[]
  reconstructedSegments[], reconstructedChambers[]
  costsByCategory, lengthsByCategory, score
```

`Solution` хранит конструкцию. `Evaluation` — производный снимок расчёта этой конструкции. После изменения `Solution.revision` предыдущий расчёт недействителен.

**[Решение]** Не копируем весь городской датасет в каждое состояние поиска. Неизменяемые исходные геометрии разделяются; копируются только изменяемые части новой сети. Кэш геометрического пути и кэш полной стоимости — разные кэши.

## 4. Подготовка данных без загрузки всего файла в память

### 4.1. Первый проход

**[Решение на основе РГ, §4 и §13]** JSON читается потоковым парсером. Для первого MVP объекты текущего набора храним в памяти вместе с типом, ID, атрибутами, геометрией и bounding box — охватывающим прямоугольником; проверяем заданный лимит памяти/размера геометрии. Число 144 не отменяет этих лимитов.

**Для больших входов, после MVP:** тот же интерфейс загрузчика записывает объекты во временное дисковое хранилище. Реализация этой стратегии не должна блокировать первый сквозной запуск.

Проверяем обязательные поля, тип геометрии, конечность чисел, уникальность ID и валидность геометрии. Входные ошибки не «исправляем» через `buffer(0)` или замыкание контуров без сообщения. Неизвестный `restriction_type` нельзя молча считать свободным пространством. [ТА, §2; РГ, §4]

Связи по ID проверяются вторым проходом: объект, на который ссылаются, может находиться в конце файла.

В режиме хранения в памяти расход RAM зависит от всех загруженных геометрий и индекса. В дисковом режиме рабочий объём зависит от текущего объекта, буферов записи и кэшей. **Потоковый разбор сам по себе не означает постоянную память.** Для очень крупных объектов нужен отдельный лимит/режим обработки и понятная диагностика.

### 4.2. Индексы и локальные окна

**[Решение]** В MVP — пространственный индекс в памяти и выборка объектов локального окна. После приёмки baseline масштабируемый вариант — дисковое пространственное хранилище с индексом и ограниченным кэшем. Конкретный движок выбирается отдельным решением; БД не является зависимостью первого спринта.

Нельзя загружать только объекты, чьи **центры** лежат в окне: длинная труба или полигон могут пересекать окно, а центр находиться снаружи. Отбор делается по пересечению bounding box, затем точной геометрии. Окно увеличивается на запас под габариты, отступы и границы спецпроходов.

Для расчёта реконструкции дополнительно подтягивается **вся цепочка к источнику**, даже за пределами геометрического окна. Локальная оптимизация не делает реконструкцию локальной.

### 4.3. Восстановление старой сети

**[ТА, §2.2]** Направление задаёт `upstream_object_id`, а не порядок координат в LineString.

**[Решение]** Для каждой трубы определить конец со стороны следующего объекта. Если следующий объект — камера/источник, проверить геометрическое совпадение конца с точкой. Если следующая труба — найти согласованное место соединения. Использовать исходную топологию; нельзя автоматически соединять все линии, которые просто пересекаются на карте.

Если из ссылок и геометрии нельзя однозначно определить соединение, вернуть `AMBIGUOUS_UPSTREAM_GEOMETRY` с ID. Развёрнутая в координатах линия должна давать тот же результат расчёта.

Ориентируем внутреннюю копию трубы так, чтобы `s = 0` был со стороны источника, `s = L` — с противоположной стороны. `s` — расстояние вдоль линии, а не расстояние по прямой. Это потребуется для частичной реконструкции.

Проверить отсутствие циклов ссылок, существование всех целей ссылок и достижение источника. Число существующих участков камеры восстанавливается из её физической примыкаемости и согласованной топологии, а не из одного поля `diameter`.


## 5. `TieInFinder`: как искать точки врезки

### 5.1. Кандидаты бывают двух типов

**[ТА, §8.2; Решение]** Рассматриваем существующие камеры и новые точки на существующих трубах. «Ближайшая точка» — способ предложить кандидат, а не окончательный ответ: немного более далёкая врезка может избежать дорогой реконструкции.

Для одного ОКС:

1. Найти ближайшие камеры по пространственному индексу.
2. Найти ближайшие существующие трубы и проекцию точки ОКС на каждую LineString.
3. Добавить точки вдоль этих труб рядом с проекцией, а также подходящие концы. Это позволяет выбрать сторону препятствия или менее дорогую реконструируемую часть.
4. Применить правило близости камер и убрать дубликаты.
5. Упорядочить кандидатов по дешёвой предварительной оценке: расстояние, наличие свободного порта камеры, примерный запас пропускной способности пути к источнику. Это эвристика, не доказанная нижняя граница полной стоимости.
6. Для первых кандидатов строить реальные маршруты. При неуспехе расширять радиус, набор труб и число точек.

**Стартовые настройки MVP [Решение]:** до 8 ближайших камер и до 12 труб в начальном радиусе 250 м; на трубах сначала брать проекции и подходящие концы. При неуспехе расширять радиус и список, не исключая оставшиеся камеры/трубы текущего набора. Числа не взяты из ТЗ; полный набор параметров и лимитов — в §18.

**После MVP:** добавлять точки вдоль труб через 20 м возле проекции. Это расширяет поиск врезок, но не нужно для первого запуска. Функция `sampleNearProjection` в псевдокоде ниже при выключенном `sample_pipe_points` возвращает пустой список.

Длина, число кандидатов и радиус ограничены бюджетом поиска. Неудача в первых 250 м не доказывает, что ОКС невозможно подключить.

### 5.2. Правило 10 м и вместимость камеры

**[ТА, §8.2]** Если выбранная точка врезки не далее 10 м от существующей камеры **и после подключения к ней будет не более четырёх участков**, врезку выполняют в этой камере. Если вместимости недостаточно либо подходящая камера дальше 10 м, создают новую камеру в точке врезки.

**[РГ, §4]** При нескольких камерах в радиусе 10 м выбирать вариант по стоимости. Несколько независимых новых ветвей в одну камеру — несколько врезок.

**[Решение]** Проверяем камеру с учётом **всего текущего кандидата**, а не только старой сети:

```text
degree_after = существующие физически примыкающие участки
             + выбранные новые примыкания этого варианта
```

При `degree_after > 4` этот способ подключения недопустим. Проверка повторяется после объединения, разделения или смены врезки.

Если несколько подходящих камер имеют свободные места, создаём альтернативы с концом маршрута в каждой камере. Не оставляем рядом отдельную новую камеру просто ради удобства трассировки, когда правило требует использовать существующую. Если все близкие камеры заполнены, проверяем вариант с новой камерой на трубе.

Расстояние 10 м измеряется в расчётной проекции между кандидатной точкой и камерой. Ровно 10 м входит в условие «не далее». Допуск геометрических вычислений не должен превращать 10,5 м в 10 м.

### 5.3. Что считать новым примыканием

Новая врезка внутрь старой трубы делит её на две топологические части. Поэтому у новой камеры на старой трубе уже есть два существующих направления. Одна новая ветка даст степень 3, две — степень 4. Если врезка совпала с существующим концом/узлом, считать фактическую топологию, а не автоматически добавлять два участка. [Решение, следствие ТА §3 и §8.2]

При создании такой камеры её размер определяется максимальным диаметром **всех** примыкающих частей: новых, старых и реконструируемых. Камера возле трубы большого диаметра не становится маленькой только потому, что новая ветка тонкая. [ТА, §8.2]

### 5.4. Псевдокод

```text
findTieIns(anchor, solution, budget):
    raw = nearestChambers(anchor)
    for pipe in nearestPipes(anchor):
        raw += projection(anchor, pipe)
        raw += sampleNearProjection(pipe)
        raw += relevantPipeEnds(pipe)

    result = []
    for candidate in raw:
        if candidate.isExistingChamber:
            if hasFreePort(candidate, solution):
                result += candidate
            continue

        nearby = allChambersWithin(candidate.point, 10 m)
        usable = [c for c in nearby if hasFreePort(c, solution)]
        if usable is not empty:
            result += candidateAtEach(usable)
        else:
            result += candidateWithNewChamber(candidate)

    result = deduplicateByPhysicalHostAndStation(result)
    return rankForRouting(result, budget)
```

`hasFreePort` — предварительная проверка. Окончательная степень, выбор камер и цена проверяются после присоединения всей ветви. Данные о занятых портах не кэшируются без `solution.revision`.

## 6. `RoutePlanner`: по какому пространству ищем путь

### 6.1. Конкретный выбор для MVP

**[Решение, зафиксировано для первого MVP]** Используем **локальную регулярную восьмисвязную сетку + обязательные точки + переходы через разрешённые препятствия**:

- обычные короткие рёбра соединяют соседние точки свободного пространства;
- точные координаты точек подключения, камер и врезок добавляются отдельно; узлы ветвления добавятся на этапе объединений;
- точные конечные точки соединяются с соседними узлами сетки проверенными отрезками; дополнительные сокращающие прямые соединения можно добавить позже;
- специальные длинные рёбра проводят маршрут через дорогу, трамвай или коммуникацию целиком, с соблюдением правил.

Это не дорожный граф и не равномерная 3D-сетка всего города. Дорога у нас — препятствие с разрешённым переходом, а не бесплатная линия для прокладки вдоль неё.

Начальный шаг сетки — 2 м; при тесных проходах пробуем 1 м, затем 0,5 м в ограниченном окне. Это параметры реализации. Узлы создаются лениво или по локальным блокам, а не для всей территории сразу.

На такой структуре A* ищет путь по рёбрам. Математический механизм A* не знает предметных ограничений: они должны быть реализованы в построении графа и проверке переходов. [Методический источник M1]

### 6.2. Окно поиска

Начать с прямоугольника, охватывающего начало и конец, расширенного на 100 м. При неуспехе расширять запас вдвое, пока не исчерпан бюджет или не покрыта релевантная область датасета.

Использовать единое начало координат сетки: расширение окна не должно смещать все узлы. Ключ узла — целочисленные индексы сетки и уровень детализации.

Ограничение окна ускоряет поиск, но может отрезать длинный обход. Поэтому возвращаем разные причины: `NO_PATH_ON_EXPLORED_GRAPH`, `ROUTING_BUDGET_EXHAUSTED`, `ENDPOINT_IN_FORBIDDEN_ZONE`. Только первые две говорят о результате **ограниченного поиска**, а не о доказанной невозможности в непрерывном пространстве.

### 6.3. Запретные полигоны и габарит новой сети

**[ТА, §4.2 и §5.1]** Линия — продольная ось расчётного габарита пары труб. Для существующего ОКС отступ зависит от условного диаметра: менее 500 мм — 5 м; 500–800 мм — 7 м; от 900 мм — 9 м. Для парков, социальных, запрещённых территорий и воды — 1 м.

**[Решение]** При проверке оси относительно полигона используем:

```text
radius_for_axis = нормативный горизонтальный отступ
                + расчётная ширина новой пары / 2
                + небольшой строительный запас алгоритма
```

Для прохождения рядом с линейной коммуникацией:

```text
axis_clearance = отступ между внешними габаритами
               + ширина новой пары / 2
               + ширина существующего объекта / 2
               + запас
```

Ширины берутся из приложения, не приравниваются к условному диаметру. Для газопровода условный габарит 0,4 м, кабеля — 0,2 м; существующая теплосеть — по таблице её диаметра. [ТА, §4.2–4.3]

Буферы ускоряют отсев. Для принятия ребра дополнительно проверяем точное расстояние/пересечение исходных геометрий. Полигональная аппроксимация округлых буферов имеет погрешность; её нельзя использовать для разрешения маршрута ближе установленного расстояния. [M2; Решение]

**Нельзя проверять только концы ребра:** диагональное ребро может пересечь угол здания, хотя оба конца находятся снаружи. Проверяем весь отрезок и весь расчётный габарит маршрута.

### 6.4. Разрешённые пересечения — не просто «дорогие клетки»

| Объект | Прохождение рядом, м | Пересечение | Границы специального участка | Kспец |
| --- | --- | --- | --- | --- |
| Дорога | 1,5 | Угол не менее 45° | Внутри полигона и по 3 м с двух сторон | 1,60 |
| Трамвайные пути | 1,5 | Угол не менее 45° | Внутри полигона и по 3 м с двух сторон | 1,75 |
| Газопровод | 2,0 | Допускается | По 2 м от точки пересечения | 1,25 |
| Кабель до 35 кВ | 2,0 | Допускается | По 2 м от точки пересечения | 1,15 |
| Существующая теплосеть без врезки | 1,0 | Допускается | По 2 м от точки пересечения | 1,05 |

Это параметры ТА, §5.1. Вертикальные условия включаются только в дополнительном режиме глубины.

**[Решение]** Обычные рёбра не пересекают запретную для параллельного сближения область коммуникации. Вместо них добавляем **переход**: одно составное ребро от безопасной точки с одной стороны до безопасной точки с другой. У ребра сохранены все пересечения и интервалы стоимости.

Так алгоритм не сможет проложить трубу вдоль газопровода внутри отступа, оправдывая это повышенным коэффициентом.

### 6.5. Как построить такие переходы

**[Решение]** Для каждого препятствия в рабочем окне:

1. Выбрать конечный набор мест перехода: около прямого направления «начало — конец», возле ближайших точек и через заданный шаг вдоль границы/линейной геометрии.
2. В каждом месте попробовать несколько направлений: поперечное и отклонённые от него. Для дороги/трамвая оставить только допустимые по углу.
3. Продлить прямой участок в обе стороны до выхода из области обязательного отступа. Дополнительно обеспечить полную длину специальных «крыльев» по 2 или 3 м.
4. Проверить весь переход против остальных объектов. Если он пересекает несколько разрешённых препятствий, рассмотреть их вместе; если хотя бы одно запрещённое — отклонить.
5. Создать две точные точки входа/выхода и связь между ними. Они могут находиться вне обычных узлов сетки.
6. Соединить эти точки с видимыми соседними узлами сетки безопасными рёбрами.

Если близкие препятствия не оставляют свободной точки между собой, строится общий переход через группу; его цена делится по фактическим интервалам, а не назначается одним произвольным коэффициентом.

Внутри перехода нельзя устроить поворот или ветвление без новой проверки. При изменении диаметра переход проверяется заново, поскольку безопасные границы меняются.

**[Уточнить Q01]** Приложение задаёт угол пересечения дороги, но не определяет, относительно какой линии измерять его для сложного полигона. Временный вариант: на простом участке проверять угол с локальными касательными двух противоположных границ; для прямой дороги они параллельны её оси. Переходы через неоднозначные перекрёстки этим правилом не «узакониваем»: нужен согласованный `CrossingAnglePolicy` или другой коридор. Это ограничение текущей реализации, не дополнительный запрет из ТЗ.

### 6.6. Подход к точке врезки

Общий запрет сближаться с существующей трубой не должен блокировать саму врезку.

**[Решение]** Для конечного подхода к выбранному `hostId` разрешается специальное терминальное ребро: оно заканчивается точно в точке врезки и не продолжает движение вдоль/через этот объект. Другие ограничения действуют полностью. Настоящая врезка не считается независимым спецпересечением этой же трубы.

Для существующей камеры действует аналогичная терминальная проверка с учётом примыкающих старых труб. Нельзя глобально отключить проверки существующей теплосети только потому, что она является целью маршрута.

### 6.7. Стоимость ребра для A*

Для фиксированного предполагаемого диаметра `D`:

```text
route_weight(edge, D) =
    0.7 × constructionCost(edge, D) / 25_000_000
  + 0.3 × actualLength(edge) / 100
```

В 2D `constructionCost` учитывает длину, ставку диаметра и интервалы Kспец. Цена врезки, камер и реконструкции не размазывается произвольным образом по клеткам: она учитывается в полном расчёте кандидата.

Для A* берём нижнюю оценку оставшейся цены:

```text
heuristic(node) = straightDistance(node, goal)
               × (0.7 × basePricePerMeter(D) / 25_000_000 + 0.3 / 100)
```

**[Решение]** Такая оценка не включает ещё неизвестные надбавки и применяется только к графу с неотрицательными, не меньшими базовой ставки весами. Если добавляем скидку за использование построенной магистрали, эту оценку нельзя оставлять без доказательства: в MVP скидки внутри маршрутизатора не вводим, а выгоду объединения считаем целиком в evaluator.

В тестах A* с этой эвристикой должен дать тот же вес кратчайшего пути, что Дейкстра на **том же фиксированном графе**. Это не означает нахождение кратчайшей линии среди всех возможных непрерывных кривых.

### 6.8. Сглаживание и новая сеть как препятствие

После поиска удаляем лишние повороты только если новый прямой отрезок проходит повторную проверку габаритов, расстояний, углов, специнтервалов и конечных привязок. Затем пересчитываем длину и стоимость.

**[Решение]** Для новой сети различаем два действия:

- присоединиться к выбранной ветке: явно добавить узел и пересчитать общий расход;
- пройти независимо: не допускать физического наложения/столкновения габаритов.

Правил независимого пересечения **двух новых** сетей приложение отдельно не задаёт. Поэтому в 2D-MVP такое пересечение без узла отклоняем или перестраиваем. Не применяем автоматически коэффициент 1,05: он относится к существующей теплосети. [Уточнить Q08]

## 7. Спецпроходы и до k альтернативных маршрутов

### 7.1. Как выделить специальный участок

**[ТА, §5 и §8.1; Решение]** Для готовой линии вводим расстояние вдоль неё `s` от 0 до длины. Находим все пересечения:

- дорога/трамвай: интервал входа-выхода из полигона, расширенный вдоль маршрута на 3 м с каждой стороны;
- газ/кабель/независимое пересечение теплосети: интервал `[s_cross − 2, s_cross + 2]`.

Если линия пересекает один полигон несколько раз, обрабатываем каждый вход-выход. Касание границы не приравниваем автоматически к корректному переходу насквозь.

Если обязательный специальный интервал вылезает за конец проектируемой линии, нельзя просто укоротить его через `clamp(0, L)` и объявить соответствие. Нужно продлить/изменить подход либо получить уточнение для такого узла. [Уточнить Q02]

### 7.2. Наложения

**[РГ, §4]** На перекрытии применяется максимальный коэффициент, не произведение.

**[Решение]** Разбить линию по всем концам интервалов; для каждого элементарного отрезка определить активные ограничения:

```text
K(segment) = max(1, K всех покрывающих его специнтервалов)
```

Пример: газ даёт 1,25 на метрах 10–14, кабель — 1,15 на 12–16. Получаем: 10–14 с 1,25 и 14–16 с 1,15. На 12–14 не должно быть `1,25 × 1,15`.

При изменении применяемого коэффициента создаётся граница расчётного участка, даже если `laying_method` по обе стороны остаётся `special`. Изменение набора препятствий без изменения расчётных параметров можно оставить внутренней метаданной.

### 7.3. Что означает k

**[Решение]** Для пары «точка подключения — кандидат врезки» хотим получить **до k разных пригодных маршрутов**. В первом MVP `k = 1`: один найденный маршрут на кандидата, но сами кандидаты врезки сравниваются между собой. При неуспехе продолжаем расширение окна/уточнение сетки и перебор врезок, а не прекращаем обработку ОКС.

**После MVP:** `k = 3` и поиск разных коридоров по процедуре ниже. Это не обещание обязательно найти три маршрута и не заявление о трёх математически кратчайших путях.

Алгоритм альтернативных маршрутов:

1. Найти первый путь с базовыми весами.
2. Для следующих попыток увеличить поисковые веса уже использованных коридоров или временно закрыть один из использованных переходов.
3. Снова запустить поиск, проверить и сгладить маршрут.
4. Убрать почти совпадающие линии.
5. Вернуть до k вариантов с **истинными** длинами и ценами.

Поисковая надбавка за повторный коридор не попадает в стоимость строительства и итоговый S. Число попыток ограничено, например 12. Если нужны именно k кратчайших простых путей, это отдельная реализация, а не название для такого эвристического перебора.

### 7.4. Контракт результата маршрутизатора

```text
RouteResult
  routes[]:
    geometryXY
    length
    diameterUsedForClearance
    crossingEvents[]
    specialIntervals[]
    constructionCostEstimate
    corridorSignature
  exploredWindow
  gridStep
  stopReason
```

В кэш маршрута входят: версия данных и правил, точные концы, диаметр, режим 2D/глубина, ограничения текущей новой сети, способ измерения угла и параметры графа. **Кэш по одной паре точек недостаточен.**

## 8. Построение первого решения

### 8.1. Независимые подключения — baseline, а не доказанный оптимум

**[Решение]** Сначала не объединяем ОКС новой общей магистралью. Для каждого предлагаем отдельный путь до существующей сети. Они могут использовать одну старую камеру только в рамках её вместимости.

В первом MVP используем **один** порядок: по убыванию расхода, при равенстве — по ID ОКС. Это делает baseline воспроизводимым.

После MVP добавляем порядки по возрастанию числа доступных врезок и случайный с фиксированным seed. Это дополнительные стартовые эвристики, а не обязательные три выходных варианта.

Почему нельзя просто выбрать минимум для каждого ОКС независимо? Два подключения могут вместе вызвать реконструкцию общего старого участка или занять последний порт камеры. Поэтому после каждого добавления пересчитываем **весь частичный набор с окончательно учтёнными штрафами за остальных**.

### 8.2. Детальная процедура

```text
buildIndependentBaseline(problem, order, budget):
    current = решение без новых труб
    current.unconnected = все ОКС
    currentEval = evaluate(current)  # штрафы включены

    for oks in order:
        if not budget.canStartDemand(): break
        alternatives = []
        candidates = findTieIns(oks.point, current, budget)

        for tieIn in candidates:
            d0 = minimumDiameterForFlow(oks.flow)
            routes = route(oks.point, tieIn.point, d0, k)

            for path in routes:
                trial = copy(current)
                addIndependentConnection(trial, oks, tieIn, path)
                trial.unconnected.remove(oks)
                result = materializeAndEvaluate(trial, budget)
                if result.valid:
                    alternatives.add(result)

        # Не подключать этот ОКС пока тоже разрешённая альтернатива.
        alternatives.add(currentEval)
        chosen = minByActualS(alternatives)
        current = chosen.solution
        currentEval = chosen

    return currentEval
```

Если маршрут невозможен из-за уже выбранной новой ветви, пробуем другую врезку или допустимый обход с учётом построенной ветви; не превращаем пересечение молча в объединение. Другие порядки старта добавляются после первого MVP.

Все вложенные построения путей и оценки используют общий бюджет. При его исчерпании возвращается последний проверенный `currentEval`; ещё не обработанные ОКС уже находятся в его списке неподключённых со штрафами.

В MVP допустимый baseline может оставить часть ОКС неподключёнными. Мы **не гарантируем** существование валидного варианта со всеми подключениями. До завершения перебора пробуем расширение области и набора врезок в пределах бюджета; оставшимся ОКС начисляем штраф и сохраняем причину. Общее подключение — последующее улучшение, а не скрытая зависимость baseline.

### 8.3. Первые объединения — после MVP

**[Roadmap]** Этот подраздел не входит в первый спринт и не вызывается в профиле `baseline`.

Берём пары или небольшие группы ОКС/ветвей, в том числе ранее неподключённые. Генерируем несколько мест общей камеры: существующие узлы новой сети, проекции на её ветви, свободные точки возле центра группы и маршрутов к кандидатам врезки.

Центр группы — лишь предложение. Если он попал в парк или не обеспечивает выгодной трассы, он отбрасывается. У каждого кандидата камеры строим пути от потребителей и к врезке; при группе более трёх дочерних ветвей нужна дополнительная структура камер, а не камера степени 5.

Дальше:

```text
tryMerge(group, current, budget):
    trial = detachSelectedDemands(current, group)
    # Сохраняем пути остальных ОКС, удаляем только ненужные хвосты.
    for branchPoint in candidateBranchPoints(group):
        for tieIn in candidateTieInsForGroup(group):
            candidate = buildSharedTree(trial, group, branchPoint, tieIn)
            result = materializeAndEvaluate(candidate, budget)
            keepBestValid(result)
    return bestCandidate
```

Принимаем объединение, только если его **полный** S меньше S текущего решения. Два близких ОКС не обязаны выгодно объединяться: диаметр, камера и реконструкция могут перекрыть экономию длины.

Повторяем лучшие найденные объединения до исчерпания улучшений или бюджета. Кандидаты, построенные до предыдущего объединения, перепроверяются: их стоимость могла измениться.


## 9. Инженерная проверка: расходы, диаметры, геометрия

### 9.1. Порядок расчёта одного кандидата

**[ТА, §3–8; Решение по организации расчёта]**

1. Проверить физические узлы, связность подключённых ОКС и отсутствие циклов.
2. Уточнить привязки врезок и число примыканий камер.
3. Ориентировать новые ветви от потребителей к единственной врезке каждой компоненты.
4. Посчитать расходы снизу вверх.
5. Подготовить назначения диаметров через `DiameterPlanner`; в evaluator независимо проверить их достаточность, предельные длины и допустимые повышения.
6. Определить реконструкцию старых участков и размеры примыкающих камер.
7. Проверить габариты новых маршрутов, отступы, углы и спецпроходы для полученных диаметров.
8. В дополнительном режиме построить и проверить профиль глубины.
9. Разделить линии на расчётные участки с постоянными параметрами.
10. Посчитать все категории стоимости, штрафы, длины и S.

На ранних этапах можно быстро отбрасывать очевидно недопустимые кандидаты, но финальный порядок зависимостей сохраняется: сначала расход/диаметр, потом окончательная проверка габарита.

### 9.2. Расход

**[ТА, §3]** Для новой ветви:

```text
flow(edge) = сумма flow_tph всех ОКС,
             путь которых к врезке проходит через edge
```

Подачу и обратку не складываем. `heat_load` — справочная нагрузка; для расхода используем `flow_tph`, не придумываем пересчёт нагрузки в расход. [ТА, §2.2]

**[Решение]** Обход дерева делать итеративно, чтобы глубокая сеть не переполнила стек. У каждого узла хранить сумму дочерних потоков и собственный спрос. Технический узел спроса не добавляет.

ОКС, исключённый из варианта, не должен продолжать увеличивать расходы на старых общих участках. После удаления/возврата ОКС пересчитываются все зависимые ветви до источника.

### 9.3. Диаметр

**[ТА, §3 и таблица 4.1]** Выбираем первый диаметр из каталога, у которого пропускная способность не меньше расхода. При превышении максимальной пропускной способности каталога кандидат не может быть принят без изменения группировки подключений.

Пример: 12 т/ч требует минимум ДУ80 с пропускной способностью 13,2 т/ч; ДУ65 с 8,3 т/ч недостаточен.

### 9.4. Предельная длина

**[ТА, §3]** Проверяется непрерывная часть сети одного диаметра. Камера без смены диаметра отсчёт не обнуляет; смена диаметра начинает новый отсчёт.

**[РГ, §4 и §8, шаг 7]** Записано, что при ветвлении без смены диаметра протяжённость суммируется по номенклатуре, а при превышении можно повысить диаметр на одну позицию каталога.

**[Решение; Уточнить Q03]** Для MVP формализуем это как сумму длин рёбер каждой **связной компоненты одного диаметра** в новой сети. Несвязанные части одинакового диаметра не складываются. Новые технические узлы и разбиение на `base/special` сами по себе не создают новый отсчёт. Правило необходимо подтвердить у организаторов: обычная проверка длины отдельного пути дала бы другой результат.

Повышение ограничиваем относительно минимума по расходу текущей ветви: разрешены `Dmin` и следующая позиция. Нельзя повышать ещё на одну позицию на каждой итерации и незаметно получить многоступенчатое увеличение.

### 9.5. Конкретный подбор с учётом длины

**[Решение]** Этот подбор выполняется в `DiameterPlanner`, вызываемом материализатором. Evaluator получает выбранные диаметры и независимо проверяет их, а не меняет конструкцию. На неизменной топологии сначала назначаем всем логическим ветвям `Dmin`. Если ограничение длины нарушено, выполняем ограниченный поиск вариантов повышения:

```text
assignDiameters(tree, catalog, budget):
    base = minimumDiametersByFlow(tree)
    queue = [base]
    seen = {}
    bestFeasible = NONE

    while queue not empty and budget available:
        assignment = popMostPromising(queue)
        if assignment in seen: continue
        seen.add(assignment)
        components = connectedSameDiameterComponents(tree, assignment)
        bad = components violating maxLength

        if bad is empty:
            rememberByConstructionEstimate(assignment)
            continue

        component = chooseBadComponent(bad)
        for branch in component that is still at base diameter:
            if nextCatalogDiameter(branch) exists:
                queue.add(assignment with that branch promoted once)

    return bestFeasible or DIAMETER_SEARCH_INCOMPLETE
```

В MVP логическая ветвь между физическими узлами имеет один назначенный диаметр. Не режем её произвольно на миллиметровые куски для искусственного сброса длины. Разрешение дополнительных осмысленных точек смены диаметра — возможное расширение пространства поиска.

Это ограниченный поиск, не доказательство несуществования другого распределения диаметров. Если бюджет исчерпан, верхний solver может разделить группу, изменить врезку или геометрию. Недопустимый диаметр никогда не экспортируется как допустимый из-за таймаута.

### 9.6. Цикл «диаметр изменился — маршрут устарел»

**[Решение]** `EngineeringEvaluator` не двигает трубы тайно. Он возвращает `REQUIRES_REROUTE` с перечнем конфликтов. `CandidateMaterializer` перестраивает нужные ветви и вызывает расчёт заново.

```text
materializeAndEvaluate(draft, budget):
    current = normalizePhysicalNodesAndTieIns(draft)
    flows = calculateFlows(current)
    assignment = diameterPlanner.assignCandidate(current, flows, current.lengths, budget)
    if assignment.failed:
        return assignment.failure
    current = withDiameters(current, assignment)
    signatures = {}

    for pass in 1..repairPassLimit:
        result = evaluator.evaluate(current)
        if result.valid:
            return result
        if result.notRepairable:
            return result
        if signature(current, result) in signatures:
            return SEARCH_INCOMPLETE("повтор состояния ремонта")
        signatures.add(signature(current, result))

        current = repairGeometryOrAssignment(current, result.violations)
        if repair failed:
            return failure

    return SEARCH_INCOMPLETE("исчерпан бюджет ремонта")
```

В частности, после увеличения ДУ400 до ДУ500 отступ от здания меняется с 5 до 7 м. Старый маршрут может стать недопустимым, хотя его центральная линия не сдвинулась. Удлинение нового маршрута может снова изменить проверку предельной длины. [ТА, §5.1; Решение]

Успех означает согласованный результат **всех** проверок. Неуспех после четырёх проходов — ограничение поиска, не повод сохранить последнюю недопустимую линию.

### 9.7. Камеры

**[ТА, §3 и §8.2]** Камера обязательна на каждой развилке. Её диаметр — максимум диаметров всех итоговых примыкающих участков. Для существующей камеры, использованной под врезку, сравниваем этот максимум с её исходным `diameter`.

Если максимум вырос, стоимость реконструкции камеры берём по шкале для итогового диаметра, а не как разницу двух цен. Существующую камеру учитываем один раз независимо от числа врезок. Старые камеры, не используемые для врезки, отдельно не реконструируем и не оплачиваем. [ТА, §8.2]

Технический узел — не камера. Изменение коэффициента или диаметра без развилки не должно добавлять 3–12 млн рублей за несуществующую камеру.

### 9.8. Дополнительный режим глубины

**[ТА, §4.3 и §6]** Это отдельный режим после работающего 2D:

```text
условная поверхность горизонтальна
обычная глубина до верха габарита = 3,0 м
минимальная глубина = 0,7 м
|изменение глубины| / горизонтальная длина ≤ 0,10
Kгл(h) = 1, если h ≤ 3
Kгл(h) = 1 + 0,10 × (h − 3), если h > 3
```

Для коммуникации с верхом на глубине `h_old`, высотой `H_old`, новой высотой `H_new` и требуемым просветом `g` проверяются два случая:

```text
выше: h_new + H_new + g ≤ h_old
ниже: h_new ≥ h_old + H_old + g
```

Это следствие проверки просветов между внешними габаритами, а не между осями. Для газопровода `g = 0,2 м`, для кабеля и старой теплосети `g = 0,5 м`. Под дорогой верх новой сети не выше глубины 1,0 м, под трамваем — 1,2 м. [ТА, §5.1]

**[Решение]** После 2D-маршрута генерировать варианты «над/под», соединять их подъёмами/спусками нужной длины и проверять весь профиль. Для линейных коммуникаций постоянная глубина сохраняется по 2 м с каждой стороны пересечения. Изменение на 1 м требует минимум 10 м горизонтального подхода. Нельзя заменить профиль одной глубокой точкой.

Для близких переходов совместно подбирать профиль; если не получается, возвращаться к выбору коридора. Критерий объединения переходов и длина расчётного наклонного участка требуют уточнения (§20). При пересечении глубины 3 м добавляется технический узел; средний коэффициент подъёма/спуска считается отдельно по частям. [ТА, §6.1]

В 2D-выходе `depth_start` и `depth_end` равны `null`. Не записывать глубину как положительную Z-координату EPSG:4326: глубина от условной поверхности не является геодезической высотой.

## 10. Как считать реконструкцию существующей сети

### 10.1. Передача расхода до источника

**[ТА, §7]** Для каждой врезки известен суммарный новый расход, пришедший из её ветвей. Дальше он распространяется по `upstream_object_id` до источника.

В каждом затронутом старом участке:

```text
G_total = G_existing + сумма всех добавленных расходов через эту часть
D_required = минимальный диаметр, пропускающий G_total
```

Если `D_required ≤ D_existing`, реконструкции нет. Если больше — реконструируем соответствующую часть до `D_required`. Ни стоимость исходного строительства, ни старая длина сами по себе в цену варианта не включаются.

### 10.2. Врезка внутри линии

Для трубы длиной `L`, ориентированной от источника, врезка на станции `s_tie` добавляет расход только на интервал `[0, s_tie]`. На части `[s_tie, L]` этот расход не появляется. У всех последующих по направлению к источнику труб затрагивается весь проходимый участок. [ТА, §7]

Если входные связи подразумевают нестандартное соединение в середине старой линии, сначала оно должно быть однозначно нормализовано во внутренние участки с сохранением исходного ID. Нельзя автоматически считать всё ребро целиком, если геометрическая связь говорит об ином.

### 10.3. Несколько врезок в одну трубу

**[Решение]** Не запускать независимый расчёт стоимости для каждой врезки с последующим суммированием: общая часть будет оплачена несколько раз.

Сначала накопить интервалы добавленного расхода, затем разбить старую линию по всем их границам. Для каждого элементарного интервала сложить активные расходы, выбрать один итоговый диаметр и посчитать одну стоимость.

```text
collectReconstruction(solution, existing):
    additions = map: existingPipeId → list of {from, to, addedFlow}

    for port in allTieInPorts(solution):
        G = flowThroughPort(port)
        if port.host is pipe:
            additions[port.pipe].add(0, port.station, G)
            next = upstream(port.pipe)
        else:
            next = upstream(port.chamber)

        while next is not source:
            if next is pipe:
                additions[next.id].add(0, next.length, G)
            next = upstream(next)

    result = []
    for pipeId, intervals in additions:
        for atomicInterval in splitAtAllIntervalBoundaries(intervals):
            G_added = sumFlowsCovering(atomicInterval)
            G_total = existing[pipeId].flow + G_added
            D = minimumDiameterForFlow(G_total)
            if D > existing[pipeId].diameter:
                result += extractActualGeometryAndPrice(pipeId, atomicInterval, D)

    return result
```

Для производительности накопление на общих предках затем можно заменить обратным обходом существующего дерева. Сначала реализуется прозрачная версия и проверяется на маленьких примерах; оптимизированная должна давать тот же результат.

### 10.4. Числовой пример частичной реконструкции

Пусть старая труба имеет длину 200 м, ДУ100 и расход 20 т/ч. Станции считаются от источника. Добавляем 20 т/ч на станции 40 м и 5 т/ч на станции 100 м.

| Часть старой трубы | Добавленный расход | Итоговый расход | Требуемый диаметр | Решение |
| --- | --- | --- | --- | --- |
| 0–40 м | 25 т/ч | 45 т/ч | ДУ150 | Реконструировать 40 м |
| 40–100 м | 5 т/ч | 25 т/ч | ДУ125 | Реконструировать 60 м |
| 100–200 м | 0 | 20 т/ч | ДУ100 | Не реконструировать |

По таблице 4.1:

```text
C_reconstruction = 40 × 152_295 + 60 × 148_030
                 = 14_973_600 руб.
L_reconstruction = 100 м
```

Это контроль арифметики **только реконструкции трубы**, без новых труб, врезок и камер. [Расчёт по ТА, §4.1 и §7]

### 10.5. Геометрия, коэффициенты, камеры

**[ТА, §7]** Выход содержит извлечённую часть исходной LineString, без изменения её трассы. К реконструкции труб не применяются Kспец и Kгл.

**[Решение]** Соседние части одного исходного объекта объединять только при совпадении итогового диаметра, добавленного расхода и остальных выходных параметров. Разные значения `added_flow_tph` нельзя спрятать в один участок с усреднённым расходом.

После интервального расчёта обновить диаметры у концов, примыкающих к использованным камерам, и один раз вычислить реконструкцию каждой такой камеры. Частичное расширение трубы на другом её конце не должно автоматически увеличивать все камеры этой трубы.

**[Уточнить Q09; консервативное решение]** При пространственной проверке новой сети рядом с реконструируемой старой частью использовать итоговый габарит старой трубы. Приложение не разъясняет отдельно, какой габарит применять к таким совместным изменениям; это правило следует согласовать.

## 11. Полная стоимость и контрольные примеры

### 11.1. Новые участки

**[ТА, §8.1]**

```text
C_segment = length × newPrice(D) × Kгл × Kспец
```

Для обычного участка `Kспец = 1`, для 2D `Kгл = 1`. На линии меняется диаметр, способ или коэффициент — появляется граница расчётного участка.

### 11.2. Камеры и врезки

**[ТА, §8.2]**

| Максимальный примыкающий диаметр | Новая камера или реконструкция используемой старой камеры |
| --- | --- |
| ДУ50–200 | 3 000 000 руб. |
| ДУ250–500 | 5 000 000 руб. |
| ДУ600–1000 | 8 000 000 руб. |
| ДУ1200–1400 | 12 000 000 руб. |

Каждая независимая врезка — 5 000 000 руб. Это отдельная стоимость, не включённая автоматически в стоимость камеры.

### 11.3. Неподключённые

**[ТА, §8.3]** Для каждого неподключённого ОКС:

```text
penalty(oks) = 100_000_000 + 500_000 × oks.flow_tph
```

Штраф суммируется с прочей стоимостью **до** вычисления S. Считаем по ОКС, не по количеству временных ветвей или попыток маршрута.

### 11.4. Сборка итогов

```text
C = construction_cost
  + chamber_construction_cost
  + tie_in_cost
  + reconstruction_cost
  + chamber_reconstruction_cost
  + unconnected_penalty

L = new_network_length + reconstruction_length
S = 0.7 × C / 25_000_000 + 0.3 × L / 100
```

Считать линейные работы по уникальным физическим участкам. Не дублировать общий участок для каждого ОКС, который через него питается.

### 11.5. Контрольный пример одного подключения

Условие теста: один ОКС 3 т/ч, новая обычная линия длиной 100 м, врезка в существующую камеру ДУ100 со свободным портом; старый путь имеет достаточную пропускную способность, реконструкции и спецпроходов нет.

```text
новый диаметр       = ДУ50
новое строительство = 100 × 74_023 = 7_402_300 руб.
врезка              = 5_000_000 руб.
новая камера        = 0
реконструкция       = 0
C                   = 12_402_300 руб.
L                   = 100 м
S                   = 0.6472644
```

Если заменить врезку на точку внутри подходящей старой трубы без близкой камеры, и максимальный диаметр примыкания остаётся в диапазоне ДУ50–200, добавится новая камера за 3 млн. Тогда `C = 15_402_300`, `S = 0.7312644`. Оба примера — арифметические тесты при указанных условиях, а не универсальная цена подключения. [Расчёт по ТА, §4.1, §8–9]

## 12. Roadmap: локальные операции, LNS и ALNS

### 12.1. Только после приёмки baseline

**[Решение]** В первом MVP этот раздел **не реализуется и не выполняется**. Первый результат получается через `InitialSolutionBuilder` и evaluator без внешнего цикла перестройки.

После отдельных этапов объединений и простого локального поиска кандидат на дальнейшее развитие — LNS: удалить часть новой сети и восстановить её иначе. Сначала использовать фиксированные вероятности операторов и принятие только улучшений; после проверки можно добавить имитацию отжига и адаптацию. Это roadmap, а не обязательство первого спринта.

Разделение на стартовое решение, destroy/repair, критерий принятия и обновление выбора операторов соответствует структуре ALNS, но конкретные операции теплосети проектируем сами. Готовый пример маршрутизации автомобилей не решает наш кейс без этих модулей. [M3–M4]

### 12.2. Операторы изменения

| Операция | Что меняем | Что обязательно пересчитать |
| --- | --- | --- |
| `CHANGE_TIE_IN` | Переподключаем компоненту к другой врезке | Путь, порты камер, реконструкцию до источника |
| `MERGE` | Делаем общую магистраль | Сумму расходов, диаметры, новую развилку, исчезнувшие врезки |
| `SPLIT` | Разделяем общую компоненту | Новые точки подключения, камеры, все суммы |
| `MOVE_BRANCH_POINT` | Переносим камеру | Все примыкающие маршруты и их ограничения |
| `REROUTE` | Меняем коридор одной ветви | Геометрию, длину, специальные участки, проверку диаметра |
| `PRUNE_AND_REGRAFT` | Отделяем поддерево и присоединяем в другом месте | Связность, отсутствие циклов, все затронутые потоки |
| `EDGE_EXCHANGE` | Добавляем связь и удаляем другую из возникшего цикла | Топологию и полный инженерный расчёт |
| `DISCONNECT/RECONNECT` | Меняем набор подключённых ОКС | Штрафы, ненужные ветви, общие расходы |

### 12.3. Ограничение `EDGE_EXCHANGE`

**[Решение]** Операция «добавить ребро — удалить ребро цикла» сохраняет дерево только при правильных исходных условиях: добавляем ребро между узлами одного дерева, после чего удаляем другое ребро **именно возникшего цикла**.

Если соединены два разных дерева новой сети, цикла внутри нового леса может не быть. В таком случае используем явное отсечение старой привязки и переподключение, а не «ищем любой цикл». Старые трубы и связи к источнику не удаляются ради улучшения S.

Даже корректная операция над деревом не гарантирует допустимость проекта: может появиться камера степени 5, запрещённое пересечение или слишком толстая магистраль. После неё обязательна полная проверка.

### 12.4. Destroy: что именно удалить

**[Решение]** Начальный набор:

- случайно выбрать несколько ОКС и убрать их эксклюзивные пути;
- выбрать географически близкую группу ОКС;
- выбрать компоненту с дорогой врезкой/реконструкцией;
- выбрать неудачный переход или участок общей магистрали.

Удаление выполняется по назначениям потребителей. Сохраняем объединение путей ОКС, которые остаются подключёнными. Если удалили общий участок и потеряли связь нескольких потребителей, все они входят в `unassigned`, даже если исходно хотели изменить одного.

После удаления убираем ветви без потребителей и необязательные пустые новые камеры. Существующие объекты не удаляем. Сохранённая геометрия может остаться на месте, но расходы и реконструкция на ней всё равно пересчитываются.

### 12.5. Repair: как восстановить

**[Решение]** Для каждого неназначенного ОКС/поддерева предлагаем:

1. независимую врезку;
2. присоединение к существующей новой камере с местом;
3. присоединение к точке новой ветви с созданием камеры;
4. совместное подключение небольшой группы;
5. оставить неподключённым со штрафом.

Для каждого предлагаемого действия строим геометрию и оцениваем полное изменение S. Ограничиваем число вариантов предварительным ранжированием, но не подменяем окончательный расчёт суммой прямых расстояний.

Первый repair — жадный: выбираем минимальный S среди проверенных вставок. Второй — «сначала трудные»: для каждого ОКС смотрим разницу между лучшей и второй лучшей вставкой и сначала вставляем тот, которому потерять хороший вариант дороже. Это эвристика regret-2, а не дополнительное правило ТЗ.

```text
repair(partial, budget):
    while partial.unassigned not empty and budget available:
        proposals = buildInsertionOptions(partial)
        oks = chooseNextDemand(proposals)
        option = bestFullyEvaluatedOptionFor(oks)
        apply(option)

    markRemainingAsUnconnectedWithPenalty(partial)
    return materializeAndEvaluate(partial, budget)
```

Законченный вариант с неподключёнными допустим, если остальные правила соблюдены. Но список `unassigned` не должен утечь в экспорт как забытые ОКС без штрафа.

### 12.6. Принимать или отклонять

Для минимизации S:

```text
delta = S(candidate) − S(current)
если delta ≤ 0: принять
иначе: принять с вероятностью exp(−delta / T)
```

`T` — температура поиска, а не температура теплоносителя. Недопустимые кандидаты отвергаются **до** этой формулы. Лучший найденный вариант хранится отдельно от текущего: временное ухудшение не должно потерять лучший результат. [M5; Решение]

**[Решение]** Начальную T настроить по пробным положительным изменениям S на валидационных задачах, например так, чтобы типичное ухудшение принималось с вероятностью 0,2. При отсутствии подходящих наблюдений оставить жадное принятие. Точное охлаждение — параметр эксперимента, не инженерная константа.

### 12.7. Адаптация операторов без нейросети

**[Решение]** Для совместимых пар destroy/repair хранить положительные веса, начально одинаковые. Пример награды паре: 5 за новый лучший результат, 2 за улучшение текущего, 0,5 за принятый неулучшающий, 0 за отказ. Это внутренние награды настройки, не официальный S.

После блока, например 50 попыток:

```text
weight = max(weight_min,
             (1 − eta) × weight + eta × averageOperatorReward)
```

Выбирать пару пропорционально весу; оставить ненулевую вероятность исследования. Редко используемые операторы без наблюдений не объявлять бесполезными. Значения наград, `eta` и размер блока подбираются на валидации. Это уже ALNS-подобная адаптация, но ещё не обучение нейросети. [M3; Решение]

### 12.8. Главный цикл оптимизации

```text
optimize(initialSolutions, budget):
    archive = new VariantArchive()
    archive.addAllValid(initialSolutions)
    current = chooseInitial(initialSolutions)
    best = archive.best

    while budget.canStartIteration():
        pair = selectDestroyRepair(current)
        partial = pair.destroy(copy(current.solution))
        draft = pair.repair(partial, remainingBudget)
        candidate = materializeAndEvaluate(draft, budget)

        if not candidate.valid:
            logRejection(candidate)
            updateOperatorStats(pair, failure)
            continue

        archive.consider(candidate)  # Включая кандидаты, не принятые в current.
        improvedBest = candidate.score < best.score
        if improvedBest:
            best = candidate
        accepted = acceptance(current, candidate, temperature)
        updateOperatorStats(pair, outcome(improvedBest, accepted))
        if accepted:
            current = candidate

        if stagnationLimitReached:
            current = restartFromDifferentArchivedVariantOrBaseline()

    return archive
```

Простой локальный поиск сначала проверяет единичные изменения; LNS добавляет возможность перестроить несколько ветвей сразу. Не требуется одновременно внедрять MCTS, генетический алгоритм, полный MILP и RL.


## 13. Как получить действительно разные варианты

### 13.1. Требование и наше расширение

**Первый MVP возвращает один проверенный вариант.** Архив разнообразия и подбор нескольких схем в этом разделе реализуются позже; не нужно дублировать единственную схему ради трёх записей.

**[ТА, §9–10]** Разрешено вернуть **до трёх** вариантов с ранжированием по S. Формальной меры «насколько они должны различаться» приложение не задаёт.

**[Решение в ответ на требование проекта]** Храним разнообразный архив. Один валидный вариант лучше трёх копий с чуть сдвинутыми координатами. Всегда сохраняем лучший найденный по S, даже если он похож на другой.

### 13.2. Признаки содержательной разницы

Для кандидата сохраняем:

```text
connectedSet: какие ОКС подключены
rootAssignments: группа ОКС → существующий hostId и место врезки
branchingSignature: какие группы имеют общие ветви/камеры
corridorGeometry: физическая геометрия новых линий
```

Разные ID технических узлов, направление обхода LineString и количество промежуточных точек не делают проект другим. Одного изменения диаметра без изменения связей/коридора для отдельного варианта в MVP недостаточно.

### 13.3. Дедупликация

**[Решение]** Сначала канонизировать:

1. Свернуть служебные узлы степени 2 для сравнения топологии, сохранив физические камеры и врезки.
2. Сортировать ID потребителей и группы общих ветвей независимо от порядка обхода.
3. Представлять врезку как существующую камеру либо пару `(existingPipeId, station)`.
4. Строить геометрическую подпись на фиксированной сравнительной сетке, например 2 м. Координаты проектной линии при этом **не меняются**.
5. Хэш использовать как ускоритель. Спорные совпадения проверять по структуре и реальной геометрии.

Если два варианта практически одинаковы, оставляем вариант с меньшим истинным S.

### 13.4. Геометрическое отличие

**[Решение]** Для двух объединений новых линий `A` и `B` вычисляем долю длины, не покрытую небольшим буфером другого варианта:

```text
d_geo = (length(A outside buffer(B, r))
       + length(B outside buffer(A, r)))
      / max(length(A) + length(B), smallPositiveValue)
```

Стартово `r = 2 м`, заметная разница — `d_geo ≥ 0,10`. Эти числа предназначены **только для сравнения вариантов**, не для допуска нарушений расстояний.

Разные существующие камеры — разные врезки. Для одной старой трубы начально считаем сдвиг станции хотя бы на 10 м значимым; меньший сдвиг может всё равно дать другой коридор или другую группировку. Это также не нормативное правило 10 м из §8.2, а отдельный параметр архива.

### 13.5. Источники разнообразия

Получаем варианты через разные порядки baseline, разные кандидаты врезки, обходы по разным сторонам препятствий, разные группировки ОКС и перезапуски LNS с другими seed.

Архив можно ограничить, например, 30 представителями разных решений. Перед экспортом:

```text
selected = [лучший по S]
for candidate in archive sorted by S:
    if meaningfullyDifferentFromAll(candidate, selected):
        if passesOptionalQualityWindow(candidate):
            selected.add(candidate)
    if len(selected) == 3: break
```

Окно качества, например не хуже лучшего более чем на 25%, — отключаемая продуктовая настройка. ТЗ не требует такого процента. Если различимых хороших вариантов меньше трёх, экспортируем один или два. После отбора присваиваем `rank` снова по истинному S; разнообразие не входит в формулу ранжирования.

## 14. Как сформировать выходной GeoJSON

### 14.1. Контракт

**[ТА, §10]** Один `FeatureCollection` в EPSG:4326. Все варианты в одном `features`, различаются `variant_id`. Каждому варианту соответствует ровно один `variant_summary` с `geometry = null`.

Выходные категории:

| `object_type` | Геометрия | Когда создаём |
| --- | --- | --- |
| `heat_network` | LineString | Для каждой рассчитанной новой части |
| `tie_in` | Point | Для каждой независимой врезки |
| `heat_network_reconstruction` | LineString | Только для действительно реконструируемой части старой трубы |
| `heat_chamber` | Point | Для новых камер |
| `heat_chamber_reconstruction` | Point | Для реконструкции старой камеры, используемой под врезку |
| `technical_node` | Point | Для изменения параметров, если там нет камеры/врезки |
| `variant_summary` | null | Одна запись итогов на вариант |

Это поддерживаемые типы, а не требование создать фиктивный объект каждого типа в любом варианте. Если реконструкция не нужна, соответствующих features нет, а её суммарная стоимость равна нулю.

Точки подключения перспективных ОКС повторно не выводим. При этом `start_node_id`/`end_node_id` новой линии могут ссылаться на входную точку подключения. Проверять ссылки нужно по входу **и** выходу, не только внутри результата. [ТА, §10 и §10.1]

### 14.2. Где разбивать новую линию

Разбивать в точках:

- врезки, развилки и существующей границы логической ветви;
- изменения диаметра;
- перехода `base ↔ special` или изменения Kспец;
- в режиме глубины — границ подъёма/спуска и постоянной глубины, а также пересечения глубины 3 м.

Изгиб LineString без изменения параметров сам по себе не требует камеры или технического узла. Лишние точки координат не считаются отдельными трубами.

**[ТА, §3 и §8.1]** В месте изменения параметров без камеры/врезки создаётся `technical_node`. Разбиение на участки не должно сбрасывать проверку предельной длины одинакового диаметра.

### 14.3. Одна точка, несколько ролей

Новая камера и врезка могут физически совпадать. Для них нужны разные выходные сущности и разные категории стоимости, но не два физических узла, соединённых нулевой трубой.

**[Решение; Уточнить Q06]** Во внутренней модели есть один `physicalNodeId` и его роли. В выходе создаём нужные `tie_in` и `heat_chamber` с совпадающими координатами; конец новой ветви ссылается на роль `tie_in`. Для других развилок используется ID камеры, для чистых изменений параметров — ID технического узла. Согласовать это с валидатором организаторов: приложение перечисляет сущности, но отдельно схему совпадающих ролей не поясняет.

Если несколько независимых врезок используют одну старую камеру, физическая камера одна, записи врезок и их цена — по числу независимых подключений. Реконструкция этой камеры выводится максимум один раз на вариант.

### 14.4. Поля и идентификаторы

**[ТА, §10]** У каждого типа — только собственный обязательный набор полей; нельзя добавлять чужие поля с `null`. Полный перечень дословных технических имён приведён в приложении B этого документа.

Исключения, где `null` прямо нужен: `geometry` у `variant_summary`, `depth_start`/`depth_end` у нового участка в 2D.

**[Решение]** Выходные ID делать уникальными во всём файле, например `v01_network_0001`. Ссылки на исходные объекты оставлять с исходными ID. Не перезаписывать старый `heat_network` новой линией под тем же ID. `variant_id` хранится строкой.

В диагностике можно хранить `rulesVersion`, seed, причины неподключения, подписи коридоров, шаг сетки и сведения о бюджете. Не добавлять их в обязательные GeoJSON-сущности, пока не согласовано расширение схемы.

### 14.5. Числа и согласованность

**[Решение]** Полный внутренний расчёт ведётся без промежуточного округления. При записи выбрать единый профиль точности, например длины до 6 знаков после запятой, стоимости до копеек, координаты с достаточным числом знаков для согласованного геометрического допуска.

Суммы в `variant_summary` формировать из тех значений, которые реально записаны в features. Затем пересчитать `calculated_cost`, `length` и `score` по выходным суммам. Перед присвоением `rank` повторно отсортировать подготовленные сводки по записываемому `score`, чтобы округление не нарушило порядок почти равных вариантов. Установить и протестировать допустимую погрешность между длиной записанной геометрии и `length`; точный допуск организаторы не задали.

Не округлять входной расход вниз перед выбором диаметра. Не исправлять фактическое расстояние 4,999 м до 5 м так, чтобы нарушение исчезло: применять согласованный численный допуск или строить с безопасным запасом. Пример округления из рабочего гайда не заменяет определённой политики точности. [РГ, §4; Уточнить Q07]

### 14.6. Псевдокод экспортера

```text
export(problem, selectedVariants, targetFile):
    prepared = []
    for variant in selectedVariants:
        evaluation = fullReevaluation(variant)
        require evaluation.valid
        prepared += prepareSerializedNumbersAndRecomputeSummary(evaluation)
    writer = openTemporaryFeatureCollection()

    for rank, evaluation in enumerate(sortByFinalSerializedScore(prepared), start = 1):
        ids = assignStableUniqueIds(evaluation, variantId(rank))

        writeFeatures(newSegments(evaluation, ids))
        writeFeatures(tieIns(evaluation, ids))
        writeFeatures(reconstructedSegments(evaluation, ids))
        writeFeatures(newChambers(evaluation, ids))
        writeFeatures(reconstructedChambers(evaluation, ids))
        writeFeatures(technicalNodes(evaluation, ids))
        writeFeature(summaryFromWrittenValues(evaluation, ids, rank))

    closeCollection(writer)
    validation = validateInputAndOutputTogether(problem, writer.file)
    if validation.failed:
        return errorWithoutPublishingPartialResult(validation)
    atomicRename(writer.file, targetFile)
```

### 14.7. Проверка выхода

Отдельный валидатор проверяет уникальные ID, типы/обязательные поля, координаты, все ссылки, расходы, камеру в каждой развилке, допустимость диаметров/длин, спецучастки, интервальную реконструкцию, штрафы, суммы, S и порядок `rank`.

Желательно не использовать для всех проверок буквально тот же код, что строит результат: иначе одна ошибка повторится и в построении, и в самопроверке. Каталоги параметров могут быть общими, а контрольные арифметические примеры и простые проверки — независимыми.

## 15. Интерфейсы и главный алгоритм сервиса

### 15.1. Контракты методов

`DestroyOperator`, `RepairOperator`, `AcceptanceCriterion` и `VariantArchive` — интерфейсы roadmap. В профиле `baseline` они не вызываются и не требуются для сборки первого решения.

Это псевдоинтерфейсы для переноса в Java 11. Они не являются уже созданным API или компилируемым исходным кодом. Неизменяемый `problem` и настройки доступны модулям через контекст; в кратких внутренних вызовах они могут быть опущены. Общий бюджет передаётся явно и учитывается во вложенных операциях.

```text

ExistingTopologyBuilder.build(problem) -> ExistingNetwork | TopologyErrors
TieInFinder.find(anchor, solution, limits) -> TieInCandidates

SpecialPassBuilder.split(route, restrictions, rules) -> CalculatedIntervals

ReconstructionCalculator.calculate(tieInFlows, existing) -> ReconstructionPlan

GeoJsonExporter.write(validVariants, problem, stream) -> ExportReport
```

### 15.2. Главная функция с ранним завершением MVP

```text
solve(inputStream, config, targetFile):
    problem = loadAndValidate(inputStream, config.inputLimits)
    if problem.invalid:
        return INPUT_ERROR(problem.errors)

    existing = buildAndValidateExistingTopology(problem)
    if existing.invalid:
        return INPUT_ERROR(existing.errors)

    initializeRuleVersionAndCatalogs(problem)
    budget = new Budget(config)
    baselineResults = []

    # Профиль baseline: один порядок, k = 1 на кандидата врезки.
    orders = baselineOrders(problem.demands, config.search.baseline_orders,
                            config.seed)
    for order in orders:
        baseline = buildIndependentBaseline(problem, order, budget)
        if baseline.valid:
            baselineResults += baseline

    if baselineResults is empty:
        return SOLVER_ERROR("не получен даже проверенный исходный вариант")

    if config.profile == "baseline":
        best = minByActualS(baselineResults)
        verified = fullRevalidateAll([best])
        if verified is empty:
            return SOLVER_ERROR("финальная проверка baseline не пройдена")
        return export(problem, verified, targetFile)

    # Только после MVP: модули ниже не нужны профилю baseline.
    starts = baselineResults
    if config.search.merge_enabled:
        starts += improveByGreedyMerges(baselineResults, budget)
    archive = archiveOf(starts)
    if config.search.lns_enabled:
        archive = optimize(starts, budget, archive)
    selected = archive.selectDiverse(maxCount = config.archive.output_limit)
    verified = fullRevalidateAll(selected)
    if verified is empty:
        return SOLVER_ERROR("финальная проверка не пройдена")
    return export(problem, verified, targetFile)
```

**Условие выхода первого спринта:** первый `return export(...)`. Реализовывать оптимизатор ради прохождения этой ветки не требуется.

### 15.3. Важные гарантии реализации

**[Решение]** Резервировать часть общего бюджета для финального расчёта, валидации и записи. Воспроизводимые тесты ограничивать числом развёрнутых узлов/оценённых кандидатов, а не только секундомером. Для эксплуатации дополнительно установить лимит времени и памяти.

Исчерпание бюджета прекращает улучшения и сохраняет лучший уже проверенный вариант. Оно не разрешает экспорт недопустимого кандидата. Если найден только вариант с частью неподключённых ОКС, возвращать его со штрафами и отдельной честной диагностикой, а не заявлять, что все подключения физически невозможны.


## 16. Roadmap: на чём и как обучать

### 16.1. Сначала определить, что вообще обучается

**[Решение]** В первой рабочей версии не обучаем ни маршрутизатор, ни расчёт диаметров, ни стоимость. Они работают по алгоритмам и таблицам.

| Уровень | Нужно ли отдельное обучение | Что используется |
| --- | --- | --- |
| A*, проверка препятствий | Нет | Геометрия, правила, ставки |
| Расходы, диаметры, реконструкция, S | Нет | Формулы приложения |
| Обычный LNS | Нет | Заданные операторы и вероятности |
| Адаптивный выбор операторов | Может адаптироваться в ходе каждого запуска | Статистика удачных/неудачных операций |
| Предобученный выбор действий | Да, только после рабочего solver-а | Собственные журналы решений и проверенные задачи |

**GeoJSON не является набором правильных ответов.** Он описывает задачу. Для обучения нужен результат: какие действия в каких состояниях помогли уменьшить S и какие были недопустимы.

### 16.2. Сначала создать генератор задач

**[Решение]** Генератор создаёт небольшую вымышленную территорию в метрических координатах, затем переводит геометрию в EPSG:4326 для проверки настоящего входного pipeline.

Параметры генератора:

```text
sceneId, seed
размер области
число ОКС и их расположение: одиночные, группы, цепочки, разделённые зоны
расходы, в том числе рядом с порогами каталога
существующее дерево, камеры, корректные upstream-ссылки
диаметры и расходы существующей сети
запрещённые полигоны и узкие проходы
дороги, трамвай, кабели, газопроводы
намеренно сложные, но известные ограничения камер
```

Генератор обязан обеспечивать смысловую корректность, а не только валидный JSON: расход общей старой ветви согласуется с её исходными потребителями, ссылки ведут к источнику, геометрия действительно соответствует связям. Сценарии с ошибками входа создаются отдельной серией и имеют ожидаемый код ошибки.

### 16.3. Три набора синтетики

**[Решение]**

1. **Эталонные маленькие задачи:** 1–5 ОКС, небольшой заранее заданный набор коридоров. Их можно перебрать или проверить вручную. Они нужны для правильности, а не для большого обучения.
2. **Обычные задачи:** десятки ОКС, группы препятствий, несколько врезок и общие старые участки. Они нужны для подбора параметров LNS/ALNS и сбора переходов.
3. **Трудные задачи:** узкие коридоры, почти заполненные камеры, скачки диаметра, несколько наложенных переходов, большие штрафы или дорогая реконструкция. Они проверяют перенос на ситуации, которые простая эвристика обрабатывает плохо.

Стартовый объём эксперимента, а не норматив: около 30 ручных эталонов и 1 000–2 000 сгенерированных сцен. Сначала важнее разнообразие правил и воспроизводимость, чем миллион похожих карт.

### 16.4. Как использовать текущий набор и будущие большие входы

Текущий набор из 144 объектов и 17 точек подключения [НД] сначала используем целиком как интеграционный пример baseline. Само количество объектов не делает его обучающей выборкой и не подтверждает качество алгоритма на других территориях.

На этапе развития можно получать вырезки по группам ОКС, а при появлении более крупных наборов — по районам. Перед этим загрузчик проверяет детальные поля и геометрию. Каждая вырезка включает:

- нужные ОКС и их точки подключения;
- все препятствия, пересекающие окно с запасом;
- подходящие камеры и трубы;
- полные цепочки старой сети к источнику и исходные расходы.

Сохранить исходный ID, `sourceFileHash`, границы окна, список включённых объектов и причину их включения. Нельзя обрезать старый путь на границе района и считать, что реконструкция заканчивается там.

Реальные вырезки проверяют правдоподобие синтетики. Они не дают сами по себе оптимального ответа. Хороший найденный вариант называется **лучшим известным**, пока его оптимальность не доказана.

### 16.5. Как получить метки для обучения

**[Решение]** Запускать обычный проверенный solver с разными seed и операторами. В выбранном состоянии сохранить несколько альтернативных действий; каждое оценить с одной и той же исходной копии состояния и одинаковым локальным бюджетом восстановления.

Запись журнала:

```text
sceneId, split, sourceHash, rulesVersion
stateId, stateFeatures
operatorId, actionParameters, actionFeatures
valid / invalid / search_incomplete
S_before, S_after, deltaS
costBreakdown_before, costBreakdown_after
connectedOks_before, connectedOks_after
candidateGenerationBudget, evaluationsUsed, elapsedMillis
seed, solverVersion
```

`deltaS = S_after − S_before`. Для допустимого действия меньшая `deltaS` лучше. Недопустимый результат — отдельная метка, а не «очень дешёвый проект».

Для маленьких фиксированных графов получать точное лучшее значение полным перебором допустимых вариантов. Для средних — более длительным поиском несколькими методами. В журнале хранить `referenceType = exact_on_candidate_graph | best_known | manual`, не смешивать их.

### 16.6. Не допустить утечки между обучением и тестом

**[Решение]** Делить данные на обучение/валидацию/тест **до** создания переходов, вариаций и аугментаций. Начальная пропорция может быть 70/15/15, но это лишь настройка эксперимента.

Все состояния одного эпизода и все изменённые версии одной базовой сцены остаются в одной части. Нельзя обучаться на карте, а проверять качество на её копии со сдвинутыми координатами.

Реальные районы разделять с пространственным запасом, по возможности также по питающим ветвям. Если у районов общий старый источник/магистраль, это явно фиксировать: такие задачи не полностью независимы. Самый строгий тест переноса — другой район/исходная сцена, отсутствовавшие при подборе.

Тестовую часть не использовать для выбора шага сетки, числа кандидатов, температуры, операторов, весов модели или порогов разнообразия. Для этого есть валидация. Адаптация ALNS внутри нового тестового запуска допустима как часть заявленного алгоритма; начальные веса и настройки должны быть одинаково зафиксированы для сравнения.

### 16.7. Первая обучаемая модель — проще нейросети

**[Решение]** Начать с линейной модели ранжирования действий. Она предсказывает, какие предложения первыми отправить на дорогой полный расчёт.

Признаки, доступные **до** полного расчёта:

```text
тип операции
число перемещаемых ОКС и сумма их расходов
приблизительная длина новых/удаляемых коридоров
число потенциальных камер и врезок
предварительный запас пропускной способности старого пути
число и типы ожидаемых спецпересечений
есть ли риск перехода в следующую группу диаметров
число оставшихся кандидатов врезки
локальная плотность препятствий
```

Нельзя включать в признаки уже вычисленный `S_after`, затем заявлять, что модель предсказала его без расчёта. Признаки и метки — разные данные.

Простейший обучающий процесс:

1. На train-сценах собрать пары действий из одного состояния: более и менее полезное по полному расчёту.
2. Нормировать числовые признаки статистиками только train.
3. Обучить веса функции `priority(action) = weights · features(action)` так, чтобы полезное действие получало больший приоритет. Например, использовать парную логистическую функцию потерь.
4. На validation выбрать признаки и регуляризацию.
5. Сохранить веса, нормировку, версию признаков и правил в небольшой локальный файл.
6. В Java рассчитывать скалярное произведение, брать несколько лучших предложений и всё равно проверять их обычным evaluator.

Это собственный план реализации, не требование ТЗ. Модель обучается предпочитать хорошие **предложения**, а не гарантирует глобально лучший проект.

### 16.8. Где остаётся исследование новых решений

Не отдавать модели абсолютный контроль. Сохранить долю случайных/эвристических предложений, например 10%, и механизмы LNS/отжига. Иначе модель, обученная на немедленных улучшениях, может систематически отбрасывать шаги, полезные только через несколько перестроек.

При неизвестной версии признаков, ошибке модели, слишком большом числе отклонённых предложений или отсутствии выигрыша использовать обычный ALNS. Итоговый запуск должен оставаться офлайн. Возможность отдельного Python-обучения при требовании «всё решение на Java 11» нужно согласовать; первая линейная модель и её обучение могут быть реализованы без отдельного Python-ядра. [РГ, §4; Решение]

### 16.9. Как доказать, что обучение вообще полезно

Сравнить на одной закрытой тестовой выборке:

```text
A: baseline + фиксированный LNS
B: baseline + адаптивный выбор операторов
C: тот же алгоритм + обученное ранжирование
```

У всех одинаковые исходные решения, правила, каталоги, бюджет и набор seed. Отдельно сравнить при одинаковом количестве полных оценок и при одинаковом времени, включая время самой модели. Улучшение только скорости вызова модели без улучшения конечного S не доказывает полезность для пользователя.

Нужны не только средние значения: доля недопустимых выходов, худшие случаи, доля подключённых ОКС, качество альтернатив и стабильность по seed. Если C не лучше B на новых сценах, нейросеть не является обязательной следующей ступенью — оставляем более простой метод.

## 17. На чём и как тестировать

**Приоритет первого MVP:** ручные проверки обязательных 2D-правил и интеграционный запуск на текущем наборе [НД]. Отчёт загрузчика должен сопоставить фактическую статистику с контрольными `144 / 17 / 29 / 9 / 88 / 1`; при другой версии файла не подгонять статистику под ожидание. Все 17 точек должны быть учтены, а их расходы — однозначно связаны с ОКС. Запуск solver-а и его результаты ещё необходимо подтвердить тестовым отчётом.

Тесты объединений, LNS/ALNS, разнообразия, ML и глубины относятся к соответствующим последующим этапам. Они не являются условием завершения baseline, но обязательные правила расчёта и выхода упрощать нельзя.

### 17.1. Уровни проверки

**[Решение]** Разделить тесты на четыре уровня:

1. **Модульные:** отдельная формула, отступ, интервал реконструкции, поле выхода.
2. **Интеграционные:** маленький полный вход → выход → независимый валидатор.
3. **Качество поиска:** сравнение baseline, объединений, LNS/ALNS на одинаковых задачах.
4. **Нагрузка:** время, память, размер файла, число объектов, глубина старого дерева.

Проверка правильности и проверка качества оптимизации — разные вещи. Оптимизатор может вернуть законный, но дорогой вариант; это не то же самое, что незаконная дешёвая трасса.

### 17.3. Независимые эталоны

Для маршрутизатора сравнивать A* с Дейкстрой на одном зафиксированном графе. Для простых прямых переходов считать длины и цену вручную.

Для полного оптимизатора создать маленькие графы, например с 2–5 ОКС и 10–14 потенциальными рёбрами. Отдельный перебор перечисляет допустимые подграфы, наборы подключений и разрешённые назначения диаметров. Его расчёт проверяется ручными примерами. Получаем `S_exact` **на этом графе и в этой модели**, а не доказанный оптимум для всех кривых на реальной территории.

```text
gap_exact = (S_solver − S_exact) / S_exact
```

Если эталон получен лишь длительным эвристическим поиском, метрику назвать отклонением от лучшего известного результата, а не «ошибкой относительно оптимума». При `S_exact = 0` использовать абсолютную разницу, не делить на ноль.

### 17.4. Проверки неизменности смысла

**[Решение]** Дополнительно запускать преобразования, которые не должны менять инженерную оценку:

- перестановка features;
- добавление промежуточной коллинеарной точки в линию;
- обратный порядок координат старой трубы при сохранении upstream-связей;
- разбиение новой линии техническим узлом без изменения параметров.

Для синтетики допустим перенос всей сцены в метрической проекции до её преобразования в WGS84; физическая задача должна сохраняться в пределах численных допусков. При перестановке исходных объектов нужен детерминированный tie-break по ID, чтобы случайный порядок чтения не управлял baseline.

### 17.5. Метрики полного запуска

Сохраняем:

```text
валиден ли каждый опубликованный вариант
сколько ОКС и какой суммарный расход подключены
S лучшего результата и S baseline
все категории затрат
длина новой сети и реконструкции
число новых камер и независимых врезок
число действительно различных вариантов
время подготовки / маршрутизации / evaluator / поиска / экспорта
пиковая память и размер временного хранилища
число полных оценок, раскрытых узлов и попаданий в кэш
причины отказов и исчерпания бюджетов
```

Отчёт по нескольким seed показывает медиану, разброс и худший случай. Нельзя писать «качество выросло», показывая только самый удачный случай из большого числа запусков.

Проверить поэтапно: baseline → объединения → локальные изменения → LNS → адаптация → модель. Если новый компонент не улучшает качество/время на выбранных метриках, его полезность пока не подтверждена.

### 17.6. Нагрузка и 3 ГБ — отдельный этап

Это проверка возможного масштаба из рабочего гайда, **не описание текущего файла из 144 объектов**. Первый MVP фиксирует время и память на нынешнем наборе, но не заявляет обработку 3 ГБ без отдельного прогона.

Отдельно увеличивать:

1. число объектов;
2. число точек внутри одной геометрии;
3. число ОКС;
4. глубину и разветвлённость старой сети;
5. плотность препятствий и число возможных переходов.

Одинаковый размер файла может означать совершенно разную сложность. Тест на 3 ГБ, состоящий из повторов одного объекта, не проверяет реальную задачу и может быть просто невалидным из-за одинаковых ID.

До измерений не обещаем конкретное время обработки 3 ГБ. Для каждого прогона фиксируются CPU, RAM, лимиты JVM, число потоков, размер входа и количество объектов/координат. Проверяем отсутствие загрузки всего FeatureCollection в коллекцию и корректность очистки временных файлов.

### 17.7. Критерии готовности

**Правильность:** все опубликованные варианты проходят независимую проверку; все обязательные ручные и граничные тесты проходят; нет неучтённых ОКС и непосчитанных категорий стоимости.

**Первый MVP:** воспроизводимый baseline без LNS, один проверенный GeoJSON, все точки текущего набора учтены; нет зависимости от обучения, объединений или архива. Неподключённые ОКС не теряются, штрафуются и отражаются в диагностике.

**Поиск после MVP:** при сохранении одного и того же baseline результат не хуже него по S; улучшения и ограничения подтверждены отдельным сравнением. Глобальный оптимум не заявляется.

**Ресурсы:** превышение бюджета контролируемо, логируемо и не вызывает публикацию частично записанного результата.

**Обучение:** не является условием готовности MVP. Оно принимается только после отдельного выигрыша на неиспользованном тесте.

## 18. Параметры, остановка и диагностика

### 18.1. Отделить правила ТЗ от настроек поиска

Каталог диаметров, ставки, коэффициенты, правило 10 м, максимум четыре примыкания, формула штрафа и формула S — данные правил. Их нельзя подбирать под тест, чтобы улучшить метрику.

Ниже **конфигурация первого MVP**, без утверждения, что эти численные настройки оптимальны:

```yaml
profile: baseline
mode: 2d
seed: 42

input:
  storage: memory_with_limits
  record_dataset_statistics: true

tie_in:
  nearest_chambers: 8
  nearest_pipes: 12
  sample_pipe_points: false
  initial_radius_m: 250.0
  initial_candidate_limit: 32
  expanded_candidate_limit: 128

routing:
  graph: local_regular_8_connected_with_mandatory_points_and_portals
  grid_steps_m: [2.0, 1.0, 0.5]
  window_margin_m: 100.0
  expansion_factor: 2.0
  desired_alternatives: 1
  portal_sample_step_m: 10.0
  max_expanded_nodes_per_attempt: 250000
  safety_margin_m: 0.001

materialization:
  max_repair_passes: 4
  max_diameter_assignments: 256

search:
  baseline_orders: 1
  baseline_order: flow_desc_then_oks_id
  merge_enabled: false
  edge_exchange_enabled: false
  lns_enabled: false
  alns_enabled: false
  annealing_enabled: false
  max_candidate_evaluations: 5000
  finalization_budget_fraction: 0.1

archive:
  enabled: false
  output_limit: 1

learning:
  enabled: false
```

`max_candidate_evaluations` — предохранительный предел, а не требование выполнить 5 000 оценок. `max_repair_passes` здесь относится к исправлению геометрии/назначений диаметра для проверки ограничений, **не к LNS repair**. Настройки лимитов нужно профилировать на текущем наборе.

**Roadmap-конфигурация:** после приёмки baseline включать по одному расширению и сравнивать с сохранённой базой. Отдельными настройками добавить `k = 3`, до трёх порядков старта, сэмплирование трубы через 20 м, объединения, затем локальные операции/LNS. Архив до 30 представителей с выдачей не более трёх вариантов, параметры разнообразия и обучение операторов относятся только к расширенному профилю. Нельзя включать весь roadmap одним неявным значением по умолчанию.

`max_candidate_evaluations` учитывает дорогие полные оценки во всех фазах, включая восстановление и пробные объединения. Иначе внутренняя repair-процедура сможет незаметно израсходовать намного больше вычислений, чем внешний цикл.

Объём кэша, лимит загрузки, общий таймаут и дисковый лимит задаются по доступным ресурсам окружения и профилированию. Жёсткий лимит итераций сам по себе не защищает от одного огромного пространственного запроса.

### 18.2. Причины ошибок

| Код | Смысл |
| --- | --- |
| `INVALID_INPUT_GEOMETRY` | Невалидная исходная геометрия |
| `DUPLICATE_ID` | Повтор ID |
| `BROKEN_REFERENCE` | Ссылка на отсутствующий объект |
| `UPSTREAM_CYCLE` | Цикл старой сети |
| `AMBIGUOUS_UPSTREAM_GEOMETRY` | Нельзя однозначно определить физическое соединение |
| `UNKNOWN_RESTRICTION_TYPE` | Правило для ограничения неизвестно |
| `CHAMBER_DEGREE_EXCEEDED` | В камере больше четырёх участков |
| `FLOW_EXCEEDS_CATALOG` | Ни один разрешённый диаметр не подходит |
| `LENGTH_LIMIT_VIOLATION` | Не выполнено принятое правило длины |
| `NO_PATH_ON_EXPLORED_GRAPH` | Пути нет в исследованном конечном графе |
| `ROUTING_BUDGET_EXHAUSTED` | Поиск пути остановлен по лимиту |
| `RULE_INTERPRETATION_REQUIRED` | Для геометрии не хватает согласованного правила |
| `OUTPUT_VALIDATION_FAILED` | Сформированный выход не прошёл проверку |

ОКС, который выгоднее оставить без подключения, получает внутреннюю причину `ECONOMIC_CHOICE`, а не `PHYSICALLY_IMPOSSIBLE`. ОКС, для которого закончился поиск, — `SEARCH_BUDGET`, а не утверждение об отсутствии любого пути. Во внешнем списке `unconnected_oks_ids` должны быть учтены все фактически неподключённые ОКС; формулировку поля и экономический выбор следует уточнить (§20).

### 18.3. Проверяемость запуска

Для каждого результата сохраняем отдельно от контрактного GeoJSON: хэш входа, версию правил, версию solver-а, конфигурацию, seed, время/ресурсы, метрики и причину остановки. Для выбранного кандидата — разложение цены и ссылки на исходные объекты реконструкции.

Это позволит ответить не только «почему этот вариант дешевле», но и «какой оператор его создал и какие правила при этом применялись».

| --- | --- | --- |
| 1. Вход и исходные правила | Загрузка, статистика текущего набора, поля и расходы, каталог, CRS, `upstream_object_id`, индекс | Состав сопоставлен с [НД]; расход каждой точки определён, входные ошибки диагностируются |
| 2. Кандидаты врезки | Ближайшие камеры, проекции/концы труб, правило ≤10 м, проверка примыканий | Список допустимых кандидатов, возможность расширения поиска, T16–T20 |
| 3. A* и ограничения | Локальная регулярная сетка, обязательные точки, отступы, переходы, специнтервалы; k=1 на кандидата | Один путь проверяется по фактическому диаметру и правилам пересечений |
| 4. Полный evaluator | Расходы, диаметры, предельные длины, камеры, частичная реконструкция, коэффициенты, штрафы, S | Контрольные примеры §10.4 и §11.5 совпадают с независимым расчётом |
| 5. Независимые подключения | Один порядок ОКС; добавление пути и полная оценка текущей схемы | Каждый ОКС подключён либо учтён со штрафом; общая старая сеть пересчитана совместно |
| 6. Экспорт и приёмка | Один FeatureCollection, нужные типы и поля, проверка ссылок/сумм, Docker-запуск | Текущий набор проходит сквозной запуск; один результат проверен независимо, сохранён отчёт |

Evaluator вызывается внутри baseline: шаг 4 следует закончить до сборки всех независимых подключений. Экспортер желательно проверять на маленьком эталоне параллельно, не откладывая контракт выхода до конца.

### 19.2. Definition of Done первого MVP

При валидном входе текущий набор из 144 объектов проходит `input.geojson → result.geojson`. Все 17 точек подключения имеют учтённый исход; соответствующие ОКС подключены либо отражены в `unconnected_oks_ids` со штрафами. В результате соблюдены основные 2D-правила, посчитаны все необходимые категории стоимости и реконструкции, вывод содержит одну проверенную схему. Входные несоответствия не маскируются, вывод записывается только после проверки.

**LNS, ALNS, edge exchange, объединения, ML, три варианта и 3D не нужны для приёмки этого этапа.** Одно корректное решение не означает доказанную оптимальность или готовность к 3 ГБ. Отсутствие найденного пути в ограниченном поиске не выдаётся за физическую невозможность подключения.

| Этап развития | Что добавляется | Как проверяем пользу |
| --- | --- | --- |
| Общие ветви | Greedy merge, потом split и пересчёт габаритов | Контрольные задачи с выгодным/невыгодным объединением; полный S |

| ALNS / отжиг | Выбор операторов по статистике и иной критерий принятия | Отдельные воспроизводимые сравнения |

## 20. Что остаётся уточнить и чего алгоритм не обещает

### 20.1. Реестр неоднозначностей

Это не вопросы, без которых нельзя писать код вообще. Для каждого нужна изолированная политика, чтобы уточнение не потребовало переписывать solver.

| ID | Что не определено однозначно в источниках | Временное поведение / модуль |
| --- | --- | --- |
| Q01 | Относительно чего мерить угол дороги/трамвая у сложного полигона | `CrossingAnglePolicy`: простые границы; неоднозначные переходы не принимать без согласования |
| Q02 | Как измерять по 2/3 м у границ и что делать возле конечных узлов | `SpecialPassPolicy`: вдоль новой линии; не обрезать обязательные интервалы молча |
| Q03 | Точная длина на ветвящейся сети; статус правила повышения на одну позицию | `LengthLimitPolicy`: связная компонента одного ДУ; повышение относительно минимума по расходу; версия «по записи встречи» |
| Q04 | Возможны ли несколько точек подключения одного ОКС и как распределять его расход | В MVP требовать одну однозначную точку; неоднозначный вход диагностировать, не удваивать расход |
| Q05 | Положение терминала внутри запретного отступа и допустимый особый подход | Не разрешать произвольное движение в запретной области; правила подхода вынести отдельно |
| Q06 | Как валидатор связывает совпадающие роли врезки и новой камеры | Один физический узел внутри; отдельные features, ссылка ветви на tie_in; сверить с валидатором |
| Q07 | Допуски геометрии, округление и точность выходных сумм | Отдельный `PrecisionPolicy`; безопасный запас, контроль выходной геометрии |
| Q08 | Независимые пересечения и зазоры двух новых сетей | В 2D-MVP не разрешать столкновения без узла; не переносить правило старой сети автоматически |
| Q09 | Габарит старой трубы после реконструкции при проверке новой трассы | Консервативно использовать итоговый диаметр на реконструируемой части |
| Q10 | Длина наклонной линии для цены/S и объединение близких переходов по глубине | Основной режим 2D однозначен; для дополнительного режима зафиксировать согласованную политику до сдачи |
| Q11 | Поле `unconnected_oks_ids` описано как «маршрут не найден», хотя разрешён экономический отказ | Выводить всех реально неподключённых и штрафовать; причину хранить отдельно, трактовку согласовать |
| Q12 | Ограничения времени, RAM, стороннего обучения и точный API | Настройки развертывания; не делать неподтверждённых обещаний о производительности |
| Q13 | Сводка текущего набора не выделяет `oks_future`; поля расхода и связь с 17 точками не раскрыты | Проверить `oks_id` и источник `flow_tph`; при иной схеме нужен явный адаптер, при отсутствии данных — входная ошибка, не нулевые расходы |

Известная сводка состава [НД] не заменяет валидацию полей, геометрии ограничений и связей старой сети при загрузке. Зафиксировать эти результаты вместе с хэшем конкретного файла.

### 20.2. Ограничения предлагаемого метода

**[Решение]** Метод ищет хорошее решение в ограниченном пространстве кандидатов. Ограничения возникают из-за конечной сетки, дискретных мест врезок/ветвления, ограниченного числа переходов, бюджета ремонта диаметров и числа итераций.

Следовательно:

- результат A* оптимален только относительно конкретного графа и его фиксированных весов при соблюдении условий эвристики;
- набор до k маршрутов в MVP эвристический;
- лучший найденный проект не обязательно глобально лучший;
- отсутствие найденного подключения не доказывает физическую невозможность;
- корректность формул не гарантирует экономическую оптимальность;
- испытание на маленькой синтетике не доказывает нужную скорость на реальном большом файле.

Эти ограничения не мешают сделать полноценный инженерно проверяемый MVP. Они определяют, какие утверждения можно делать о результате и какие расширения проверять дальше.

### Что считать итогом этой спецификации

Разработчик должен суметь проследить любой итоговый метр трубы до кандидата маршрута, любое значение диаметра — до суммарного расхода и длины, любую реконструируемую часть — до врезок и цепочки к источнику, а любую сумму в сводке — до конкретных выходных сущностей.

Сводка состава текущего датасета известна [НД]; это не равнозначно проверке работающего solver-а на нём. Следующие доказательства готовности — реализация baseline, прохождение тестов и сохранённый отчёт сквозного запуска. Нагрузочные прогоны и сравнения оптимизаторов относятся к последующим этапам.
