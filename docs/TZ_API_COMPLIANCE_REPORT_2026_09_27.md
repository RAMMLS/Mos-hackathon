# API по требованиям ТЗ

Дата: 2026-09-27  
Статус: реализовано и проверено на развёрнутом Docker-сервисе

## Контракт

Основной endpoint:

```text
POST /api/trace
Content-Type: multipart/form-data
file: combined GeoJSON FeatureCollection
```

Параметры: `algorithm`, `budgetMs`, `entryStrategy`, `ruleset`. Production defaults:
`PORTFOLIO`, `AUTO`, `DOCUMENT_NEAREST_V1`. Ответ имеет тип
`application/geo+json` и скачивается как `heat-network-result.geojson`.

Служебные endpoint-ы:

- `GET /api/trace/algorithms` — реализации и их статусы;
- `GET /api/trace/configuration` — defaults, rulesets, лимиты и ветки портфеля;
- `GET /v3/api-docs` — OpenAPI JSON;
- `GET /swagger-ui.html` — Swagger UI.

## Соответствие программным требованиям

| Требование ТЗ | Реализация | Проверка |
|---|---|---|
| Java 11 | OpenJDK 11 runtime | `java -version` внутри контейнера |
| Spring Boot 2.6.3 | parent зафиксирован в `pom.xml` | Maven build |
| Swagger UI 1.7.0 | `springdoc-openapi-ui:1.7.0` | `/v3/api-docs` 200, Swagger redirect 302 |
| Ubuntu Server 22 | runtime-образ `ubuntu:22.04` | `/etc/os-release` внутри контейнера |
| Docker Compose | приложение и временный volume описаны в compose | `docker compose up -d --build` |
| Вход до 3 ГБ | multipart limits 3 ГБ, threshold 0, temp volume | configuration endpoint и Spring config |
| Выход до 500 МБ | потоковый `StreamingResponseBody`/`JsonGenerator` | streaming unit test и живой API |
| Не держать файл целиком | вход читается `JsonParser` по одному Feature, выход пишется по одному Feature | 2 streaming unit tests |
| До 50 пользователей | Tomcat 100 threads, response pool 10-50, bounded portfolio pool 8 | нагрузочные прогоны по 50 запросов |

Граничные файлы ровно 3 ГБ и 500 МБ не создавались: это потребовало бы отдельного
длительного soak-теста и большого синтетического набора. Лимиты, временный диск и
потоковые пути исполнения настроены; фактическая производительность на таких объёмах
зависит от числа геометрий и сложности маршрутизации, а не только от размера файла.

## Параллельный PORTFOLIO

1. `B2-C-J` строит быстрый сертифицированный incumbent.
2. В общем ограниченном executor-е параллельно работают `B3`, `R1`, `R2`, `X1`, `X2`.
3. `X1/X2` запускаются только при поддерживаемом размере сцены (до 6 ОКС).
4. Все кандидаты проходят проверку конечности objective, степеней узлов и геометрии.
5. Выбор: сначала полнота подключения, затем score, затем стоимость.
6. Единый wall-clock `budgetMs` отменяет незавершённые ветки через interrupt.
7. При малом бюджете возвращается лучший готовый частичный вариант с
   `unconnected_oks_ids`, как требует раздел 2.9 ТЗ.

Контрольный Иннополис, `PORTFOLIO`, бюджет 120 секунд:

| HTTP | ОКС | Длина | Стоимость | Score | Время API | Checker |
|---:|---:|---:|---:|---:|---:|---|
| 200 | 6/6 | 527.86 м | 74 473 341.01 руб. | 3.67 | 4.50 с | VALID, 0 нарушений |

В архиве приняты все ветки: `B2-C-J,B3,R1,R2,X1,X2`; failures отсутствуют.

Нагрузка на той же сцене:

| Профиль | Запросы | HTTP 200 | Полные ответы | Wall time | p95 |
|---|---:|---:|---:|---:|---:|
| B0-CORRIDOR, 5 с | 50 | 50 | не критерий теста | 0.354 с | 0.330 с |
| PORTFOLIO, 1 с | 50 | 50 | 21/50 | 1.291 с | 1.279 с |
| PORTFOLIO, 5 с | 50 | 50 | 50/50 | 5.278 с | 5.220 с |

Односекундный стресс показывает ожидаемую CPU-конкуренцию: API остаётся доступным и
возвращает законченные частичные варианты, но не обещает полное решение при заведомо
недостаточном бюджете. При 5 секундах все 50 одновременных запросов вернули 6/6.
После нагрузки в серверном логе нет WARN, ERROR или исключений.

Машинные артефакты контрольного ответа находятся в
`results/api-tz-complete-2026-09-27/`.

## Ошибки и дедлайн

- неверные параметры и пустой файл: HTTP 400;
- повреждённый JSON: HTTP 400 `INVALID_GEOJSON`;
- файл больше 3 ГБ: HTTP 413 `PAYLOAD_TOO_LARGE`;
- недоступный алгоритм: HTTP 422;
- при исчерпании времени возвращается законченный GeoJSON, а не промежуточное
  изменяемое состояние;
- timeout-aborted пустые маршруты не записываются в cache как невозможные.

## Граница вывода

Этот отчёт подтверждает API, развёртывание, параллельное выполнение и проверку
текущих выходных сущностей. Он не утверждает, что любой файл размером 3 ГБ будет
оптимизирован за фиксированное время или что эвристический PORTFOLIO доказывает
глобальный оптимум.
