# Как улучшить алгоритмы теплосети: единый план доработки

**Версия:** 1.0 · **Дата:** 26 сентября 2026 года.  
**Основа:** итоговый отчёт от 22.09.2026, актуальное техническое приложение и разъяснения из `ТЗ (1).zip`.  
**Назначение:** постановка задач разработчику и план экспериментов. Это не отчёт об уже выполненных улучшениях и не новая редакция конкурсного ТЗ.

> **Главное решение:** сохранить проверенную начальную сеть, устранить потерю хороших кандидатов и ошибки геометрии, сделать стоимость коридоров зависимой от диаметра, затем совместно перестраивать небольшие районы сети. X2/MILP использовать как ограниченный локальный решатель, а RL и «муху» — как проверяемый способ выбирать районы и действия. Не запускать одновременно ещё семь новых самостоятельных алгоритмов.

### Что делаем в ближайшей итерации

| Приоритет | Изменение | Проверяемый результат |
|---|---|---|
| P0 | Зафиксировать входы, checker, тарифы, конфигурации и модели | Старые и новые прогоны больше не смешиваются |
| P0 | Сохранить B2-U как начальный проверенный кандидат; исправить работу архива B3 | Результат улучшателя не хуже переданного ему допустимого начального решения |
| P0 | Разобрать две невалидные сцены B2-C-J | Причины локализованы; неверная перестройка откатывается, а не заменяет хороший проект |
| P0 | Разделить таймаут, отсутствие пути в графе и доказанную невозможность | Отказные сцены не зависают и не получают ложное «подключение невозможно» |
| P1 | Общий лениво раскрываемый граф коридоров с допустимыми диаметрами и направлениями подхода | Меньше повторной геометрии; рост ДУ не делает кэш незаметно неверным |
| P1 | Стоимостные перестройки: junction внутри ребра, перенос камеры, обмен группами, смена присоединения | Меняется реальная конструкция сети, а не только порядок подключения |
| P1 | Локальный repair для 2–6 ОКС с полным пересчётом затронутой части | X2/перебор/MILP ищет лучшую небольшую конструкцию, не теряя влияние на остальную сеть |
| P2 | Диспетчер вычислительного бюджета, затем bandit/RL/fly-selector | Измеримая польза выбора действий при одинаковых кандидатах и правилах |

**Не делать первым:** полное переобучение PPO, новый глобальный MILP, переписывание всего маршрутизатора, обучение внутренних связей коннектома, визуальное сглаживание без повторной проверки.

### Целевая архитектура

```text
Текущие данные + версия правил
              ↓
Подготовка вводов ОКС и кандидатов присоединения
              ↓
Начальный проверенный проект B2-U / портфель начальных решений
              ↓
Общий граф коридоров и предложения конструкций
              ↓
Выбор небольшого района и операции
              ↓
Перестройка + ограниченный локальный поиск
              ↓
Расходы → диаметры/длины → геометрия → камеры/стоимость
              ↓
Экспорт кандидата → независимая проверка
              ↓
Неизменяемый архив проверенных решений
              ↓
Лучший допустимый результат к установленному сроку
```

Выбор операции сначала эвристический. После измерений на это же место можно поставить bandit, обычную обученную модель и контроллер с коннектомом. Ни один из них не получает право менять тарифы, пропускать checker или намеренно оставлять доступный ОКС неподключённым.

## 2. Контракт, который все улучшения обязаны сохранять

**[ТЗ]** Расчётную модель брать из актуального приложения; при расхождении действует оно по ответу №16. Полное основное ТЗ содержит несогласованные старые пункты, поэтому нельзя смешивать старую реконструкцию с новым входом. [A; Q, №14, №16]

| Область | Правило для текущей реализации |
|---|---|
| ОКС | Каждая `oks_connection_point` — отдельный потребитель с `flow_tph`; принадлежность одному зданию не объединяет потребителей |
| Старые сети | Реконструкция и проверка резерва старой сети не входят в обязательный расчёт; `upstream_object_id` не требовать |
| Направление | Для каждого подключённого ОКС один путь по новой сети до законного присоединения; циклы запрещены |
| Присоединение | Через существующую или новую `heat_chamber`; отдельного объекта `tie_in` нет |
| Существующая камера | Каждый новый линейный участок, заканчивающийся в ней, даёт врезку за 5 млн ₽ |
| Новая камера | Её цена уже включает присоединение к старой сети; определяется максимальным ДУ всех примыкающих участков, в том числе старых |
| Вместимость камеры | Не более четырёх примыканий; проходящая старая линия занимает два |
| Правило 10 м | Существующая камера используется, если выбрано присоединение не далее 10 м и хватает примыканий |
| Диаметр | Минимальный, удовлетворяющий расходу и длине; к месту присоединения не уменьшается |
| Постоянный расход | Между узлами изменения расхода ДУ постоянен; нельзя менять ДУ ради сброса длины |
| Предельная длина | По каждому непрерывному пути одного ДУ; параллельные ветви не складываются |
| Повороты | Изменение направления до 90° включительно; обычный поворот не требует камеры и отдельной денежной надбавки |
| Спецпроход | Прямой; с разбиением на границах; геометрические правила всех перекрытых ограничений выполняются, коэффициент — максимум |
| Здания | Собственный полигон не удаляется; допускается только описанный финальный прямой подход к своей точке |
| Новые трубы | Не пересекаются вне общего узла; формальная вершина графа сама по себе не заменяет разрешённый инженерный узел |
| Отказ | Нельзя намеренно не подключать технически доступную точку ради экономии |
| Выход | `heat_network`, `heat_chamber`, `technical_node`, `variant_summary`; глубина для обязательного 2D — `null` |

Основания: [A, §1–7; Q, №1–16]. Конкретные неизвестные интерпретации, например неоднозначный собственный полигон, должны получать диагностический статус, а не молчаливое упрощение.

### 2.1. Полная стоимость, а не сумма независимых маршрутов

```text
C_pipes       = Σ стоимость физических новых участков, каждый участок один раз
C_chambers    = Σ стоимость новых камер
C_connections = 5_000_000 × число новых участков у существующих камер

construction_cost = C_pipes + C_chambers + C_connections
calculated_cost   = construction_cost + unconnected_penalty
L                 = Σ длина новых физических участков
S                 = 0.7 × calculated_cost / 25_000_000 + 0.3 × L / 100
```

Нельзя прибавить разбивки камер и врезок к `construction_cost` повторно. Нельзя оплачивать общий участок отдельно за каждого проходящего через него ОКС. [A, §3.2, §6–7]

### 2.2. Полезное преобразование для поискового ядра

**[ВЫВОД]** При тех же правилах допустимости минимизация S эквивалентна минимизации:

```text
J = calculated_cost + λ × L
λ = (0.3 / 100) / (0.7 / 25_000_000)
  = 107_142.857142857… руб./м
S = (0.7 / 25_000_000) × J
```

λ — **эквивалент длины в целевой функции**, а не реальный тариф. В экспортируемую смету его не добавлять.

Для фиксированного диаметра d у отдельного коридора можно считать поисковую цену:

```text
w(e, d) = c_new(d) × Σ_i(length_i × K_special_i) + λ × length(e)
```

Это полезный внутренний вес в 2D. Но активация камеры, использование общего участка и изменение диаметра целой магистрали остаются состояниезависимыми. Они требуют оценки всего изменённого проекта, а не слепого суммирования w по независимым путям.

## 3. Что исправить в прежних предложениях, прежде чем писать код

| Прежняя упрощённая идея | Уточнение для разработки |
|---|---|
| «A* не подходит» | A* может искать путь по корректному графу и денежным весам. Ограничение — независимые подключения, неполные состояния и грубая геометрия, а не само название поиска |
| «17 ОКС — всего 2^17 состояний» | Это лишь число подмножеств. Классический Steiner DP также перебирает разбиения подмножеств, что даёт член порядка 3^k, и умножается на размер графа [W1] |
| «X2 — точный оптимум нашей теплосети» | В отчёте не показаны все ресурсы состояния и доказательство отсечений. Точность классического Steiner не переносится автоматически на диаметры, камеры, повороты и конфликты геометрии |
| «MILP: выбрать ребро и ДУ, ограничить расход — задача решена» | Ещё нужны пути без циклов и дробления, камеры, примыкания, направления, длины одного ДУ, запреты геометрии, минимальность ДУ и правила присоединения |
| «Локальный exact repair точен для всей сети» | В лучшем случае он точен для заданного локального графа, границы, модели и завершённого поиска. Если часть условий оставлена внешнему checker-у, это надо явно учитывать |
| «Цена/расход показывает самое невыгодное ребро» | Это лишь эвристический признак. Удаление группы может изменить ДУ и цену длинной общей ветви; реальная выгода определяется полным изменением стоимости |
| «Если coarse-grid разорван, пути нет» | Грубая сетка может потерять узкий допустимый проход. Отсутствие пути в ограниченном графе не доказывает отсутствие пути в допустимой геометрии |
| «Евклидово расстояние × тариф отсекает любой плохой ход» | Для одиночной фиксированной задачи — возможная нижняя оценка. Для перестройки надо учитывать удаляемые расходы и совместное использование; иначе можно выкинуть выгодный ход |
| «Дешевле и короче DP-состояние всегда доминирует» | Только при не худших ресурсах всех дальнейших продолжений: остатке длины, ДУ, примыканиях, направлениях, занятой геометрии и статусе активации камер |
| «Поставить развилку с углами 120°» | Такое свойство относится к специальной евклидовой задаче с равными весами. У нас разные цены ветвей, препятствия и инженерные ограничения; точка — только кандидат |
| «Кластеризация решает большую сцену без потери качества» | Жёстко зафиксированные кластеры могут запретить лучшую общую магистраль. Кластеры должны перекрываться и допускать обмен ОКС |
| «Guard гарантирует, что B2-U всегда сработает» | Guard отбрасывает плохое, но не создаёт хороший проект. 112 успешных сцен — эмпирический результат на конкретном наборе |

Эти уточнения не отменяют идеи. Они определяют, где можно обещать корректность, а где остаётся эвристика.

## 4. Единое состояние, проверенный архив и неизменяемое начальное решение

**[ПРЕДЛОЖЕНИЕ]** Перед улучшением эвристик унифицировать представление проекта. Не хранить «один и тот же» проект отдельно в формате B2, X2, RL и UI с различающимися правилами стоимости.

### 4.1. Разделить три структуры

**Граф коридоров:** потенциальные точки, маршруты и допустимые диаметры. Это пространство выбора, а не построенная сеть.

**Проект:** реально выбранные физические участки, камеры, вводы и направления к присоединениям. Несколько ветвей могут пользоваться одним физическим участком, но он представлен и оплачен один раз.

**Представление для экспорта:** разбиение проекта на LineString по сменам параметров и спецпроходам. Оно не изменяет топологию или отсчёт предельной длины.

Нужны стабильные ссылки между этими уровнями. Техническая вершина в коридорном графе не обязана становиться платной камерой в проекте. И наоборот: новая развилка обязана стать камерой, даже если её координата возникла как пересечение двух коридоров.

### 4.2. Что входит в снимок состояния

```text
SolutionSnapshot:
  scene_hash, rules_hash, graph_revision
  physical_edges + geometry + topology_node_ids
  parent_orientation_to_connection
  downstream_terminal_ids / агрегированные расходы
  chamber_locations + существующие и новые примыкания
  selected_connection_locations
  computed_diameters + проверяемые пути одного ДУ
  special_passage_intervals
  served_terminal_ids
  cost_breakdown, length, score
  version, content_hash
```

Кэши вычисленных полей не являются источником истины. После изменения состояние либо пересчитано, либо явно помечено `DIRTY`; DIRTY-проект нельзя отдавать в архив как проверенный.

### 4.3. Подтверждать именно экспортируемый проект

```text
Candidate
  → нормализация геометрии без изменения смысла
  → полный инженерный пересчёт
  → сериализация GeoJSON
  → независимое чтение и проверка GeoJSON
  → ValidationCertificate
  → помещение в архив
```

В сертификате фиксировать хеши входа, правил, экспортированного кандидата и версии checker-а. Сертификат предыдущей версии правил не переносить на новую. Сертификат на внутреннюю геометрию до округления не заменяет проверку финального файла.

### 4.4. Инвариант «улучшатель не теряет исходное решение»

Если B3/PORTFOLIO получил полностью подключённый допустимый проект N₀, проверенный текущим checker-ом, то:

```text
returned.contract_valid = true
returned.all_connected = true
S(returned) ≤ S(N₀) + разрешённая численная погрешность сравнения
```

Это не эмпирическое обещание оптимизации, а свойство архива: N₀ хранится неизменяемой копией и остаётся кандидатом до конца. Строгий guard не должен уничтожать его из-за ошибки в другой ветке поиска.

Инвариант не означает, что solver всегда найдёт N₀ на любой новой сцене. Если ни один метод не нашёл полного решения, возвращается честный статус и допустимый контрактом результат, а не ложный успех.

### 4.5. Таймаут — не отрицательный ответ о геометрии

Предлагаемые внутренние статусы:

| Статус | Значение |
|---|---|
| `FOUND_VALID_ROUTE` | Найден и проверен путь |
| `NO_PATH_IN_GRAPH` | Исчерпан конкретный конечный граф при данной версии и ограничениях |
| `BUDGET_EXHAUSTED` | Поиск остановлен лимитом; о существовании пути вывод не сделан |
| `CERTIFIED_INFEASIBLE` | Есть отдельное корректное доказательство в явно указанной области и модели |
| `INPUT_INVALID` | Нарушен входной контракт |
| `INTERNAL_ERROR` | Ошибка программы, не свойство сцены |

Для результата сети отдельно хранить `contract_valid`, `all_connected`, `served_terminal_ids`, `unserved_reasons`. Нельзя превращать `BUDGET_EXHAUSTED` в обучающую метку «точка неподключаема».

score_before, score_after, archive_decision, rejection_reason
elapsed_ms, routing_ms, sizing_ms, checker_ms

### 5.2. B2-C-J: не «зажать guard», а выявить нарушенный инвариант

**[ОТЧЁТ]** Две сцены невалидны. Причины по сценам в отчёте не приведены. [R, таблица свежего пересчёта]

Для каждой нужны вход, исходная валидная сеть, конкретный junction-кандидат, изменённый проект до/после resizer-а, экспорт и подробный verdict checker-а.

Проверить отдельно:

- точка X действительно лежит на разрезаемом участке, а не только близко к его bbox;
- U–X и X–V полностью заменяют U–V, без двойной оплаты и потерянного фрагмента;
- X получил роль камеры, а не `technical_node`;
- старые и новые примыкания посчитаны по физической топологии;
- нет нового пересечения ветвей вне узла;
- отвод не проходит через собственное или чужое здание в режиме обычного транзита;
- увеличенный после объединения ДУ проходит по ширине и длине;
- в местах стыка соблюдён допустимый поворот, а спецпроход остался прямым;

Проверка «нет разворота на 180°», упомянутая в отчёте, не доказывает проверку всего ограничения поворота до 90°. Нужны отдельные тесты на 89°, 90° и 91°. Не утверждаем, что нынешний checker их не умеет: проверяем покрытие. [A, §2.1; R, «Что реализовано»]

### 5.3. Делать перестройку транзакцией

```text
try_move(base, move):
    draft = copy_on_write(base)
    delta = move.apply(draft)
    recalculate_dependency_closure(draft, delta)
    result = validate_exported_candidate(draft)
    if result.is_acceptable:
        return immutable_snapshot(draft, result.certificate)
    return REJECTED(reason=result.violations)   # base не изменяется
```

Полный пересчёт сначала предпочтительнее сложной неверной инкрементальности. Ускорение включать только после дифференциальных тестов «полный пересчёт = инкрементальный».

## 6. Общий граф коридоров: геометрия должна знать о диаметре и роли участка

**[ПРЕДЛОЖЕНИЕ]** Делать не одну огромную статическую матрицу всех возможных линий, а общий разреженный каталог с ленивым добавлением маршрутов. Имеющиеся хорошие решения обязательно включать в каталог, чтобы новая дискретизация не потеряла baseline.

### 6.1. Какие вершины нужны

- Точные точки ОКС и разрешённые подходы через ближайшую границу собственного полигона.
- Существующие камеры и кандидаты новых камер на старых трубах.
- Точки обхода буферов запретных объектов.
- Входы/выходы допустимых прямых спецпроходов.
- Кандидаты junction внутри существующих **новых проектируемых** ветвей.
- Узлы и участки из нескольких проверенных хороших решений.

Не ограничиваться k ближайшими соседями по прямой. Две близкие точки могут лежать по разные стороны здания, а полезный доступный коридор — вести через более далёкий узел. Сохранять разнообразие направлений, обходов и групп ограничений.

### 6.2. Что хранить у коридора

```text
Corridor:
  endpoint_ids
  geometry_m
  length_m
  special_intervals + crossing_object_ids
  entry_tangent, exit_tangent
  legal_diameter_mask            # допустимые ДУ для фиксированной геометрии/роли
  geometric_role                # обычный / собственный ввод / присоединение / пересечение
  static_geometry_certificate
  evaluated_status_by_diameter
  provenance, graph_revision
```

**Цена не одна на всё ребро.** Хранить геометрические данные и вычислять цену для выбранного ДУ. Сам объект может быть допустим для ДУ100 и недопустим для ДУ500.

Исключение для собственного ввода должно быть привязано к целевой точке, полигону и финальному прямому участку. Нельзя закэшировать такой маршрут как свободный транзитный коридор для остальных ОКС.

### 6.3. Учитывать направление подхода

Поиск, в котором состояние — только координата v, может выбрать два по отдельности допустимых отрезка с недопустимым поворотом при соединении.

Предлагаемый вариант — состояние вида:

```text
(v, входящий_коридор, диаметр, режим_прохода)
```

Переход к следующему коридору проверяет угол по касательным. Если поиск одновременно учитывает предельные длины, нужны дополнительные ресурсы; иначе эти условия проверяются отдельно и результат поиска не объявляется инженерно окончательным.

Спецпроход представлять атомарным прямым переходом со своими границами. Обычный маршрут не должен иметь возможности свернуть или поставить произвольную развилку посередине такого перехода.

Угол при обходе LineString должен вычисляться по согласованному направлению движения, а не случайному порядку координат. В неоднозначных трактовках угла в камере использовать согласованную версию правил; нельзя требовать ограничения для каждой произвольной пары дочерних ветвей, между которыми теплоноситель по модели не проходит.

### 6.4. Пересечения и общий участок — разные события

Если два выбранных коридора пересекаются:

- либо это запрещённое пересечение новых труб;
- либо создаётся общий инженерный узел с разрешённой ролью и стоимостью;
- либо это совпадение участка, которое явно нормализуется в общую физическую трубу с суммой расходов.

Не «узловывать» все пересечения графа молча: добавление камеры может изменить расход, стоимость и лимит примыканий. Альтернативные коридоры в каталоге могут пересекаться; одновременно выбранные участки проекта обязаны пройти проверку.

### 6.5. Версионированный кэш

Минимальная смысловая зависимость ключа:

```text
input_geometry_hash + rules_hash + endpoints + direction_constraints
+ diameter + geometric_role + own_terminal_exception
+ routing_parameters + relevant_dynamic_geometry_version
```

Статический кэш препятствий отделить от динамической проверки пересечений с уже построенными новыми трубами. Изменение новой сети не должно инвалидировать всю карту, но обязано инвалидировать затронутые проверки.

`BUDGET_EXHAUSTED` не кэшируется как `NO_PATH`. `NO_PATH_IN_GRAPH` действует только для конкретных графа, области и условий. Симметрию route(A,B)=reverse(route(B,A)) использовать только когда роли, углы входа и правила пересечения действительно симметричны.

### 6.6. Не потерять смысл при сжатии графа

Можно объединять цепочки степени 2 в макрорёбра, если сохраняются полная геометрия, сумма длины, интервалы спецпроходов, углы и возможность раскрыть ребро для новой развилки. Нельзя обнулять длину одного ДУ на каждой технической точке или навсегда удалить потенциальное место соединения только потому, что сегодня оно имеет степень 2.

## 7. Как ускорить дорогую геометрию и отказные сцены

### 7.1. Сначала измерить, куда ушло время

**[ПРЕДЛОЖЕНИЕ]** Для каждой сцены измерять подготовку, построение кандидатов, запросы маршрутов, resizer, full checker, экспорт и работу каждого решателя. Для маршрутов — число вызовов, уникальные пары, cache hit rate, число геометрических предикатов и причину окончания.

Утверждение отчёта «дорогие A* рёбра» — повод проверить профиль, а не доказательство, что ускорение самого heap в A* даст наибольший эффект. [R, «Недостатки по этапам»]

### 7.2. Ленивое раскрытие коридоров

Идея LazySP: сначала использовать дешёвые оценки рёбер, а дорогие проверки выполнять по востребованным кандидатным путям. Это известный подход для задач с дорогой оценкой рёбер [W2]. Наша адаптация:

1. Дешёво проверить прямую видимость и грубую нижнюю оценку стоимости.
2. Дорогой обход считать, когда коридор вошёл в перспективную конструкцию.
3. Реальную геометрию, цену и допустимые ДУ положить в кэш.
4. Невалидное ребро исключить в текущих условиях и продолжить поиск.
5. Непроверенный коридор никогда не передавать в конечный архив.

Оптимистическая цена — инструмент очереди, не подтверждённая стоимость трубы. Если оценка используется для математического отсечения, отдельно доказать, что это действительно нижняя граница.

### 7.3. Меньше повторных однопарных поисков

Один запуск поиска расстояний от корня может обслужить несколько ОКС, **только если** граф, веса, диаметр и направленные ограничения для запросов совместимы. Разные расходы и разные собственные вводы не всегда позволяют использовать одно дерево путей.

В группе запросов хранить несколько коридоров, а не только самый короткий: самый дешёвый индивидуально маршрут может мешать совместному использованию или будущему расширению ДУ.

### 7.4. Раннее обнаружение явно невозможных случаев

Разделить два приближения пространства:

- **Осторожное:** разрешает только подтверждённо свободные переходы. Найденный путь полезен, отсутствие пути ничего не доказывает.
- **Оптимистическое:** содержит все реальные допустимые пути и, возможно, лишние. Если даже такое пространство доказанно разорвано, можно получить необходимое условие невозможности.

Грубая сетка с заблокированными пересекающими препятствие клетками обычно относится к первому случаю, а не ко второму. Для сертификата нужен доказанный охват пространства, а не название алгоритма.

В положительных примерах использовать минимально возможный для отдельного ОКС габарит как оптимистическую проверку. Увеличенный диаметр общей ветви не должен преждевременно запрещать самостоятельное подключение меньшей трубой.

Граница текущего окна поиска не является препятствием из ТЗ. Непроходимая полоса на ограниченном bbox может обходиться за пределами окна. Глобальное доказательство возможно, например, для корректно обработанного замкнутого запрещённого барьера с учётом собственного ввода; это должно проверяться отдельной процедурой. [A, §2.1–2.2]

### 7.5. Ограниченный coarse-to-fine с честным исходом

```text
прямая проверка
  → готовые коридоры
  → ограниченный грубый поиск
  → уточнение около препятствий и узких мест
  → расширение области при наличии бюджета
  → FOUND / NO_PATH_IN_GRAPH / BUDGET_EXHAUSTED
```

Нужен общий deadline задачи и локальный лимит дорогого запроса. При исчерпании локального лимита диспетчер может проверить другой кандидат, но не заявлять техническую невозможность.

### 7.6. Осторожно с нижними оценками при перестройке

При замене области R нижняя оценка итоговой цели должна иметь вид:

```text
J_lower = неизбежная_стоимость_сохраняемой_части
        + нижняя_оценка_всей_новой_области
```

Нельзя взять текущую полную цену и просто добавить кратчайшую новую трубу: старые трубы/камеры могут исчезнуть, а оставшиеся — уменьшить ДУ.

Нельзя складывать индивидуальные расстояния всех ОКС как нижнюю границу длины общей сети: общие участки тогда оплачиваются несколько раз. Без доказанного bound такая величина — только эвристика приоритета, не основание безопасного отсечения.


## 8. Основные улучшения конструкции: деньги, группы ОКС и реальные узлы

**[ПРЕДЛОЖЕНИЕ]** Приоритетным объектом изменения сделать группу потребителей и её способ подключения. Стоимость отдельных труб — только признак для отбора района.

### 8.1. `JUNCTION_IN_EDGE`: развилка внутри новой трубы

```text
Было:                         Стало:
U ───────────────── V         U ─────── X ─────── V
                                       │
             B                         B
```

Предлагать точки X из проекций на прямые части LineString, точек пересечения кандидатных коридоров и нескольких соседних положений. Проецировать не обязательно сам ОКС: использовать его допустимую внешнюю точку подхода, иначе проекция через собственное здание может давать бессмысленные варианты.

После выбора X:

1. Проверить принадлежность сегменту и отличимость от соседних узлов с согласованной точностью.
2. Разрезать геометрию с сохранением длины и параметров обеих частей.
3. Вставить платную камеру; посчитать её реальные примыкания.
4. Добавить допустимый отвод.
5. Пересчитать расходы, ДУ и пути одного ДУ до затронутого корня.
6. Перепроверить геометрию **всех участков с изменившимся ДУ**, а не только нового отвода.
7. Пересчитать цену и проверить экспорт.

Если X совпал с существующим узлом, не создавать вторую камеру с теми же координатами для искусственного обхода ограничения степени. Точное правило слияния близких, но разных узлов должно быть отдельной настройкой численной геометрии, а не произвольным проектным отступом.

### 8.2. `MERGE_GROUP` и `SPLIT_GROUP`: объединение не всегда выгодно

Начальный размер групп — 2–4 ОКС как экспериментальная настройка. Рассматривать группы, близкие по **доступным коридорам**, а не только по координатам.

Для каждой группы сравнивать:

- существующие независимые подключения;
- общую магистраль с присоединением к выбранной старой камере;
- общую магистраль с новой камерой на старом участке;
- присоединение к другой уже выбранной новой ветви;
- разбиение группы на две подгруппы.

Нельзя посадить четыре дочерних отвода и питающую магистраль в одну камеру: это пять примыканий. Для группы из четырёх точек может потребоваться две камеры либо иная структура. [A, §2.1]

Промежуточный медоид или геометрический центр — только предложение расположения, не окончательный узел. Геометрически близкие здания по разные стороны воды могут оказаться невыгодной группой.

### 8.3. `DIAMETER_THRESHOLD_REPAIR`: использовать скачки тарифа

У общей трубы есть суммарный расход Q. Если перенос группы U на другой корень уменьшает расход до следующего тарифного порога, может уменьшиться цена всей оставшейся магистрали.

```text
Ищем U, для которого:
Q − Σ flow(U) ≤ capacity(DU_lower)
```

Это лишь необходимая подсказка. Требуется проверить, что меньший ДУ проходит длину и согласован с дочерними трубами.

Оценивать эффект как:

```text
ΔJ = J(полный проект после переноса U) − J(исходный проект)
```

Не как «цена нового отвода минус цена удалённого отвода»: уменьшение ДУ затрагивает общий путь, камеры и доступность геометрии.

Для отбора районов полезны признаки: расстояние до порога расхода; доля цены длинных общих участков; запас длины одного ДУ; возможное уменьшение категории цены камеры. Они лучше отражают таблицу затрат, чем только `cost / flow`.

### 8.4. `ROOT_REASSIGNMENT` и обмен группами между присоединениями

Два близких ОКС не обязательно должны иметь общий корень. Предлагать перенос одной подветви и обмен двумя группами между присоединениями.

Обязательные условия:

- повторно применить правило 10 м к новой выбранной точке;
- посчитать старые и новые примыкания камеры;
- если создаётся новая камера на старой трубе, учесть ДУ старой трубы в её цене;
- не начислять реконструкцию;
- не превращать независимое пересечение старой сети в бесплатную врезку.

Различать геометрическое положение корня и способ оплаты. При передвижении на несколько метров может измениться разрешённый тип присоединения. Это реальная дискретность задачи, а не повод подбирать искусственное `10 м + epsilon` без пространственного обоснования.

### 8.5. `CHAMBER_COLLAPSE` и `PORT_RELEASE`

Кандидат на улучшение — лишняя новая камера, которая после перестройки больше не является развилкой и не нужна как присоединение. Если её можно удалить без нарушения роли технических узлов, стоимость уменьшается.

Иная ситуация: у существующей камеры заняты все четыре места, но две новые ветви можно свести в одну общую магистраль до этой камеры. Это освобождает одно примыкание, меняет число оплачиваемых врезок и может открыть подключение другого ОКС. Проверять как единую перестройку, а не по отдельной цене каждого движения.

Камеру на старой трубе нельзя удалить просто потому, что у неё один новый отвод: она выполняет функцию присоединения.

### 8.6. Держать «банк возможностей», а не сканировать всё после каждого хода

Хранить предложения с признаком зависимости:

```text
Opportunity:
  terminal_group
  affected_edges, affected_chambers
  operation_family
  optimistic_priority       # не обязательно доказанный bound
  dependency_versions
```

После принятого изменения обновлять предложения, затрагивающие изменённые участки, их пути к корню и соседнюю геометрию. При этом периодически делать полный обзор, чтобы не потерять новые связи между районами.

Эффект измерять отдельно: число проверенных предложений на секунду, доля устаревших предложений и полезных изменений. «Банк возможностей» не должен кэшировать финальный verdict при изменившемся расходе общей магистрали.

## 9. Связанный расчёт «топология — диаметры — геометрия»

Нельзя считать, что мы один раз нашли линию, затем независимо назначили ДУ и задача закончена. Расходы определяются топологией; ДУ зависит ещё и от длины; увеличение ДУ изменяет ширину и иногда требуемый отступ от здания. [A, §2.3, §3.1, таблица 2]

### 9.1. Канонические цепочки постоянного расхода

Перед sizing выделять цепочки между узлами изменения расхода. Внутри цепочки смена `base/special`, техническая точка или обычный поворот не разрешает произвольную смену ДУ.

Далее:

1. Суммировать расходы точек снизу вверх, без удвоения пары труб.
2. Получить минимальные допустимые ДУ по расходу как начальные значения.
3. Проверить непрерывные пути одинакового ДУ и монотонность к корню.
4. При необходимости выбрать допустимое увеличение на соответствующей целой цепочке.
5. Перепроверить пути, потому что совпавшие после увеличения ДУ могут объединить раньше раздельные интервалы длины.
6. Повторить геометрическую проверку изменённых габаритов.

Этот список задаёт обязательные проверки, но **не доказывает оптимальность произвольного жадного порядка увеличений**. На небольших фиксированных топологиях быстрый resizer надо сравнить с перечислением допустимых назначений и согласованной трактовкой минимального ДУ. Если правило минимальности допускает неоднозначную трактовку на ветвлении, фиксировать конкретный спорный пример для организаторов, а не скрывать выбор внутри кода.

### 9.2. Зачем учитывать состояние на границе поддерева

Два поддерева могут обслуживать одинаковый набор ОКС и заканчиваться в одной точке, но иметь различный остаток допустимой длины одного ДУ.

Условный пример: в одном варианте к точке X уже подходит непрерывный путь ДУ50 длиной 170 м, а в другом — 150 м. Продолжение на 20 м пересекает лимит 181 м только в первом. Его низкая текущая цена ещё не означает, что он даст более дешёвое завершение. [A, таблица 1; арифметический пример]

Поэтому ресурсы границы включают не только расход и стоимость, но и последний ДУ, длину продолжающихся участков этого ДУ и условия изменения диаметра.

### 9.3. Пересчёт зависимостей вместо «новой трубы только»

Для изменения в поддереве область пересчёта содержит:

- само поддерево;
- все общие новые участки до изменяемого присоединения;
- дочерние/соседние цепочки, вовлечённые в новые непрерывные пути одинакового ДУ;
- камеры, у которых меняется максимальный примыкающий ДУ или степень;
- геометрические соседства всех увеличившихся габаритов.

После переноса к другому корню пересчитываются оба затронутых пути. Старые сети не включаются как реконструируемые, но их габариты и примыкания остаются ограничениями.

Инкрементальный расчёт — ускорение этой процедуры, а не иная модель. Его результат должен совпадать с полным пересчётом на одной и той же нормализованной сети.

## 10. Главный следующий оператор: ограниченное совместное перепроектирование района

**[ПРЕДЛОЖЕНИЕ]** Заменить часть repair «вставить ОКС один за другим» на `REGION_REOPTIMIZE`: выбрать небольшой район и найти лучшую совместную конструкцию на ограниченном графе.

Это развитие LNS: обычный поиск выбирает район, а локальный математический решатель или перебор подбирает конструкцию. Использование MIP-решателя внутри локальных окрестностей имеет известные реализации, например local branching [W3]. Это обоснование архитектуры, не готовая модель нашего ТЗ.

### 10.1. Что выбирать для разрушения

Приоритетные районы:

- 2–6 ОКС рядом с дорогим общим участком;
- подветвь около порога диаметра;
- область с лишними камерами;
- группа около перегруженной по примыканиям камеры;
- конфликтная область двух разных хороших решений;
- коридор, для которого обнаружена более прямая допустимая альтернатива.

Случайный район оставить для разнообразия. «Разрушить большой процент всех ОКС» без связи со временем repair не должно быть единственной стратегией.

### 10.2. Граница района — часть задачи

```text
BoundaryContext:
  сохранённые внешние узлы и геометрия
  допустимые точки присоединения к внешней новой сети
  расходы сохранённых внешних поддеревьев
  занятые примыкания и типы камер
  ДУ и состояние непрерывных путей на границе
  разрешённые изменения на общих путях к корням
  неподвижные препятствия и собственные вводы
```

Точки границы не являются бесплатными источниками с бесконечными портами. Присоединение к ним может увеличить ДУ и стоимость за пределами локальной области.

Два режима реализации:

**Закрытый repair:** внешняя геометрия и граничные ресурсы фиксируются; локальное решение обязано сохранить совместимость. Поиск уже, зато его легко проверить.

**Repair с расширением:** разрешить изменения по затронутым общим новым путям до корней; после склейки пересчитать полную область зависимостей. Если влияние вышло дальше, расширить область либо отклонить кандидат. Это не «точный локальный минимум при неизменном окружении».

### 10.3. Первая версия без нового внешнего solver-а

На локальной сцене с 2–4 ОКС:

1. Взять конечный набор корней, junction-точек и маршрутов, включая исходное решение.
2. Перебрать допустимые варианты группировок и родительских связей, ограничив число камер.
3. Для каждого построить физическую сеть, убрать дубли общих участков и выполнить полный evaluator.
4. Отсеивать только доказанно невозможные либо заведомо хуже по корректной нижней оценке варианты.
5. При лимите времени вернуть лучший проверенный вариант с `search_exhausted=false`.

Если перебор завершён, можно заявить оптимум **только в зафиксированном наборе разрешённых конструкций**, перечисленном в сертификате. Слово «точный» не должно означать «просто использовали X2».

Размер 2–4, затем 2–6 — параметры эксперимента, не гарантии времени.

### 10.4. Следующая версия: MIP на локальном графе

Отдельные бинарные переменные могут описывать выбор направленного коридора с ДУ, активацию камеры и выбор присоединения. Но модель обязательно должна включать весь необходимый контракт.

Минимальный перечень ограничений:

| Группа | Что моделировать |
|---|---|
| Обязательные точки | Все цели локальной задачи подключены; экономическое выключение не разрешено |
| Родитель | У активного узла единственное продолжение к его корню; нет дробления потока по двум независимым путям |
| Баланс | По направлению ОКС → корень: исходящий расход минус входящий равен локальной нагрузке, кроме корневого поглощения |
| Ацикличность | Топологический порядок или корректные connectivity/cycle cuts |
| Диаметр | Пропускная способность, монотонность, постоянство на цепочках неизменного расхода |
| Предельные длины | Непрерывные пути одного ДУ через камеры и технические точки; нельзя проверять только длину одного ребра |
| Камеры | Наличие камеры при ветвлении, максимум четыре примыкания, уже занятые внешние порты |
| Цена узлов | Максимальный ДУ, старые трубы у нового присоединения, врезка только в существующую камеру |
| Геометрия | Недопустимые совместные коридоры, углы входа/выхода, роли спецпроходов |
| Присоединения | Правило 10 м и допустимые старые участки; физические корни отличать от служебного super-root |
| Граница | Все сохранённые ресурсы и затраты внешней сети |

Одних `flow[e] ≤ capacity[d]` и минимизации цены недостаточно.

Служебный super-root удобен для описания нескольких компонентов, подключённых к разным местам старой сети. Его рёбра не являются трубами, не дают бесплатных физических соединений и не экспортируются.

**Стоимость в модели:** физические трубы учитываются по одному разу; камеры оплачиваются при активации; длина учитывается через официальный S или эквивалентный J. Геометрические пересечения альтернативных рёбер должны быть ограничениями выбора, а не неожиданной ошибкой только в конце.

Если сложные правила оставлены за внешним checker-ом, возможен цикл «решить → проверить → добавить корректное запрещение невалидной комбинации → повторить». Но нельзя выкидывать навсегда отдельное ребро, если неверен лишь его конкретный ДУ или сочетание с соседним ребром.

### 10.5. Условия честного результата локального solver-а

```text
model_kind: full_case | relaxation | surrogate
candidate_graph_hash
boundary_context_hash
incumbent_value
lower_bound            # только если математически относится к этой модели
termination: optimal | time_limit | exhausted | infeasible_in_model | error
validated_under_case_rules: true/false
```

`optimal` для упрощённой модели не означает оптимум исходного кейса. Завершение по таймауту с хорошим кандидатом — нормальный результат, но не доказательство оптимальности. Даже точный минимум полного кейса на одном фиксированном локальном графе не доказывает глобальный геометрический оптимум.

Для минимизации разрыв между подтверждённым верхним и нижним значениями **одной модели** можно считать как `(UB − LB) / max(abs(UB), eps)`. Сравнение с «лучшим известным» имеет другое название: `gap_to_best_known`, не `optimality_gap`.

### 10.6. Java-контур

Не подключать неразрешённый отдельный Python/C++-сервис в конкурсный runtime только ради MIP. Сначала локальный конечный перебор на существующем Java-ядре. MIP можно использовать в исследовательском бенчмарке или подключить после проверки совместимости библиотек, лицензии и требований к итоговому стеку.

Внешние DHNx/topotherm подтверждают полезность постановки «выбор труб + размеры», но не являются библиотеками, полностью реализующими наши правила [W4].

## 11. X2: сохранить сильную идею, проверить корректность состояния и ограничить стоимость

**[ОТЧЁТ]** X2 — bounded Steiner graph с subset-DP и свободными junction-точками; на старом наборе он почти совпал с портфелем. Конкретная рекуррентность, состояние и доказательство доминирования в отчёте отсутствуют. [R, «Что реализовано»; старый бенч]

### 11.1. Почему обычного `DP[subset][node]` может не хватать

В классической задаче Штейнера на графе веса рёбер фиксированы и суммируются [W1]. В нашем кейсе цена и допустимость продолжения зависят от:

- расхода выбранного подмножества;
- текущего ДУ и накопленной длины его непрерывных путей;
- углов подхода;
- числа уже занятых примыканий и статуса активации камеры;
- ранее выбранной геометрии, с которой продолжение может конфликтовать;
- того, какой общий участок уже построен и оплачен;
- выбранного присоединения и граничных условий.

Точное состояние должно не терять сведения, влияющие на оптимальное продолжение. Записать более длинный ключ ещё не означает доказать его достаточность.

### 11.2. Аудит X2 на маленьких контрпримерах

Сравнить X2 с полным перечислением на фиксированном маленьком графе:

1. Два варианта одного подмножества в X с разным запасом длины одного ДУ.
2. Две одинаковые по цене ветви, но одна занимает последний порт камеры.
3. Продолжение, геометрически пересекающее ранее выбранную ветвь только у одного состояния.
4. Два дочерних пути, которые при объединении используют общий физический участок: проверка отсутствия двойной цены/двойного потока.
5. Выбор присоединения в существующую камеру против новой камеры на старой трубе.
6. Случай, где самый дешёвый по длине Steiner-кандидат требует более дорогого назначения ДУ.

Если X2 проигрывает из-за потери состояния, допустимы два честных пути:

- расширить метки и доказать безопасные отсечения;
- оставить X2 генератором сильных топологических кандидатов, а не называть его точным решателем полного кейса.

### 11.3. Многокритериальные метки

Предлагаемый инженерный вариант — хранить несколько недоминируемых меток для сочетания подмножества и граничной точки.

Пример содержимого метки, **не доказательство достаточности**:

```text
served_subset, attachment_node
cost, physical_edge_usage
outgoing_DU, same_DU_path_resources
incoming_direction_signature
chamber_activation_and_free_ports
geometry_conflict_signature
boundary_root_compatibility
```

Метка A доминирует B только если любое допустимое полезное продолжение B можно не хуже реализовать из A. «Меньше цена и длина» недостаточно.

Ограничение числа меток лучшими m — полезная beam-эвристика, но отменяет автоматическую гарантию точности. В отчёт добавлять число удалённых меток и факт эвристического truncation.

### 11.4. Реальный масштаб subset-DP

Для классической задачи число подмножеств равно 2^k, но перебор их разбиений даёт компонент порядка 3^k; есть также множитель размера графа [W1].

При k=17:

```text
2^17 = 131 072
3^17 = 129 140 163
```

Если хранить хотя бы одно число float64 для каждого из 131 072 подмножеств в 2000 вершинах, это около **2,10 ГБ** только для массива значений. Предки, дополнительные метки, граф и объекты Java увеличивают память. Это расчёт гипотетической конфигурации, а не замер текущего X2.

Поэтому «17 — мало» не является оценкой времени или памяти. На проверочных сценах число ОКС может быть другим; зашивать 17 нельзя. [Q, №17]

### 11.5. Как ускорять X2 без незаметной подмены задачи

- Предвычислять расход каждого подмножества и переиспользовать его.
- Сжимать цепочки степени 2 с сохранением ресурсов и возможностью раскрытия.
- Переиспользовать статические маршруты в совместимых условиях.
- Использовать incumbent от B2-U для доказанных bound-отсечений.
- Лениво строить геометрию реально востребованных рёбер.
- Запускать X2 на локальных районах, а не на всём графе без оценки размера состояния.
- Для графов с узкими разделителями пробовать декомпозицию по ним, передавая полноценное состояние границы.
- Сохранять несколько внешних интерфейсов района: не фиксировать один медоид навсегда.

Отсечения ближайшими k рёбрами, beam по меткам и ограничение числа корней — обозначать как эвристические. Для оценки их потерь периодически запускать расширенный граф на контрольных малых сценах.

### 11.6. Проверять не только скорость, но и потолок генератора

На небольшом наборе задач построить два графа:

```text
G_small ⊂ G_expanded
```

Если одна и та же полная конечная модель действительно оптимально решена на обоих, то расширение не должно ухудшить минимум. Это контроль пространства решений.

Если вместо точного решения используется ограниченная эвристика, результат может стать хуже из-за расхода бюджета. Поэтому обязательно включать старый проверенный проект как кандидат и раздельно измерять **потенциал графа** и **умение solver-а найти решение на этом графе**.

## 12. X0/X1 и эталоны: что можно считать точным

**[ОТЧЁТ]** X0 ограничен перебором порядков; X1 перебирает деревья родителей через последовательности Прюфера; X2 работает на bounded graph. [R, «Что реализовано»]

### 12.1. Границы каждого подхода

- Перебор всех порядков вставки точен только относительно процедуры вставки и её shortlist, а не всех сетей.
- Перебор деревьев фиксированного набора вершин не перебирает автоматически все новые координаты камер, все маршруты рёбер и все схемы нескольких присоединений.
- Steiner-оптимум с фиксированными весами не равен оптимуму полного инженерного evaluator-а.
- «Точный solver завершился» не заменяет проверку, что сформулирована именно требуемая задача.

### 12.2. Предлагаемый маленький oracle

Создать отдельную коллекцию малых конечных графов с 2–5 ОКС, несколькими явно перечисленными корнями, junction-точками и вариантами маршрутов. Число вариантов ограничить так, чтобы перечисление реально завершалось.

Перебрать все допустимые выбранные подграфы/родительские схемы в этом наборе; для каждого проверить:

```text
обязательное подключение → отсутствие циклов → физическая геометрия
→ камеры/порты → расход → допустимое назначение ДУ и длины → полная стоимость
```

Для нескольких корней использовать корректное представление леса. Нельзя случайно требовать соединить все выбранные точки присоединения новыми трубами: это добавляет лишнее ограничение, которого нет в задаче.

Итоговый сертификат:

```text
exact_for = finite_candidate_graph_and_declared_case_rules
graph_hash, rules_hash, admissible_choices
enumerated_count, pruned_count, pruning_rules
search_exhausted = true
best_verified_solution_hash
```

Если исчерпан только временной бюджет, `search_exhausted=false`, а найденный проект — верхняя оценка. Доказательство «маршрута нет» в этом oracle относится к его конечному графу, не ко всей плоскости.

### 12.3. Два разных теста

**Тест оптимизатора:** все методы используют один фиксированный граф, сравниваем поиск конструкции.

**Тест маршрутизатора/генератора:** методы могут строить разные графы, сравниваем итоговую допустимую сеть и отдельно измеряем покрытие геометрических возможностей. В этом тесте gap к oracle другого графа не является точным optimality gap.

## 13. Геометрическая доводка после выбора структуры

**[ПРЕДЛОЖЕНИЕ]** Добавить дешёвую финальную фазу для проверенных проектов: перенести свободные новые камеры и упростить избыточные участки без потери допустимости.

### 13.1. `JUNCTION_RELOCATION`

Сохраняем, какие ветви соединены в камере. Перемещаем только её положение в допустимом диапазоне и перестраиваем соседние коридоры.

Для фиксированных соседей, постоянных ДУ и обычных прямых участков локальный ориентир:

```text
min_X Σ_i (c_new(d_i) + λ) × distance(X, neighbour_i)
```

Это взвешенная, а не обязательно обычная геометрическая медиана. Реальные ограничения и спецпроходы требуют полной проверки. Если движение меняет ДУ по длине, цена перестаёт соответствовать этой простой функции.

Практическая первая реализация: несколько точек вдоль доступных направлений и вдоль близких коридоров; уменьшение шага вокруг удачного положения; полный пересчёт после каждой принятой перемены. ОКС и существующие камеры не двигать.

Условие принятия: целевой S уменьшился и все правила выполнены. При равенстве S можно предпочесть менее изломанную геометрию как критерий ничьей, не меняя официальную смету.

### 13.2. `CHAIN_SHORTCUT`

Для цепочки без разветвлений пробовать заменить несколько звеньев более короткой прямой или допустимым обходом.

Обязательно сохранить:

- точные концы и собственный ввод;
- последовательность необходимых спецпересечений либо заново корректно пересчитать её;
- ограничения поворотов;
- ДУ и предельную длину после нормализации;
- отсутствие пересечения других новых труб.

Удалять коллинеарные промежуточные вершины допустимо только если на них нет смены параметра или иной значимой роли. Удалять технические границы спецпроходов ради красивой линии нельзя.

### 13.3. Отдельная проверка визуальной нормальности

Количество поворотов, коротких звеньев и суммарная угловая вариация — диагностические показатели. В ТЗ нет отдельного тарифа за поворот и численной минимальной длины между поворотами. Поэтому нельзя объявить любой отрезок короче выбранных разработчиком 5 м нарушением ТЗ.

Для «необоснованных мелких изломов» сохранять объяснение: существует ли проверенный shortcut с теми же концами, не ухудшающий S и убирающий изломы. Это более предметный тест, чем произвольный штраф за количество вершин. [A, §2.1; Q, №5]

## 14. Элитные решения: обмениваться структурой, а не только выбирать минимум

**[ПРЕДЛОЖЕНИЕ]** Идею path relinking вводить после измерения различий между результатами. Если B2, X2 и R2 возвращают одну сеть, сложное скрещивание не даёт новых вариантов.

### 14.1. Хранить небольшой разнообразный архив

У каждой сети вычислять две разные подписи:

- **Топология:** группы ОКС, корни, дерево камер, разделяемые участки.
- **Геометрия:** коридоры/последовательности препятствий, нормализованные линии.

Разные случайные ID не делают проекты разными. Не считать небольшой сдвиг той же трассы новым содержательным вариантом. [A, §6]

Внутренний архив может иметь больше трёх элементов; наружу выдаются до трёх вариантов по контракту. Размер внутреннего архива — параметр, а не новое требование ТЗ.

### 14.2. Перепроектировать только район разногласия

Пусть проект A объединяет {1,2}, а проект B — {2,3}. Общую идентичную часть оставить, в районе {1,2,3} взять коридоры обоих проектов и несколько дополнительных соединений, затем выполнить локальный repair.

```text
A + B
 → найти несовпадающие группы/корни
 → построить локальный граф объединённых возможностей
 → подобрать совместимую конструкцию
 → пересчитать полную стоимость
 → проверить
```

Не объединять физические рёбра A и B как готовую сеть: могут появиться циклы, пятые примыкания, двойная оплата и пересечения. Включать A и B как допустимые исходные кандидаты, чтобы операция могла закончиться без ухудшения.

### 14.3. Измерить полезность прежде, чем включать постоянно

На фиксированном наборе записывать число различных топологий, число успешных комбинирований, уникальные улучшения сверх исходного архива и время. Если почти все попытки возвращают A или B, оставить оператор редким либо отключить. Не объявлять path relinking обязательной следующей ступенью только по теоретической привлекательности.


## 15. PORTFOLIO как диспетчер бюджета, а не запуск всего подряд

**[ПРЕДЛОЖЕНИЕ]** Сначала получить и сохранить подтверждённую сеть. Потом тратить оставшееся время на улучшения, сохраняя лучший результат. Не начинать fallback после того, как X2 уже израсходовал весь deadline.

### 15.1. Рекомендуемый порядок

1. Подготовить общие входные данные и начальный граф.
2. Запустить B2-U; подтвердить полноту и корректность. Другие быстрые начальные методы включить по измерениям.
3. Сохранить сериализованный проверенный результат как резерв.
4. Проверить несколько недорогих стоимостных перестроек.
5. Дать ограниченный бюджет X2/локальному repair в наиболее перспективных районах.
6. При наличии времени — релокация камер и рекомбинация разных хороших проектов.
7. Вернуть лучший сохранённый файл, сертифицированный на текущем входе, с корректным статусом.

Если B2-U не получил полного решения, диспетчер сначала решает задачу восстановления подключений другими методами. 112/112 в отчёте не превращает этот метод в математически гарантированный fallback.

### 15.2. Необходимые инварианты бюджета

- Общий deadline проверяется внутри долгих операций, а не только между ними.
- Есть ограничение памяти и размера DP.
- Финальный ответ не зависит от того, успел ли завершиться последний экспериментальный кандидат.
- Локальный таймаут не уничтожает ранее найденный результат.
- Число одновременных CPU-потоков ограничено для всей задачи; несколько solver-ов не создают бесконтрольно собственные пулы.
- Время подготовки, проверки и экспорта входит в end-to-end измерение.

Параллельный портфель и последовательный X2 сравнивать как разные режимы по CPU-секундам и пиковым ресурсам. Разница старого среднего времени PORTFOLIO и X2 может зависеть от кэша и расписания; из отчёта конкретная причина не следует. [R, старый сравнительный бенч]

### 15.3. Измерять уникальный вклад методов

Для каждого кандидата сохранять `origin_algorithm` и историю улучшений. Для метода M измерять:

```text
unique_wins(M)       — сцены, где без M итог портфеля хуже
marginal_gain(M)     — изменение результата портфеля при исключении M
extra_wall_time(M)  — добавленное время
extra_cpu_time(M)   — добавленная процессорная работа
```

Ablation «портфель без M» выполнять с честным бюджетом. Простое удаление готового результата M из общего архива не учитывает, что другие методы могли бы использовать освободившееся время.

### 15.4. Полный цикл улучшения: псевдокод

Это контракт для реализации, не готовый исполняемый файл проекта.

```text
solve(scene, config):
    rules = load_pinned_rules(config.rules_hash)
    context = prepare_scene(scene, rules)
    archive = CertifiedArchive(scene.hash, rules.hash)
    deadline = create_global_deadline(config)

    for seed_method in config.seed_methods:
        if no_budget_for_safe_attempt(deadline): break
        seed = seed_method.build(context, deadline)
        submit_export_and_check(seed, archive, context)

    if not archive.has_complete_solution():
        run_bounded_connection_recovery(context, archive, deadline)

    current = archive.choose_starting_solution_or_partial_working_state()

    while budget_for_next_attempt(deadline):
        opportunities = generate_or_refresh_opportunities(current, context)
        if opportunities.empty(): break

        action = selector.choose(opportunities, remaining_budget(deadline))
        working = transaction_snapshot(current)
        proposal = apply_topology_change_or_local_repair(working, action, deadline)

        if proposal.status in {TIME_LIMIT_WITHOUT_CANDIDATE, REJECTED, ERROR}:
            log_attempt_without_mutating_archive(action, proposal)
            continue

        evaluated = full_or_verified_incremental_evaluation(proposal, context)
        certificate = check_exported_result(evaluated, context)
        if not certificate.contract_valid:
            rollback(working)
            log_geometry_or_engineering_failure(action, certificate)
            continue

        archive.consider(evaluated, certificate)
        current = acceptance_policy.choose(current, evaluated)
        selector.observe(action, archive.improvement(), measured_cost())

    return archive.best_currently_certified_output_or_explicit_failure()
```

Рабочая acceptance policy может иногда принимать временно более дорогой **допустимый** полный проект для выхода из локального минимума. Архив лучшего не ухудшается. Неполная внутренняя перестройка не получает статус готового ответа и не используется для искусственной экономии.

### 15.5. Сначала простое адаптивное расписание

Начать с частот операторов по наблюдаемой полезности с обязательной долей исследования редких действий. Затем сравнить с bandit-selector. Работы по ALNS и bandit-LNS показывают такую архитектуру в других задачах [W5, W6]. Это не обещание аналогичного процента ускорения здесь.

Приоритет может учитывать и ожидаемое улучшение, и вычислительную стоимость. Но `выигрыш/секунда` — внутренняя цель диспетчера; она не заменяет официальный S. Награду RL с делением каждого шага на время нельзя автоматически считать эквивалентной минимизации конечного S.

## 16. Независимый checker: проверять не только готовые хорошие примеры

**[ОТЧЁТ]** Checker уже используется. Его полнота по отдельным правилам в отчёте не доказана. [R, «Что реализовано»]

**[ПРЕДЛОЖЕНИЕ]** Общие тарифные таблицы и определения контракта можно разделять между компонентами. Но checker не должен доверять полям `flow_tph`, `cost`, `score` и списку подключённых ОКС из самого solver-а: их нужно независимо восстановить из входа и экспортированного результата.

### 16.1. Что пересчитывать независимо

- Ссылки на входные точки и камеры с сохранением типа ID.
- Совпадение концов геометрии с заявленными узлами.
- Пути ОКС → законное присоединение и отсутствие двойных путей/циклов.
- Суммы расходов, ДУ, постоянство ДУ на участках неизменного расхода.
- Непрерывные длины одного ДУ по путям, включая границы спецпроходов.
- Камеры, примыкания, максимальный ДУ и правила оплаты.
- Габариты, препятствия, собственный ввод, углы, прямизну спецпроходов.
- Новые пересечения и отсутствие двойного физического учёта совпадающих труб.
- Стоимости частей и итоговую сводку.

Не проверять старую реконструкцию, не требовать `oks_future` и не объявлять физическую гидравлику проверенной в обязательном 2D-режиме. [A, §1–7]

### 16.3. Проверить точность самого checker-а

Мутации должны давать ожидаемые **коды** нарушений, а не просто любой `INVALID`. Наряду с плохими примерами нужны хорошие: равноправные обходы, корректные ссылки на входные точки, существующая камера с последним свободным портом, обязательный ввод внутри своего здания.

Checker, отвергающий все варианты, легко ловит все мутации, но непригоден. Поэтому измерять и обнаружение нарушений, и ложные отказы на ручных положительных эталонах.

## 17. Новый бенчмарк: качество, надёжность и бюджет без смешения версий

### 17.1. Зафиксировать паспорт прогона

```text
run_id
input_manifest_hash
scene_hash + parent_scene_id + split
rules_hash + checker_commit + numeric_policy_hash
solver_commit + config_hash + model_hash
candidate_graph_hash + candidate_generation_mode
seed + deadline + evaluator_budget
machine + CPU_threads + memory_limit
cache_mode: cold | warm_within_scene | shared_explicit
```

Версия кэша, начинающегося с чужого готового результата, — часть эксперимента. Без неё X2, запускающийся холодным, и PORTFOLIO с уже построенными коридорами сравниваются не как одинаковая вычислительная задача.

### 17.2. Разделить наборы

**Текущие 112 сцен:** единый сравнительный прогон всех методов на одних хешах. Отчёт говорит о split 72/20/20 по независимым родителям. Не называть суммарные 112 сцен «независимым тестом RL», если часть использовалась для обучения или настройки. [R, «Свежий пересчёт»]

**Стресс-пул 1644:** отказоустойчивость, тяжёлые геометрии, timeouts. Запустить на нём не только B1, но сначала выбранный надёжный production-профиль. Существование полного допустимого проекта для каждой сцены в отчёте не установлено.

**Малые конечные графы:** точность оптимизатора, resizer-а, отсечений и стоимости. Здесь нужен исчерпываемый oracle из §12.

**Новые закрытые сцены:** отдельные географические родители, размеры и плотности. Они нужны после многократного ручного улучшения методов по уже известным 112 сценам.

Все производные одной карты, включая повороты, перестановки и новые потоки, держать в одном split. После ужесточения checker-а заново проверить обучающие проекты и метки. Не считать таймаут учителя доказательством отсутствия полезного действия.

### 17.3. Размечать выполнимость отдельно от результата solver-а

Предлагаемые классы сцен:

- `KNOWN_FEASIBLE`: есть полный проект-свидетель, принятый текущим checker-ом.
- `CERTIFIED_INFEASIBLE`: доказательство с явными предпосылками и областью.
- `UNKNOWN`: такого свидетельства/доказательства нет.

Сценарий с тем же географическим названием, но изменёнными полигонами требует нового свидетельства. Успех solver-а может установить `KNOWN_FEASIBLE`; его одиночный неуспех — не `CERTIFIED_INFEASIBLE`.

Нормативное разрешение вернуть неполный результат, когда допустимый маршрут не найден, не равно утверждению, что невозможность математически доказана. В отчёте держать эти вещи раздельно. [A, §2.5]

### 17.4. Метрики

| Блок | Метрики |
|---|---|
| Правильность | contract_valid, all_connected, served_points, served_flow, коды нарушений |
| Качество | полный S и его разбивка; paired improvement на одинаковых сценах; число побед/ничьих/поражений |
| Скорость | time_to_first_valid_complete, end_to_end, p50/p95/p99, число таймаутов |
| Ресурсы | CPU-секунды, пиковая RAM, число route/evaluator/checker вызовов |
| Поиск | число предложений, доля допустимых, доля принятых, уникальные улучшения, кэш |
| Геометрия | число поворотов, special-переходов, повторных проверок после роста ДУ, причины отклонения junction |
| Точность | gap к доказанному оптимуму того же конечного графа или отдельно gap_to_best_known |

Для общего рейтинга сначала показывать полноту и валидность, затем качество на согласованном наборе. `INVALID` не получает преимущества за маленькую цену. Среднее только по успешным случаям допустимо как дополнительная колонка с явным знаменателем, но не как итоговый рейтинг.

### 17.5. Парное сравнение

Для сцены i, где оба метода дали полный допустимый результат:

```text
improvement_i = (S_baseline_i − S_method_i) / S_baseline_i
```

Публиковать распределение этих значений, медиану, среднее, число сцен и крайние регрессии. Не подменять это одним отношением средних по разным множествам.

Для стохастических методов задать одинаковый список seed и повторные запуски. Доверительные интервалы оценивать с группировкой по независимому географическому родителю, а не изображать сотни вариаций одной карты независимыми наблюдениями. Число повторов определить бюджетом; как начальная исследовательская настройка — 5 seed, с расширением при высокой вариативности.

Таймауты включать в таблицу временных исходов и total runtime. p95 только по успешным быстрым задачам рядом с большой долей таймаутов вводит в заблуждение.

### 17.6. Два режима честного сравнения

**End-to-end при одном wall-clock бюджете:** учитываются подготовка, геометрия, нейросимуляция, evaluator и checker. Это основной пользовательский результат.

**Сравнение выбора действий:** одинаковые кандидаты, начальное решение, версия графа и число разрешённых оценок. Это изолирует качество селектора. Дополнительно всё равно показывается полное время, потому что один селектор может быть существенно дороже другого.

### 17.7. Последовательность экспериментов

| Эксперимент | Контроль | Меняем только |
|---|---|---|
| E0 | Текущий закреплённый B2-U | Ничего: повторяем и сохраняем артефакты |
| E1 | B3 с явным начальным B2-U | Архив, rollback, выбор результата |
| E2 | Та же топология/операции | Динамические габариты и исправленные junction-проверки |
| E3 | Общий граф и те же методы | Кэш, lazy routing, coarse-to-fine и бюджет |
| E4 | Стабильный поиск | Пороговые/group/root-перестройки |
| E5 | Те же операции | Совместный локальный repair вместо последовательной вставки |
| E6 | Те же проекты | Перемещение камер и проверяемые shortcut |
| E7 | То же ядро и кандидаты | Heuristic → bandit → обычный RL → fly-selector |

Новый метод включается в production не потому, что имеет красивое название, а после прохождения регрессий и подтверждения выбранного компромисса «S — время — надёжность».

## 18. Что делать с R1/R2 и «мозгом мухи»

**[ОТЧЁТ]** R1/R2 уже имеют runtime, обучение и модели. Переписывать их с нуля не требуется. Устойчивое преимущество на текущих входах пока не доказано; полный свежий прогон отсутствует. [R, «RL: что реально доказано»]

### 18.1. Сначала измерить, где теряется качество

На контрольном наборе состояний записать все предложенные действия и выполнить расширенную оценку продолжений для небольшой части состояний.

Возможны разные проблемы:

1. **Хорошего действия нет среди кандидатов.** Расширять генератор и интерфейс действий.
2. **Оно есть, но policy его редко выбирает.** Улучшать признаки, обучение или селектор.
3. **Выбран хороший тип операции, но repair слабый.** Улучшать repair, не только PPO.
4. **Топология перспективна, но guard отвергает геометрию.** Проверять маршруты, роли и resizer.
5. **Policy выбирает выгодное действие слишком поздно.** Добавлять оставшийся бюджет и стоимость действия в наблюдение.

Это диагностический протокол; отчёт не позволяет заранее приписать все потери одной причине.

### 18.2. Новая единица действия — конкретная перестройка

```text
Action:
  operation_family
  terminal_group / subtree_id
  target_corridor / root_candidate / junction_position
  repair_method
  local_budget
  precondition_snapshot_hash
```

Не учить выбирать абстрактное `MERGE`, если затем скрытая эвристика произвольно решает, каких ОКС объединять. Конкретика действия должна быть воспроизводимой и доступной обычному поиску.

Для R2 можно сохранить выбор пары destroy/repair, но добавить размер района и ограниченный бюджет. Для R1 — оставить конкретные действия, дополнив их внутренними junction и root/group-перестройками.

### 18.3. Признаки из экономики ТЗ

Наблюдение включает расходы, ДУ, расстояния до порогов capacity/length, свободные порты камер, тип и цену присоединения, число дополнительных камер, доступность коридоров по ДУ, признаки пересечений и оставшийся бюджет.

Не включать реконструкцию старой сети как обязательную цену. Не давать агенту финальное действие «отказаться от доступного ОКС ради S». [A, §2.4–2.5]

Точные последствия действия, которые требуют дорогого evaluator-а, не должны попадать во вход policy бесплатно и скрыто. Если заранее посчитаны ΔS всех действий, стоимость этих расчётов включается в бюджет; иначе получится сравнение, где нейросеть лишь читает готовый ответ.

### 18.4. Учитель полезен, но «лучший следующий шаг» — не всегда лучшая стратегия

Сначала собирать траектории сильного портфеля/локального solver-а: состояние, кандидаты, выбранное действие, фактический результат, бюджет и сертификат.

Можно предобучить ранжирование действий или районов на этих данных. Идея обучаемого выбора подзадач с передачей их обычному solver-у исследуется, например, в Learning to Delegate [W7]. Но если метка учителя — только немедленный ΔS, модель будет имитировать жадный выбор. Для обучения долгосрочной стратегии нужны завершённые продолжения или последующая RL-настройка.

NLNS — полезный исходный референс архитектуры обучаемого repair, а не готовое решение теплосетей [W8]. Его правила маршрутизации грузов нельзя автоматически переносить в наш контракт.

### 18.5. Согласовать награду с тем, что реально возвращается

Предлагаемый первый режим — агент улучшает полный начальный проект, а все изменения атомарны. Результат эпизода — **лучший проверенный проект архива**, не обязательно последняя рабочая сеть.

Тогда естественная награда:

```text
r_t = S(best_valid_t) − S(best_valid_{t+1})
```

При γ=1 и фиксированной нормировке сумма наград телескопируется в улучшение возвращаемого лучшего проекта. Учитывать finite horizon и оставшийся бюджет в состоянии. Такая награда может быть разреженной; это цена точного соответствия цели, а не повод добавлять произвольный денежный бонус за камеру.

Вариант `S(current_t) − S(current_{t+1})` также телескопируется, но оптимизирует последнее рабочее состояние, если не сделана дополнительная согласованная терминальная коррекция. Эти варианты не считать автоматически эквивалентными, когда результатом служит best archive.

Временный более дорогой допустимый рабочий проект можно принять для исследования. Временное отключение внутри одной транзакции не становится отдельным дешёвым состоянием с наградой. Невалидный ход расходует бюджет и откатывается. Показатели нарушения нельзя компенсировать хорошим score.

### 18.6. Маски действий

Безусловно невозможные действия отсекать точными дешёвыми правилами: неверный ID, очевидное лишнее примыкание, отсутствующая цель. Для сложной геометрии модель может оценивать риск, но окончательно решение проверяет инженерный код.

Не использовать необученный предиктор допустимости как безошибочную маску: ложный отказ может удалить единственный хороший коридор. `Unknown` и `Invalid` — разные состояния.

### 18.7. Сравнение селекторов

| Контроллер | Условие эксперимента |
|---|---|
| Детерминированная эвристика | Тот же банк конкретных действий |
| Адаптивные частоты / bandit | Тот же repair, graph и evaluator budget |
| Обычная компактная модель | Те же входные признаки и право на действия |
| Фиксированный случайный резервуар + считывание | Контроль пользы сложной динамики вообще |
| Фиксированный коннектом + считывание | Проверка пользы именно коннектомной структуры |

Время симуляции коннектома, подготовки признаков и ранжирования включать в end-to-end бюджет. Не давать «мухе» дополнительные действия, данные либо больше дорогих проверок относительно контроля.

Для начала сохраняем внутренние веса коннектома и обучаем только считывание, как описано в отдельной инструкции по эксперименту. Настоящий биологический граф и случайный контроль обязаны быть явно различены в метаданных. Анимация мухи — слой воспроизведения действий, не свидетельство работы коннектома.

**Критерий продолжения исследования:** устойчивый выигрыш S или времени на независимых сценах без ухудшения корректности при одинаковом ядре. Если пользы нет, оставить муху экспериментом/визуализацией и не делать её обязательной частью конкурсного solver-а.

## 20. Как принимать или отклонять улучшение

### 20.1. Обязательные условия включения в основной режим

1. Нет новых контрактных ошибок на закреплённых положительных сценах.
2. Полнота подтверждённых подключений не уменьшается; алгоритм не экономит за счёт отказа.
3. Сохранено неухудшение переданного начального проекта.
4. Есть end-to-end измерение, а не только время внутренней функции.
5. Ухудшения на отдельных сценах, таймауты и память не скрыты средним score.
6. Преимущество измерено на данных, не использованных для настройки именно этой версии.

Эвристическое улучшение не обязано победить на каждой сцене. Но production-портфель обязан сохранять уже доступный лучший проверенный кандидат, а выбранный профиль качества/времени должен быть явным.

### 20.2. Не назначать заранее желаемый score

Не ставить задачу «обязательно получить 9 вместо 11» или «минус 20%» без нижней оценки и экспериментов. Нынешний отчёт содержит разные сцены и версии входов. Лучше формулировка:

> При том же wall-clock бюджете повысить качество на парном наборе без новых INVALID; отдельно показать цену улучшения в CPU/RAM и p95.

Для инженерного решения можно заранее определить допустимые пороги времени/памяти и минимально интересный выигрыш. Но это продуктовые критерии команды, а не факты из отчёта и не гарантии алгоритма.

### 20.3. Когда перестать усложнять

- Если новый junction-оператор почти всегда дублирует старый — изменить генерацию, а не повышать число повторов.
- Если X2 ограничен геометрией, не увеличивать DP-бюджет вслепую.
- Если все элитные проекты одинаковы, не тратить время на path relinking.
- Если RL не лучше простого selector-а при тех же действиях — оставить его экспериментальным.
- Если большая часть времени ушла на отказы, сначала исправлять negative-search path.
- Если локальный exact solver не успевает, уменьшить район/модель и сохранить честный статус вместо обещания точности.

## Итоговое решение

Ближайшее улучшение — **не ещё одно имя B4 и не ещё один запуск обучения**. Нужен единый, воспроизводимый цикл:

> **Сохранить хорошую сеть → найти экономически важный район → предложить совместную перестройку с правильными габаритами → пересчитать её влияние на общий путь → проверить экспорт → сохранить улучшение.**

Сначала этот цикл обязан работать с обычным выбором действий. После этого проверяем, какой селектор — эвристика, bandit, R1/R2 или коннектом — лучше использует то же пространство конструкций и тот же вычислительный бюджет.
