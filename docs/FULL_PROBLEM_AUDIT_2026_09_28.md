# Полный аудит проблем алгоритмов и текущего решения

**Дата:** 28.09.2026  
**Статус документа:** честный аудит текущего состояния, не отчёт о готовности  
**Основной прогон:** `results/topologizer-next-iteration-final-all-algorithms-2026-09-28/`

## 1. Исправление главного неверного вывода

Текущую систему **нельзя называть полностью готовым решением задачи**.

Фраза «16/16 валидных результатов» означает только следующее: B3, R1, R2 и
PORTFOLIO на каждой из 16 сцен вернули GeoJSON, который не нарушил проверяемые
геометрические и контрактные правила. Она **не означает**, что на этих сценах
подключены все потребители.

Фактическое качество основного прогона:

- 16/16 запросов имеют сертифицированный, но часто частичный ответ;
- полностью подключена 1 сцена из 16, то есть 6,25%;
- подключено 65 ОКС из 104, то есть 62,50%;
- не подключено 39 ОКС;
- macro coverage по сценам — 61,20%;
- R1 и R2 не улучшили B3 ни на одной сцене;
- PORTFOLIO не улучшил B3, но работал примерно втрое дольше в среднем.

Итог: готова инфраструктура построения и проверки **частичного допустимого
проекта**. Алгоритм полного подключения и доказательство конкурсного качества не
готовы.

## 2. Критическая терминологическая проблема API

Сейчас API разделяет ответы на `CERTIFIED` и `DIAGNOSTIC_FALLBACK`, но не делает
столь же заметным разделение на полный и частичный проект. Частичный результат
может получить HTTP 200 и `X-Solution-Certified: true`, если его построенные
участки допустимы, а неподключенные ОКС перечислены и учтены штрафом.

Это технически соответствует текущему checker-у, но создаёт опасную
двусмысленность:

```text
CERTIFIED != ALL_TARGETS_CONNECTED
```

Необходимо добавить в API и UI отдельные признаки:

- `solution_status=FULL|PARTIAL|NO_CERTIFIED_SOLUTION`;
- `connected_oks_count`, `total_oks_count`, `coverage_percent`;
- заголовок `X-Solution-Complete: true|false`;
- запрет слов «готово» и «успех» без явного указания покрытия.

## 5. Проблемы отдельных алгоритмов

### B3

B3 — лучший текущий практический baseline, но это `IMPLEMENTED_LITE`, а не
полный оптимизатор.

Проблемы:

- подключает только 65 из 104 ОКС на regression suite;
- полностью решает 1 из 16 сцен;
- не доказывает невозможность остальных подключений;
- перебирает ограниченные порядки и локальные перестройки, а не всё пространство
  топологий;
- часто сохраняет частичное решение вместо перестройки общей схемы сети;
- не имеет полного регионального atomizer/assembler для конфликтных областей;
- не имеет доказательства оптимальности стоимости или длины.

### R1

R1 теперь безопасно стартует с сертифицированного B3 seed и не ухудшает его, но
пользы от policy в текущем пространстве действий не показано.

На 16 сценах:

- 245 действий были фактически оценены;
- 264 попытки завершились отказом;
- 230 полученных конструкций оказались дубликатами;
- улучшений архива — 0;
- R1 вернул исходный seed на всех 16 сценах;
- причины отказов: 137 геометрически небезопасных действий, 127 регрессий
  покрытия и 6 дополнительных потерь connected set.

Вывод: модель сейчас не улучшает сеть. Она в основном повторяет одинаковые
конструкции или предлагает недопустимые изменения. Повторное обучение без новых
операторов не устраняет основной предел.

### R2

R2 также совпал с B3 на всех сценах:

- улучшений — 0;
- 21 оператор отклонён;
- преимущество learned operator controller не доказано;
- дополнительное время не превращается в лучшее покрытие или стоимость.

### PORTFOLIO

PORTFOLIO вернул те же проекты, что B3/R1/R2:

- coverage и score идентичны B3;
- среднее время 21,934 с против 7,251 с у B3;
- p95 170,138 с против 76,113 с у B3;
- фактического разнообразия победителей в текущей серии нет.

Пока PORTFOLIO — дорогая страховочная оболочка, а не ансамбль, который даёт
лучший результат.

### B2-C-J

Единственный из пяти финально сравнивавшихся методов с явными потерями
сертификата:

- 13/16 сертифицированных ответов;
- две сцены завершились `NO_CERTIFIED_SOLUTION`;
- одна сцена отклонена checker-ом из-за `CHAMBER_DIAMETER_TOO_SMALL`;
- macro coverage по всем запросам — 46,09%;
- низкий средний score нельзя сравнивать с B3 напрямую, потому что он посчитан
  только по 13 выжившим ответам.

### Остальные алгоритмы API

API объявляет runnable 15 методов: PORTFOLIO, B0-GRID, B0-CORRIDOR, B1, B2-U,
B2-Q, B2-C, B2-C-J, B3, R1-PILOT, R1, R2, X0, X1 и X2.

Финальный единый 16-сценовый прогон включал только пять: B2-C-J, B3, R1, R2 и
PORTFOLIO. Поэтому утверждение «все алгоритмы проверены финальным бенчмарком»
неверно.

Дополнительные ограничения:

- B0-CORRIDOR, B1, B2-U/Q/C и B3 маркированы `IMPLEMENTED_LITE`;
- B2-C-J, R1, R2 и X2 маркированы experimental;
- R1-PILOT прямо не является production;
- X0/X1 ограничены малыми сценами;
- X2 выполняет ограниченный DP и не выдаёт глобальный сертификат оптимальности.

## 6. Проблемы топологизатора

Реализованы безопасные общие хвосты, отдельные parallel-branch repair,
пересчёт решения и post-export проверка. Но следующий модуль из приложенного
плана не завершён полностью.

Не хватает:

1. Общего geometric atomizer, который разбивает пересечения, частичные
   совпадения и обратные совпадения на атомарные рёбра.
2. Provenance каждого ребра: исходный маршрут, обслуживаемые ОКС, роль и
   направление.
3. Topology assembler, который выбирает инженерные соединения, а не просто
   объединяет линии.
4. Перебора нескольких вариантов конфликтного района из 2–4 ветвей.
5. Явной проверки циклов, двух врезок, скрытого транзита через чужой ОКС и
   перегруженных объединённых камер до дорогой финализации.
6. Транзакционного полного пересчёта потоков, диаметров, камер и стоимости для
   любого общего repair, а не только для уже реализованных частных операторов.
7. Точного подтверждения равенства после fingerprint. Миллиметровое квантование
   остаётся prefilter, а не доказательством эквивалентности сетей.

## 7. Проблемы генератора маршрутов

- «Маршрут не найден» пока означает неудачу ограниченного поиска, а не
  доказанную невозможность провести трубу.
- Порталы и visibility/grid/corridor кандидаты не гарантируют полноту
  непрерывного геометрического пространства.
- Жёсткий nearest-boundary ruleset может исключать маршруты, которые допустимы
  при другой интерпретации ТЗ. Менять ruleset ради процента нельзя; требуется
  отдельное юридически/экспертно подтверждённое правило.
- Ограничение углов проверяется, но локальное исправление поворотов может не
  найти существующий более длинный допустимый обход.
- Собственное здание разрешено только на конечном подходе. Ошибка в
  классификации собственного ОКС или ближайшей грани сразу уничтожает маршрут.
- Исправленная sub-millimeter ошибка показала, что round-trip координат влияет
  на дискретные геометрические решения. Нужны дополнительные пограничные тесты.

## 8. Проблемы валидации и бенчмарка

### Что проверяется хорошо

- GeoJSON-контракт;
- связность обслуживаемых ОКС;
- диаметры и расходы;
- углы поворота;
- запрещённые пересечения;
- конечный вход в ОКС;
- камеры и степень узлов;
- overlap;
- повторная проверка после экспорта.

### Что остаётся ограничением

- Checker внутренний, а не официальный внешний judge организаторов.
- `rule_catalog.json` сам помечен как `not_a_complete_geometry_rule_engine`.
- Известные 16 сцен многократно использовались для разработки и больше не
  являются честным неизвестным holdout.
- Нет финального прогона на отдельном неиспользованном наборе городов/районов.
- Нет нескольких повторов для оценки стабильности времени.
- Время измерялось при четырёх параллельных worker-ах на одной машине; p95
  зависит от конкуренции запросов за CPU.
- «Победа» в таблице определяется внутри частичных решений и не заменяет полный
  конкурсный критерий.
- Средний score по разному числу валидных сцен нельзя сравнивать напрямую.
- 36 тестов из последнего ZIP были спецификациями со статусом
  `NOT_IMPLEMENTED_IN_THIS_PACKAGE`; часть сценариев покрыта нашими тестами, но
  полный traceability matrix 36/36 не закрыт.

## 9. Проблемы данных

- Большой набор построен из реальной OSM-геометрии, но точки спроса и некоторые
  производные сцены подготовлены нашим pipeline, а не подтверждены заказчиком
  как реальные объекты подключения.
- Требуется сохранять связь `ОКС → конкретное здание → источник свойства
  flow_tph` и показывать её в UI.
- Нужен аудит каждой точки на нахождение внутри правильного собственного ОКС,
  отсутствие дубликатов и реалистичность расхода.
- Производные bucket-сцены из одной parent-географии нельзя распределять между
  train/test как независимые объекты.
- Исходный конкурсный датасет и расширенный исследовательский набор должны быть
  раздельными когортами в отчёте.

## 10. Проблемы визуализатора

Исправлено:

- подключённые ОКС теперь зелёные, неподключённые розовые;
- источник отделён красным цветом;
- обводки сегментов вынесены под зелёную сеть;
- удалена анимация, при которой оставалась видна чёрная подложка без трубы.

Остаётся:

- UI показывает `15/17`, но должен ещё крупно писать `ЧАСТИЧНОЕ РЕШЕНИЕ`;
- нужен список неподключённых ID с переходом к точке на карте;
- нужна видимая причина отказа для каждой точки;
- требуется режим «только новая сеть» и режим пути конкретного ОКС до врезки;
- отдельные зелёные компоненты, подключённые к разным участкам старой сети,
  визуально могут восприниматься как разрыв без подсветки существующего пути.

## 11. Проблемы воспроизводимости и репозитория

- Manifest теперь содержит content hashes и параметры запуска.
- Однако текущий Git checkout остаётся dirty: множество изменений и артефактов
  не закреплены одним проверенным commit-ом.
- Commit `d23e2916e63a311604d30a215872e7e7fe9eec7d` не описывает всё текущее
  состояние; воспроизводимость сейчас опирается на hashes рабочего дерева.
- Generated results занимают много места и требуют политики: какие отчёты
  коммитятся, какие архивируются отдельно.
- Нужен CI, который собирает Docker, запускает unit/integration tests,
  post-export checker и короткий regression benchmark.

## 12. Что действительно готово

- чтение исходного GeoJSON;
- REST API и OpenAPI;
- несколько исполняемых эвристик;
- построение частичных сетей;
- расчёт расходов, диаметров, стоимости и штрафов для принятого результата;
- внутренний и post-export geometry guard;
- независимый Python checker;
- диагностический fallback, отделённый от сертифицированного ответа;
- защита B3 seed в R1/R2;
- viewer исходных данных и результата;
- воспроизводимые manifests и построчные checker reports.

## 13. Что не готово

- гарантированное или практически высокое подключение всех достижимых ОКС;
- доказательство, какие из 39 пропусков физически невозможны;
- полная реализация atomizer/topology assembler/regional graph repair;
- преимущество RL над обычным поиском;
- полезное разнообразие PORTFOLIO;
- финальный benchmark всех 15 API-алгоритмов на одной конфигурации;
- неизвестный holdout и доказательство обобщения;
- официальный внешний сертификат соответствия ТЗ;
- однозначная продуктовая маркировка частичного ответа;
- конкурсная готовность, которую можно честно назвать «полным решением».

## 15. Критерий, после которого можно говорить «готово»

Слово «готово» допустимо только после одновременного выполнения условий:

1. API однозначно различает полный и частичный ответ.
2. Для каждого неподключённого ОКС есть проверяемая причина, а не общий
   `no route found`.
3. На исходном датасете получено 17/17 либо документировано, почему конкретные
   точки недостижимы по подтверждённым правилам ТЗ.
4. Целевой уровень полного покрытия заранее согласован и достигнут на неизвестном
   holdout, а не только на 16 разработческих сценах.
5. Финальный GeoJSON проходит независимый post-export checker.
6. Все заявленные production-алгоритмы, API и viewer проверяются CI.
7. Версия закреплена commit/tag и воспроизводимым Docker image digest.
